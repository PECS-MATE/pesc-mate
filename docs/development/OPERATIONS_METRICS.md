# API 음성 동기화 지표와 운영 알림

> 통합일: 2026-11-04 · 현재 사용 안내와 과거 구현 기록을 구분합니다.

API 처리·클라이언트 음성 재생·오프라인 동기화·운영 알림은 서로 다른 지표입니다. 요청 성공, 카드 선택, 문장 저장, 음성 재생 성공을 같은 사건으로 합산하지 않습니다. 조회 권한과 집계 기간·분모·누락 한계를 확인하고, 실제 장애 대응·감사 보관·백업 절차는 docs/operations를 따릅니다.

과거 날짜의 검사 통과는 현재 버전 전체의 검수나 운영 배포 승인이 아닙니다. 상세 기록에는 이전 화면·제거된 기능 설명도 있으므로 현재 사용 경로는 위 안내를 우선하고, 남은 실제 기기·권한·음성 검수는 TODO와 각 절의 미실행 기록을 확인하세요.

<a id="api-metrics--api-오류율과-응답-시간-지표"></a>
### API 오류율과 응답 시간 지표

`GET /api/admin/metrics`는 현재 API 프로세스의 요청 수, 오류율과 처리 시간 분포를 반환한다.
기존 `content_manage` 운영 권한 검사를 적용한다. AAC 사용자·보호자·일반 담당자는 403,
비로그인 요청은 401이며 모든 지표 응답은 `Cache-Control: no-store`를 사용한다.

<a id="api-metrics--수집-범위"></a>
#### 수집 범위

- 단위: 요청 전체와 HTTP 메서드·등록된 경로 템플릿별 집계
- 보관: 현재 1분과 직전 14분, 총 15개의 1분 버킷
- 내용: 요청 수, 4xx·5xx·응답 시작 후 전송 오류, 처리 시간의 합계·평균·최댓값·분포
- 시간: 요청 진입부터 ASGI 처리 완료까지의 시간. 스트리밍과 후처리 시간을 포함하며 화면 로딩 시간이나 TTS 소리 시작 시간이 아니다.
- 개인정보: 사용자 ID가 들어간 실제 URL, 쿼리, 본문, 토큰, 이름, 이미지 경로, 요청 ID, IP를 보관하지 않는다.
- 경로: 예를 들어 사용자별 요청도 `/profile/{user_id}/image` 같은 하나의 템플릿으로 집계한다. 매칭되지 않은 URL은 `unmatched`로 묶는다.
- 크기 제한: 메서드·경로 조합 128개와 초과분 `OTHER / other` 하나로 제한한다. 개별 요청이나 원시 지연 샘플은 보관하지 않는다.

집계는 메모리에만 저장하고 MongoDB에 추가로 쓰지 않는다. 계정 인증의 기존 DB 조회는 유지한다.
집계 실패가 정상 API 응답을 실패로 바꾸지 않으며 예외 원문도 로그에 출력하지 않는다.

<a id="api-metrics--조회"></a>
#### 조회

운영 권한 계정으로 로그인한 세션 토큰을 사용한다. 실제 토큰은 문서·공유 로그에 기록하지 않는다.

```http
GET /api/admin/metrics
Authorization: Bearer {access_token}
```

응답에는 다음 필드가 있다. `totals`와 각 `routes[]`는 같은 집계 필드를 사용한다.

| 필드 | 의미 |
|---|---|
| `scope` | `process`: 요청을 처리한 프로세스 하나의 집계 |
| `reset_on_restart` | `true`: 재시작·개발 리로드 시 초기화 |
| `window_seconds`, `bucket_seconds` | 최대 보관 범위 900초, 버킷 60초 |
| `uptime_seconds` | 해당 집계기 생성 후 경과 시간 |
| `totals.requests` | 현재 버킷 범위의 전체 요청 수 |
| `client_errors`, `server_errors` | 4xx, 5xx 응답 수 |
| `transfer_errors` | 성공 응답 헤더를 보낸 뒤 전송에 실패한 요청 수 |
| `errors`, `error_rate` | 4xx + 5xx + 전송 오류와 전체 요청 대비 비율 |
| `server_error_rate` | 5xx + 전송 오류의 전체 요청 대비 비율 |
| `duration_ms.sum`, `mean`, `max` | 처리 시간 합계·평균·최댓값, 단위 ms |
| `duration_ms.p50_upper_bound`, `p95_upper_bound` | 해당 백분위가 속하는 시간 버킷의 상한 |
| `duration_ms.buckets[]` | `le_ms` 이하인 요청의 누적 개수 |
| `routes[]` | 메서드·경로 템플릿별 집계 |

비율은 0~1이다. 예를 들어 `0.02`는 2%다. 전송 오류는 성공 헤더를 보낸 경우에만
별도로 세므로 5xx와 중복 합산하지 않는다. 401·403·404도 클라이언트 오류에 포함되므로
서버 장애 판단은 `server_error_rate`와 해당 경로를 함께 확인한다.

시간 버킷 상한은 10·25·50·100·250·500·1000·2500·5000·10000ms와 무한대다.
무한대는 `le_ms: null`이며 마지막 버킷 개수는 전체 요청 수와 같다. 백분위 상한은
정확한 백분위 시간이 아니다. 예를 들어 `p95_upper_bound: 500`은 95번째 백분위가
500ms 이하인 버킷에 있다는 뜻이다. 10초 초과 버킷에 속하거나 표본이 없으면 null이다.
표본이 없을 때 평균·최댓값도 null이며 요청 수와 오류율은 0이다.

버킷 경계에서 만료하므로 정확한 직전 900초 이동 구간과 최대 1분 차이가 날 수 있다.
헬스 체크·지표 조회·CORS preflight도 포함한다. 현재 지표 조회 요청 자체는 응답 집계에
아직 들어가지 않고 다음 조회부터 반영된다.

<a id="api-metrics--운영-한계와-다음-단계"></a>
#### 운영 한계와 다음 단계

현재 로컬 단일 프로세스 개발 환경을 위한 지표다. 재시작 이전 이력은 유지하지 않고,
여러 worker·서버의 값을 자동으로 합치지 않는다. 장기 추세·외부 알림·다중 프로세스 집계가
필요하면 별도 수집기로 전달하는 단계가 필요하다. 이 API의 집계를 전체 운영 서버의
누적 성공률이나 실제 기기 TTS 성공률로 해석하지 않는다.

현재 프로세스의 반복 실패를 운영자 화면에 표시하는 기능은
[운영 알림](OPERATIONS_METRICS.md#operational-alerts)에서 별도로 제공한다.

### TTS 시작 지연과 실패율

<a id="tts-metrics--현재-기본-출력-경로"></a>
#### 현재 기본 출력 경로

서버 연결 시 [로컬 MeloTTS](SPEECH_AND_AI.md#melo-tts)의 `/api/tts/speech` WAV를 우선 사용한다.
아래 기기 합성 수정 기록은 이전 경로 및 오프라인/진단 경로에 해당한다.
새 문장 음성 자체는 저장하지 않으며 기존 동의 기반 재생 결과만 별도 기록한다.
시작 지연은 서버 합성·파일 다운로드를 포함한 실제 `playing` 이벤트까지의 시간이다.

<a id="tts-metrics--2026-11-03-유나-선택-후-기기-음성-무음-후속-수정"></a>
#### 2026-11-03 유나 선택 후 기기 음성 무음 후속 수정

- 실제 iPad에서 기본 녹음은 들리지만 `유나 · 기기 저장`을 선택해도 기기 음성은
  들리지 않는다는 사용자 확인을 받았다. 음성 목록의 localService 표시는 설치 정보이며
  실제 청취 성공을 보장하지 않는다. 현재 iPad 무음의 단일 원인은 확정하지 않았다.
- 직접 말하기/기기 음성 테스트에서는 무음 Audio 준비를 선행하지 않도록 수정했다.
  비동기 문장 생성 전에 준비한 무음 Audio도 실제 SpeechSynthesis 시작 전에 중지·정리한다.
  새 발화 직전에 남은 합성 큐를 취소하고 paused 상태면 resume한 뒤 동기적으로 speak한다.
- [WebKit의 음성 합성·다른 미디어 간 간섭 기록](https://bugs.webkit.org/show_bug.cgi?id=218815)을
  참고하여 두 출력 경로의 중첩을 줄였다. 과거 보고이며 현재 기기의 동일 결함 확정 근거는 아니다.
- 기기 음성 테스트는 녹음으로 대체하지 않는 합성 전용 검사로 바꿨다.
  `한국어 기본 음성 테스트`를 추가해 voice 객체를 명시하지 않고 lang=ko-KR만 전달한다.
  기존 음성 선택 설정은 바꾸지 않으며 기본 녹음 전용 검사도 유지한다.
- 검증: 프런트엔드 빌드·변경분 공백 검사 통과. 기존 큰 JS 청크 경고 유지.
  일회성 Node 대역 검사로 무음 Audio 정리가 speak보다 먼저 수행됨, 큐 취소·재개 순서,
  선택 음성/기본 음성 전달, 늦은 unlock 완료 격리, 기본 녹음 시작을 확인했다.
- 실제 iPad/WebKit 청취·기본 음성 테스트·무음 모드/블루투스 출력·오프라인 전체 회귀는
  미실행이다. 모의 검사 성공을 실제 무음 해결로 표시하지 않는다. 유료 TTS는 추가하지 않았다.

<a id="tts-metrics--2026-11-03-기기-음성-재생-보강"></a>
#### 2026-11-03 기기 음성 재생 보강

- 현재 임의 문장은 브라우저/접속 기기의 SpeechSynthesis로 읽는다. 외부 유료 TTS나
  서버 동적 음성 합성은 이번 변경에서 추가하지 않았다. 기록 API는 음성 파일 생성 API가 아니다.
- iPad에서 카드·문장 모두 소리가 없다는 보고가 있어, 탭 시 현재 기기의 한국어 음성을 다시 조회한다.
  다른 PC에서 저장한 음성 이름이 없으면 이 기기의 한국어 음성으로 대체하며 ko_KR 표기도 인식한다.
- 사용자 클릭 시 같은 Audio 요소를 50ms 무음 WAV로 준비하고 기본 녹음 대체 경로에도 재사용한다.
  녹음 실패 시 기기 음성, 기기 음성 실패 시 녹음으로 각각 한 번만 대체하고 순환 재시도는 막는다.
  과거 play Promise의 늦은 완료가 새 오디오를 정지시키지 않게 했다.
- 기기 음성 시작 제한 시간을 2.5초에서 6초로 늘렸다. 기본 긴급/복구 녹음은 준비 작업 완료 전에도
  번들 manifest의 정적 URL로 재생한다. 오프라인에서는 준비된 Blob 경로를 우선한다.
- 설정의 기기 음성 테스트와 기본 녹음 테스트를 분리했다. 녹음 테스트는 기기 음성으로 대체하지 않아
  재생 경로를 구분할 수 있다. 권한 실패 시 직접 다시 재생하기와 음량/블루투스 확인을 안내한다.
- iOS의 사용자 동작 제한 때문에 비동기 문장 생성 후 자동 재생이 여전히 막힐 수 있다.
  이 경우 표현을 유지하고 사용자가 다시 재생을 직접 누르게 한다. 무오류를 보장하지 않는다.
- [WebKit iOS 재생 정책](https://webkit.org/blog/6784/new-video-policies-for-ios/),
  [동일 요소 재사용 안내](https://webkit.org/blog/7734/auto-play-policy-changes-for-macos/),
  [iOS SpeechSynthesis 사용자 동작 관련 기록](https://bugs.webkit.org/show_bug.cgi?id=223473)을 참고했다.
- 검증: 프런트엔드 빌드·공백 검사 통과. 기존 청크 경고 유지.
  일회성 Node 대역 검사로 한국어 선택·공유 오디오 준비·양방향 대체·녹음 전용 오류·
  늦은 play 완료의 격리를 확인했다. 실제 iPad/Safari/Chrome·기기 음량·블루투스·
  실제 청취·중단/재개 전체 회귀·오프라인 실물 검수는 미실행이다. 사용자 재확인이 필요하다.

`GET /api/admin/tts-metrics?hours=24`는 기존 `tts_events`에서 클라이언트가 보고한
최종 재생 결과와 시작 지연을 집계한다. `content_manage` 운영 권한이 필요하며
비로그인은 401, AAC 사용자·보호자·일반 담당자는 403이다. 응답은 캐시하지 않는다.

<a id="tts-metrics--수집과-조회"></a>
#### 수집과 조회

클라이언트는 재생을 먼저 시작하고 기존 `POST /api/tts/events`와
`PATCH /api/tts/events/{request_id}`로 이력을 보고한다. 별도의 발화 원문·녹음·음성 파일이나
지표용 사용자별 복제본은 추가 저장하지 않는다.

```http
GET /api/admin/tts-metrics?hours=24
Authorization: Bearer {access_token}
```

- `hours`: 기본 24, 1~168시간. 범위를 벗어나면 422다.
- 기간: 요청 시각 `requested_at`이 조회 시점 이전의 지정 기간에 포함된 건이다. 완료 시각 기준이 아니다.
- 조회: MongoDB에서 시간 조건·고정 분류로 집계한다. `requested_at` 인덱스와 `maxTimeMS=2000`을 적용한다. DB 집계 실패·시간 초과는 503이다.
- 보관: 기존 개인정보 삭제·보존 기간 정책을 그대로 따른다. 삭제된 이력은 다음 조회 집계에서도 빠진다.
- 재시작: 기존 이력에서 다시 계산하므로 API 프로세스를 재시작해도 저장된 기간의 결과를 조회할 수 있다.

<a id="tts-metrics--결과와-분모"></a>
#### 결과와 분모

| 필드 | 의미 |
|---|---|
| `scope`, `source` | `stored_events`, `client_reported` |
| `requested_from`, `requested_until`, `window_hours` | 요청 시각 기준 조회 구간 |
| `totals.requests` | 해당 기간에 저장된 고유 재생 요청 수 |
| `succeeded`, `failed` | 성공·실패로 완료 보고된 건수 |
| `cancelled` | 사용자 중지·다른 발화로 교체·화면 숨김 등 취소 건수 |
| `requested` | 완료 결과가 보고되지 않은 건수. 현재 재생 중임을 보장하지 않는다. |
| `other` | 이전 데이터에 알 수 없는 상태가 있는 경우의 고정 분류 |
| `resolved` | `succeeded + failed` |
| `success_rate`, `failure_rate` | 각각 성공·실패 수를 `resolved`로 나눈 0~1 비율 |
| `startup_ms.samples` | 유효한 시작 지연값을 보고한 완료 건수 |
| `startup_ms.mean`, `max` | 유효 표본의 평균·최댓값, 단위 ms |
| `startup_ms.p50_upper_bound`, `p95_upper_bound` | 백분위가 포함된 지연 버킷의 상한 |
| `startup_ms.buckets[]` | `le_ms` 이하인 지연 표본의 누적 개수 |
| `by_content_type[]` | 카드·문장·복구·미리 듣기 종류별 동일 집계 |
| `failure_codes[]` | 실패 상태의 허용된 오류 코드별 건수 |

취소·결과 미수신·알 수 없는 상태는 성공률·실패율의 분모에서 제외한다.
성공·실패 보고가 하나도 없으면 두 비율은 null이다. 이를 0% 실패로 해석하지 않는다.

시작값이 있는 성공·실패·취소 완료 건의 0~60000ms 값을 지연 표본으로 사용한다.
0ms도 유효한 표본이며 누락·잘못된 값은 0으로 바꾸지 않는다. 표본이 없으면 평균·
최댓값·백분위 상한은 null이다. 지연 버킷 상한은 100·250·500·1000·2500·5000·
10000·30000·60000ms이고, 마지막 누적 개수는 표본 수와 같다. 백분위는 정확한
원시 지연 시간이 아니라 해당 버킷의 상한이다.

<a id="tts-metrics--중복과-최초-결과-보존"></a>
#### 중복과 최초 결과 보존

- 시작 요청은 요청 ID·소유자로 원자적으로 생성하며, 재전송하면 실제 저장된 상태를 반환한다. 이미 완료한 건을 `requested`로 되돌리지 않는다.
- 최초 완료만 `requested` 상태에서 원자적으로 전환한다. 재전송·동시 완료 요청은 최초 저장된 상태·시각·지연을 반환한다.
- 같은 ID에 다른 결과를 보내도 최초 결과를 덮어쓰지 않는다. 실제로 다시 재생할 때는 새 UUID를 사용한다.
- 다른 사용자의 요청 ID로 시작하면 409, 완료하려 하면 404다.
- 지표는 요청 ID당 한 문서에서 계산하므로 중복 전송을 별도 재생으로 합산하지 않는다.

<a id="tts-metrics--개인정보와-해석-한계"></a>
#### 개인정보와 해석 한계

지표 응답에는 사용자·요청 ID, 이름, 발화 원문, 글자 수, 음성 이름, 이미지 URL을 포함하지 않는다.
DB에서 종류·상태·오류 코드를 정해진 분류로 바꾼 뒤 집계한다. 임의 오류 코드에 텍스트가
입력돼도 지표에는 `other`로만 표시하며, 취소 사유를 실패 코드에 섞지 않는다.

성공은 클라이언트가 최종 재생 완료를 보고했다는 뜻이다. 기기 TTS가 실패해도 기본 WAV로
대체 재생이 끝나면 성공으로 집계한다. 최초 TTS 엔진 자체의 실패율이나 사람이 실제로
소리를 들었는지를 이 값으로 판정하지 않는다.

네트워크 없이 재생해 TTS 이력을 전송하지 못한 경우와 볼륨 0으로 재생 전에 차단한 경우는
이 집계에 포함되지 않는다. 따라서 전체 오프라인 재생 성공률이나 실제 기기 지원 판정은
실제 기기에서 별도로 확인한다.
외부 경보와 기기별 분석은 이번 구현에 포함하지 않는다. 집계된 최종 실패의
운영자 화면 안내는 [운영 알림](OPERATIONS_METRICS.md#operational-alerts)을 따른다.

## 오프라인 동기화 지표

<details>
<summary>상세 구현·설정·검증 기록</summary>

<a id="offline-sync-metrics--오프라인-동기화-지표"></a>
### 오프라인 동기화 지표

`GET /api/admin/offline-sync-metrics`는 현재 API 프로세스가 확인한 오프라인 발화·학습
동기화 결과를 집계한다. `content_manage` 운영 권한이 필요하다. 비로그인은 401,
AAC 사용자·보호자·일반 담당자는 403이며 응답은 `Cache-Control: no-store`다.

<a id="offline-sync-metrics--범위와-보관"></a>
#### 범위와 보관

- 발화: `POST /api/offline/events/sync`의 실제 저장 결과를 수집한다.
- 학습: `POST /api/learning/attempts` 중 `X-Pesc-Offline-Sync: true`인 요청만 수집한다. 일반 온라인 학습은 제외한다.
- 현재 1분과 직전 14분을 합친 15개의 1분 버킷을 프로세스 메모리에 보관한다. 집계 시각은 서버 처리 종료 시점이다.
- 종류는 `communication`, `learning` 두 개, 오류는 `conflict`, `database`, `validation`, `internal` 네 개로 고정한다. 개별 요청과 사용자별 시계열을 만들지 않는다.
- 사용자·요청·카드 ID, 이름, 발화·문제 원문, 점수, 이미지 경로, IP, 토큰과 예외 원문을 저장하지 않는다. 지표용 DB 컬렉션도 만들지 않는다.
- 재시작·개발 리로드 시 초기화되며 여러 worker의 값을 합산하지 않는다. 개인정보 삭제 후에도 개인과 연결할 수 없는 짧은 기간의 합계만 만료 시까지 남는다.
- 지표 수집 오류는 성공한 저장 응답이나 원래의 오류 상태를 바꾸지 않는다.

<a id="offline-sync-metrics--필드-정의"></a>
#### 필드 정의

`totals`와 `by_kind[]`는 같은 집계 필드를 가진다.

| 필드 | 의미 |
|---|---|
| `scope`, `source`, `retry_source` | `process`, `server_observed`, `client_marked` |
| `window_seconds`, `bucket_seconds`, `reset_on_restart` | 900초, 60초, true |
| `operations` | 검증·권한·동의 확인 후 서비스 처리에 진입한 요청 수 |
| `failed_operations` | 서비스 처리 중 예외로 종료한 요청 수 |
| `operation_failure_rate` | `failed_operations / operations`, 표본이 없으면 null |
| `received` | 서비스에 전달한 항목 수. 재전송된 항목도 매번 포함 |
| `retried` | 기기의 이전 전송 시도 표시가 있는 항목 수. 서버가 받은 헤더 기준 |
| `inserted` | 이번 처리에서 실제 신규 삽입한 항목 수 |
| `duplicates` | 같은 소유자의 같은 UUID가 이미 저장돼 재삽입하지 않은 항목 수 |
| `failed` | 처리 중 오류가 발생한 항목 수 |
| `unprocessed` | 앞선 항목의 오류로 처리를 시작하지 못한 나머지 항목 수 |
| `errors` | 고정 오류 분류별 실패 요청 수 |

각 요청에서 `received = inserted + duplicates + failed + unprocessed`다.
`retried`는 이 분할과 별개이며, 신규 저장인지 중복인지와 관계없이 포함될 수 있다.
3건 중 첫 항목 저장 후 둘째 항목이 충돌하면 신규 1·실패 1·미처리 1이다.
묶음 전체를 실패 3건으로 세거나 이미 저장한 첫 항목을 되돌리지 않는다.
충돌 건을 제외하고 처음·마지막 항목을 재전송하면 중복 1·신규 1이 된다.

<a id="offline-sync-metrics--재시도-표시와-호환"></a>
#### 재시도 표시와 호환

기기는 전송 직전에 기존 IndexedDB 대기 항목에 `sync_attempted: true`를 원자적으로
기록한다. 이전 값이 true였던 항목만 이번 `retried` 수에 포함한다. 스토어 버전 변경은
없으며 이전 데이터의 누락된 표시는 첫 시도로 해석한다. 표시 저장에 실패하면 해당
항목을 보내거나 지우지 않고 기존 재시도 안내를 유지한다.

- 발화 묶음의 선택 헤더: `X-Pesc-Sync-Retried: 0~100`, 해당 묶음의 건수 이하여야 한다.
- 학습 동기화: `X-Pesc-Offline-Sync: true`와 `X-Pesc-Sync-Retried: 0~1`을 보낸다.
- 헤더 생략 시 재시도 수는 0이며, 기존 클라이언트의 본문과 응답 형식은 그대로다.
- 잘못된 헤더나 전송 건수보다 큰 재시도 수는 422다. 일반 온라인 학습에 재시도 수를 보내도 422다.
- 로컬 표시와 `user_id`는 본문에 넣지 않으며 서버 기록·내보내기에 복제하지 않는다.
- 표시도 대기 항목의 일부이므로 로그아웃·개인정보 삭제 시 기존 대기열과 함께 제거한다.
- 새로고침 후에도 표시가 남는다. 서버 응답이 유실되거나 기기 대기열 삭제가 실패해도 같은 UUID로 재전송한다.
- 전송 준비 직후 취소되거나 기기에서 서버까지 도달하지 못한 첫 시도도 표시가 남을 수 있다. 따라서 `retried`는 이전 서버 수신을 증명하지 않는다.

실제 중복 수는 클라이언트 표시가 아니라 MongoDB 삽입 결과로 판정한다. 같은 UUID의
동시 upsert에서 다른 요청이 먼저 저장해도 같은 소유자면 중복으로 수락하고, 다른
소유자면 409다. 학습 결과도 기존 최초 기록을 유지하고 중복 수락 결과를 집계한다.

<a id="offline-sync-metrics--해석-한계와-장애-확인"></a>
#### 해석 한계와 장애 확인

서버에 도착하지 않은 통신 실패, 기기의 IndexedDB 읽기·쓰기·삭제 실패, 수신 응답
유실은 이 서버 지표의 실패 건수로 직접 집계할 수 없다. 예를 들어 DB에는 저장됐으나
기기가 응답을 못 받으면 첫 시도는 신규 저장, 다음 서버 수신은 중복으로 집계된다.
서버 실패가 0이어도 기기 동기화 성공률 100%라는 뜻이 아니다. 기기의 남은 건수·
실패 안내와 [오프라인 검수](../policies/OFFLINE_POLICY.md)를 함께 확인한다.

인증·동의 거절, Pydantic 본문·헤더 검증처럼 서비스 진입 전 종료한 요청은 이 합계에
포함하지 않는다. HTTP 단계의 4xx·5xx와 요청 추적은 [API 지표](OPERATIONS_METRICS.md#api-metrics)와
기존 요청 ID 로그에서 확인한다. 서비스 오류 분류는 409 충돌, 503 DB, 422 값 불일치,
그 외 예외는 내부 오류다. 외부 경보·장기 보관·기기별 분석은 이 구현에 포함하지 않는다.
반복 실패의 운영자 화면 안내는 [운영 알림](OPERATIONS_METRICS.md#operational-alerts)을 따른다.

## 운영 알림

<details>
<summary>상세 구현·설정·검증 기록</summary>

<a id="operational-alerts--운영-알림"></a>
### 운영 알림

운영 권한 담당자에게만 공용 카드 검수 대기와 반복 실패를 안내한다.
`GET /api/admin/alerts`는 `content_manage` 권한이 필요하며, 비로그인 401,
AAC 사용자·보호자·일반 담당자는 403이다. 응답은 `Cache-Control: no-store`다.

<a id="operational-alerts--초기-파일럿-기준"></a>
#### 초기 파일럿 기준

다음 값은 서비스 품질 보장 수치나 장애 확정 기준이 아니라 점검을 시작하는 기본값이다.
운영 결과에 따른 조정은 별도 검토하며, 응답 `thresholds`에 현재 기준을 반환한다.

| 알림 | 기준 | 범위 |
|---|---|---|
| `review_pending` | 공개 승인 대기 1건 이상 | `visibility=shared`, `status=pending`만 포함 |
| 같은 대기 알림의 경고 등급 | 가장 오래된 대기가 24시간 이상 | 서버 UTC 기준, 경계 포함 |
| `api_repeated_failure` | 서버 오류+성공 헤더 이후 전송 오류 3회 이상 | 현재 프로세스의 최근 최대 15개 1분 버킷 |
| `tts_repeated_failure` | 최종 재생 실패 보고 3건 이상 | 최근 1시간에 요청한 저장 이력 |
| `offline_sync_repeated_failure` | 서비스 처리 중 실패한 동기화 요청 3회 이상 | 현재 프로세스의 최근 최대 15개 1분 버킷 |

검수 대기는 기본 `info`, 오래된 대기와 반복 실패·조회 불가는 `warning`이다.
대기 건수는 전체 공용 대기 수이고, 오래된 카드 수를 뜻하지 않는다. 날짜가 없는
이전 기록은 대기 수에 포함하되 24시간 경과를 추정하지 않는다.
개인 카드·공용 초안·승인·반려·비활성은 대기 수에 포함하지 않는다.

API의 401·403·404 등 클라이언트 오류는 API 반복 실패 알림에서 제외한다.
TTS 취소·결과 미수신은 실패로 취급하지 않으며, 기기 엔진 실패 후 기본 WAV가
끝까지 재생됐다면 최종 성공이다. 동기화 알림은 실패한 **요청 수** 기준이지
실패 항목·재시도·중복 수 기준이 아니다. 잘못된 학습 값처럼 서비스에서 422로
거절한 동기화도 점검 대상에 포함한다.

<a id="operational-alerts--응답과-장애-격리"></a>
#### 응답과 장애 격리

`generated_at`, `status`, `thresholds`, `sources`, `alerts`를 반환한다.
`sources`는 `review_queue`, `api`, `tts`, `offline_sync`이며 각각 `status=ok` 또는
`unavailable`이다. 성공한 출처만 해당 합계와 집계 범위를 포함한다. 출처 하나를
확인하지 못하면 응답은 200·`status=partial`로 반환하고 해당 출처의 `_unavailable`
경고를 추가하며, 확인된 다른 알림은 유지한다. 전체 요청 오류는 기존 공통 API
오류 응답을 따른다. 조회 불가를 0건이나 정상으로 바꾸지 않는다.

알림은 고정 `code`, `severity`, `title`, `message`, `count`, `action`을 가진다.
같은 원인은 코드 하나로만 표시하며 누적 알림 문서를 만들지 않는다. 조회 시점에
임계값 아래로 내려가거나 검수가 끝나면 다음 갱신에서 사라진다. 확인·읽음·
강제 해제·숨기기·소리·이메일·외부 푸시 발송 기능은 없다.

검수는 MongoDB에서 합계와 최초 시각만 집계하고 `shared_review_queue` 인덱스와
`maxTimeMS=2000`을 적용한다. 이미지·카드 원문·사용자별 목록은 가져오지 않는다.
TTS는 기존 시간 인덱스와 제한 시간 집계를 재사용한다. 새 개인정보 컬렉션,
별도 음성·이미지 저장, 사용자별 알림 추적은 추가하지 않는다. 지표 응답에는
사용자·요청·카드 ID, 이름, 카드명, 발화·문제 원문, 이미지 URL, 임의 오류 코드를
넣지 않는다. 예외 원문을 알림 문구로 반환하지 않는다.

<a id="operational-alerts--화면-갱신"></a>
#### 화면 갱신

- 운영 권한 계정의 화면 상단에 `운영 알림`을 표시한다. 일반 사용자 화면에서는 조회하지 않는다.
- 처음 표시할 때, 검수 목록 변경 후, 수동 새로고침, 숨긴 탭으로부터 복귀 시 조회한다.
- 탭이 표시 중이면 60초 간격으로 조회한다. 같은 갱신 주기의 진행 중 요청은 겹치지 않는다.
- 이전 갱신이나 로그아웃·계정 변경 후 늦은 응답은 화면을 덮어쓰지 않는다. 언마운트 시 타이머와 이벤트 감시를 해제한다.
- 조회 실패 시 마지막 결과를 유지하되 이전 결과임을 명시하고 재확인을 안내한다. 최초 실패는 빈 정상 상태로 표시하지 않는다. 401·403이면 이전 결과도 제거한다.
- 검수 알림에서 `검수 목록 열기`로 기존 승인 화면에 이동한다. 승인·반려 후 대기 수를 다시 조회한다.
- 숫자와 제목은 별도 요소로 두고 좁은 화면에서는 줄바꿈한다. 팝업·소리로 아동의 의사소통을 끊지 않는다.

<a id="operational-alerts--운영-해석"></a>
#### 운영 해석

표본이 없다는 것은 장애가 없다는 증거가 아니다. 운영 화면을 닫거나 브라우저가
정지되면 화면 알림도 갱신되지 않는다. 백그라운드 감시 서버와 외부 당직 호출을
대체하지 않는다. API·동기화 지표는 재시작·개발 리로드 시 초기화되고 여러 worker를
합치지 않는다. TTS는 기존 DB 기록에서 재집계하며 개인정보 삭제·보관 기간 정책을 따른다.

서버에 도착하지 않은 통신 실패와 기기 저장 실패는 서버 실패 수에 직접 잡히지 않는다.
필요하면 각 지표 API와 요청 ID 로그, 해당 기기의 남은 기록과 재생 상태를 함께
확인한다. 자동 승인·이력 삭제·전체 재전송 같은 조치를 알림이 실행하지 않는다.
상세 분모는 [API 지표](OPERATIONS_METRICS.md#api-metrics), [TTS 지표](OPERATIONS_METRICS.md#tts-metrics),
[오프라인 동기화 지표](OPERATIONS_METRICS.md#offline-sync-metrics)를 따른다.

알림의 `info`·`warning`은 장애 등급이나 자동 중단 명령이 아니다. 영향에 따른 등급·
담당자 호출·증거 보존·복구 확인은 [장애 대응 절차](../operations/INCIDENT_RESPONSE.md)를 따른다.
