# 오프라인 동기화 지표

`GET /api/admin/offline-sync-metrics`는 현재 API 프로세스가 확인한 오프라인 발화·학습
동기화 결과를 집계한다. `content_manage` 운영 권한이 필요하다. 비로그인은 401,
AAC 사용자·보호자·일반 담당자는 403이며 응답은 `Cache-Control: no-store`다.

## 범위와 보관

- 발화: `POST /api/offline/events/sync`의 실제 저장 결과를 수집한다.
- 학습: `POST /api/learning/attempts` 중 `X-Pesc-Offline-Sync: true`인 요청만 수집한다. 일반 온라인 학습은 제외한다.
- 현재 1분과 직전 14분을 합친 15개의 1분 버킷을 프로세스 메모리에 보관한다. 집계 시각은 서버 처리 종료 시점이다.
- 종류는 `communication`, `learning` 두 개, 오류는 `conflict`, `database`, `validation`, `internal` 네 개로 고정한다. 개별 요청과 사용자별 시계열을 만들지 않는다.
- 사용자·요청·카드 ID, 이름, 발화·문제 원문, 점수, 이미지 경로, IP, 토큰과 예외 원문을 저장하지 않는다. 지표용 DB 컬렉션도 만들지 않는다.
- 재시작·개발 리로드 시 초기화되며 여러 worker의 값을 합산하지 않는다. 개인정보 삭제 후에도 개인과 연결할 수 없는 짧은 기간의 합계만 만료 시까지 남는다.
- 지표 수집 오류는 성공한 저장 응답이나 원래의 오류 상태를 바꾸지 않는다.

## 필드 정의

`totals`와 `by_kind[]`는 같은 집계 필드를 가진다.

| 필드 | 의미 |
|---|---|
| `scope`, `source`, `retry_source` | `process`, `server_observed`, `client_marked` |
| `window_seconds`, `bucket_seconds`, `reset_on_restart` | 900초, 60초, true |
| `operations` | 검증·권한·동의 확인 후 서비스 처리에 진입한 요청 수 |
| `failed_operations` | 서비스 처리 중 예외로 종료한 요청 수 |
| `operation_failure_rate` | `failed_operations / operations`, 표본이 없으면 null |
| `received` | 서비스에 전달한 항목 수. 재전송된 항목도 매번 포함 |
| `retried` | 기기의 이전 전송 시도 표시가 있는 항목 수. 서버가 받은 헤더 기준 |
| `inserted` | 이번 처리에서 실제 신규 삽입한 항목 수 |
| `duplicates` | 같은 소유자의 같은 UUID가 이미 저장돼 재삽입하지 않은 항목 수 |
| `failed` | 처리 중 오류가 발생한 항목 수 |
| `unprocessed` | 앞선 항목의 오류로 처리를 시작하지 못한 나머지 항목 수 |
| `errors` | 고정 오류 분류별 실패 요청 수 |

각 요청에서 `received = inserted + duplicates + failed + unprocessed`다.
`retried`는 이 분할과 별개이며, 신규 저장인지 중복인지와 관계없이 포함될 수 있다.
3건 중 첫 항목 저장 후 둘째 항목이 충돌하면 신규 1·실패 1·미처리 1이다.
묶음 전체를 실패 3건으로 세거나 이미 저장한 첫 항목을 되돌리지 않는다.
충돌 건을 제외하고 처음·마지막 항목을 재전송하면 중복 1·신규 1이 된다.

## 재시도 표시와 호환

기기는 전송 직전에 기존 IndexedDB 대기 항목에 `sync_attempted: true`를 원자적으로
기록한다. 이전 값이 true였던 항목만 이번 `retried` 수에 포함한다. 스토어 버전 변경은
없으며 이전 데이터의 누락된 표시는 첫 시도로 해석한다. 표시 저장에 실패하면 해당
항목을 보내거나 지우지 않고 기존 재시도 안내를 유지한다.

- 발화 묶음의 선택 헤더: `X-Pesc-Sync-Retried: 0~100`, 해당 묶음의 건수 이하여야 한다.
- 학습 동기화: `X-Pesc-Offline-Sync: true`와 `X-Pesc-Sync-Retried: 0~1`을 보낸다.
- 헤더 생략 시 재시도 수는 0이며, 기존 클라이언트의 본문과 응답 형식은 그대로다.
- 잘못된 헤더나 전송 건수보다 큰 재시도 수는 422다. 일반 온라인 학습에 재시도 수를 보내도 422다.
- 로컬 표시와 `user_id`는 본문에 넣지 않으며 서버 기록·내보내기에 복제하지 않는다.
- 표시도 대기 항목의 일부이므로 로그아웃·개인정보 삭제 시 기존 대기열과 함께 제거한다.
- 새로고침 후에도 표시가 남는다. 서버 응답이 유실되거나 기기 대기열 삭제가 실패해도 같은 UUID로 재전송한다.
- 전송 준비 직후 취소되거나 기기에서 서버까지 도달하지 못한 첫 시도도 표시가 남을 수 있다. 따라서 `retried`는 이전 서버 수신을 증명하지 않는다.

실제 중복 수는 클라이언트 표시가 아니라 MongoDB 삽입 결과로 판정한다. 같은 UUID의
동시 upsert에서 다른 요청이 먼저 저장해도 같은 소유자면 중복으로 수락하고, 다른
소유자면 409다. 학습 결과도 기존 최초 기록을 유지하고 중복 수락 결과를 집계한다.

## 해석 한계와 장애 확인

서버에 도착하지 않은 통신 실패, 기기의 IndexedDB 읽기·쓰기·삭제 실패, 수신 응답
유실은 이 서버 지표의 실패 건수로 직접 집계할 수 없다. 예를 들어 DB에는 저장됐으나
기기가 응답을 못 받으면 첫 시도는 신규 저장, 다음 서버 수신은 중복으로 집계된다.
서버 실패가 0이어도 기기 동기화 성공률 100%라는 뜻이 아니다. 기기의 남은 건수·
실패 안내와 [오프라인 검수](../policies/OFFLINE_POLICY.md)를 함께 확인한다.

인증·동의 거절, Pydantic 본문·헤더 검증처럼 서비스 진입 전 종료한 요청은 이 합계에
포함하지 않는다. HTTP 단계의 4xx·5xx와 요청 추적은 [API 지표](API_METRICS.md)와
기존 요청 ID 로그에서 확인한다. 서비스 오류 분류는 409 충돌, 503 DB, 422 값 불일치,
그 외 예외는 내부 오류다. 자동 경보·장기 보관·기기별 분석은 이 구현에 포함하지 않는다.
