# A1-04 로컬 이미지 저장 안정화

2026-10-23 기준. 클라우드 저장소·파일 업로드 디렉터리·이미지 CDN 없이 현재 MongoDB 영구
볼륨을 사용한다. 이미지 바이트는 소유 카드 또는 현재 프로필 문서 안에 보관한다.
원본 보관과 정규화의 세부 검증은 [이미지 정규화](IMAGE_UPLOAD_NORMALIZATION.md)를 따른다.

## 규격과 원본

| 용도 | 최대 가로·세로 | 저장 위치 | 전달 |
|---|---|---|---|
| 원본 | 입력 128~4096px, 최대 16,000,000픽셀, 5MiB | `original_image` | API·외부 검사·JSON 내보내기 제외 |
| 카드 화면용 | 1280×1280px 이내 | `image.data` | 기본 이미지 API |
| 카드 썸네일 | 256×256px 이내 | `thumbnail.data` | `?variant=thumbnail` |
| 프로필 화면용 | 512×512px 이내 | `profile.image_data` | 기본 프로필 이미지 API |
| 프로필 썸네일 | 128×128px 이내 | `profile.thumbnail_data` | `?variant=thumbnail` |

비율·방향·투명도를 유지하며 작은 입력을 확대하거나 강제로 자르지 않는다.
화면용 WebP quality 88/method 4, 썸네일 WebP quality 82/method 4다.
EXIF·GPS·ICC·XMP·텍스트는 화면용과 썸네일에서 제거한다. 보관 원본은 입력 바이트와
MIME·크기·SHA-256을 그대로 유지하므로 촬영 위치·기기 정보가 남을 수 있다.
단일 프레임 화면용을 검사·제공하며 원본의 애니메이션 후속 프레임까지 승인했다는 뜻은 아니다.

원본+화면용은 15MiB 이하이고 작은 썸네일·문서 메타데이터를 위한 여유를 남긴다.
기존 정상 업로드를 읽을 때 필드를 강제로 추가하거나 원본을 추정 복구하지 않는다.
프로필은 현재 원본 하나만 보관한다. 사진 교체·기본 캐릭터 전환은 기존 세 변형을 함께 대체한다.
개인정보 전체 삭제는 소유 카드 문서와 프로필을 삭제하므로 원본·화면용·썸네일도 함께 제거된다.

## 생성·캐시·무효화와 권한

썸네일은 업로드 때 한 번 생성해 DB에 저장하는 파생 캐시다. 매 조회마다 변환하지 않고,
파일명이나 캐시 키별 별도 사본을 쌓지 않는다. 카드 목록과 Avatar는 `thumbnail_url`을 우선
사용하고, 이전 API/데이터에 이 필드가 없으면 기존 이미지 URL을 사용한다.
프로필 교체 URL은 새 버전, 카드 썸네일은 콘텐츠 해시 버전을 포함한다. 예전 버전 URL도
삭제한 원본이나 예전 사진을 제공하는 경로가 아니라 항상 현재 권한·현재 문서를 확인한다.

화면용/썸네일 GET은 `Cache-Control: private, no-cache`, 콘텐츠 SHA-256 ETag,
`Vary: Authorization`을 반환한다. 같은 ETag 요청은 **인증과 최신 접근 권한·존재 확인 후에만**
304다. 삭제·비활성·권한 해제 시 이전 ETag가 있어도 304로 우회하지 못한다.
원본 variant는 제공하지 않으며 지정할 수 없는 variant는 422다.

브라우저의 기존 AAC 오프라인 스냅샷에는 화면용/썸네일만 들어가고 원본은 전송하지 않는다.
연결 시 최신 목록·버전을 다시 읽고, 로그아웃·개인정보 삭제 시 기존 사용자 캐시 제거를 따른다.
오프라인의 이미 표시한 이미지나 다른 기기·이미 내려받은 파일까지 즉시 회수하는 기능은 아니다.
권한이 필요한 서버 캐시는 매 네트워크 요청마다 재검사하며 이 한계는 실제 기기 검수 대상이다.

## 저장 한도와 동시성

기본값은 사용자별 200MiB, 서비스 전체 2048MiB다. `IMAGE_USER_LIMIT_MIB`,
`IMAGE_TOTAL_LIMIT_MIB`로 로컬 Compose에서 조정한다. 사용자 한도 ≤ 전체 한도 ≤ 1TiB의
양수만 허용하며 잘못된 설정은 이미지 쓰기를 503으로 막는다. 단위는 MiB다.

한도는 활성 DB에 실제 들어 있는 원본·화면용·썸네일의 BSON 바이너리 바이트 합이다.
임시/비활성/공개 카드도 원래 소유자에게 합산하고 프로필도 포함한다. 정적 번들 PNG,
DB 메타데이터·할당 파일·저널·백업·클라이언트 캐시는 이 이미지 한도의 대상이 아니다.
백업은 아래 별도 수명 정책을 따른다. OS 전체 디스크 할당량을 설정했다는 뜻은 아니다.

업로드·프로필 교체·개인정보 이미지 삭제·정리/보강은 DB의 유일한 `image-writes` 잠금으로
직렬화한다. 두 집계에서 현재 실제 바이트를 측정해 기존 프로필 교체의 차액만 더한다.
한도 초과는 413이고 새 이미지를 쓰지 않는다. 이미 초과한 기존 데이터라도 용량 감소는 허용한다.
다른 쓰기 진행 시 409이며 카드 읽기·이미지 조회·기본 말하기는 이 잠금을 기다리지 않는다.
이미지 삭제가 업로드 처리 중 일어나면 삭제 시각과 동의를 다시 확인해 늦은 원본 재생성을 거절한다.

잠금에는 만료/TTL을 주지 않는다. 멈췄던 과거 작성자가 만료 후 다시 쓰면서 한도를 우회할 수
없도록 하기 위해서다. 프로세스가 죽으면 잠금이 남을 수 있으므로 모든 작성자를 중단하고
아래 명시적 복구를 한다. 일반 정상/예외 경로는 자신의 토큰으로 잠금을 해제한다.
이는 서비스 프로세스 간 보장이고 수동 DB 수정까지 방지하는 권한 장치는 아니다.

## 고아 탐지·정리와 기존 썸네일 보강

독립 이미지 파일이 없으므로 문서가 없는 파일이 따로 남을 수 없다. 파일시스템을 훑거나
사용자 PNG·정적 자산·임의 디렉터리를 삭제하지 않는다. 유지 도구는 소유 계정이 없는 카드
문서와 기본 프로필에 남은 불필요한 이미지 바이트를 탐지한다.

backend 디렉터리 또는 backend 컨테이너에서 실행한다. 기본은 읽기 전용이다.

```powershell
python -m app.image_maintenance audit --database pesc_mate
python -m app.image_maintenance backfill --database pesc_mate
python -m app.image_maintenance clear-lock --database pesc_mate
```

실행 중인 API/작성자를 실제로 중단한 뒤, 확인한 DB에만 적용한다. 운영 문서의 백업·복원
안전 절차도 따른다. `--writers-stopped`는 실행 중단을 대신하지 않는 운영자 확인이다.

```powershell
python -m app.image_maintenance audit --database pesc_mate --apply --confirm-database pesc_mate --writers-stopped
python -m app.image_maintenance backfill --database pesc_mate --apply --confirm-database pesc_mate --writers-stopped
python -m app.image_maintenance clear-lock --database pesc_mate --apply --confirm-database pesc_mate --writers-stopped --lock-token <조회한-정확한-토큰>
```

`audit --apply`는 고아 카드 문서와 기본 프로필의 이미지 필드만 제거한다. 일반 계정·살아 있는
카드·다른 파일은 삭제하지 않는다. 소유자를 다시 확인하고 삭제 이전 백업을 무효화한다.
`backfill --apply`는 기존 검증 가능 이미지에서 썸네일만 만든다. 원본/기존 화면용은 덮어쓰지 않는다.
썸네일이 없는 문서는 읽기 API에서 기존 화면용으로 대체하므로 보강 전에 앱이 중단되지 않는다.
보강은 원본을 새로 만들어 내지 않고 손상·한도 초과 항목은 skipped로 집계한다.

계획 조회와 `audit`는 이미지 바이트를 읽지 않고 ID만 조회한다. 실제 보강 때도 원본이나
계정 전체를 가져오지 않고 필요한 화면용 이미지·형식·URL·소유 정보만 한 문서씩 읽는다.
업로드의 최소 변 길이 128px 검사는 유지한다. 다만 이미 저장된 화면용 이미지는 비율 유지
축소로 짧은 변이 128px 미만일 수 있으므로 보강에 한해 최소 변 길이 1px를 허용한다.
예를 들어 4096×128px 업로드는 프로필 화면용 512×16px, 썸네일 128×4px가 된다.
시그니처·MIME·디코딩·바이트·최대 변·픽셀 수 검사와 메타데이터 제거는 그대로 적용한다.

종류별 기본 100개, `--batch-size` 1~500개로 제한한다. 제한에 도달한 종류가 있으면 계획을
다시 조회하고 필요한 만큼 반복한다. 여러 종류의 합계는 이 종류별 상한보다 많을 수 있다.
출력은 건수·기술 잠금 상태만 담으며 사진·이름·파일 경로·개인 원문을 출력하지 않는다.

## 이미지 삭제와 로컬 백업 수명

관리 대상은 `.local-backups/backup_<UUID>/`의 체크섬·manifest가 검증되는 전체 DB 백업이다.
원본도 포함하므로 로컬 관리자만 접근하도록 보관한다. 백업 최대 보존 기간은 생성 후 30일이다.
개인정보 전체 삭제·파괴적 이미지 정리는 DB에 단조 증가 삭제 시각을 먼저 기록한다.
재동의하더라도 이 기술 시각은 지우지 않는다.

복원 도구는 소스 DB의 최신 삭제 시각을 확인하여 삭제 이전에 만든 백업이나 30일 만료 백업의
복원을 차단한다. 한 사람 삭제에도 해당 시점 이전의 전체 DB 백업을 보수적으로 무효화한다.
새 백업을 만들고 검증해야 한다. 소스 DB 상태를 확인할 수 없거나 시각이 잘못되면 우회 복원하지 않는다.
복원 대상은 기존과 같이 새로운 격리 DB만 허용하며 개발/운영 DB에 덮어쓰지 않는다.

백업 파일의 실제 파기는 호스트에서 계획 확인 후 명시적으로 실행한다. 앱 컨테이너가 호스트
백업 디렉터리를 자동 삭제하거나 내려받은 사본·외부 복제본을 원격 삭제하는 기능은 아니다.

```powershell
python backend/app/mongo_backup.py purge --database pesc_mate
python backend/app/mongo_backup.py purge --database pesc_mate --apply --confirm-backup-root <.local-backups의-정확한-절대경로> --writers-stopped
```

두 번째 명령 전에는 백업 생성/복원 작성자도 중단한다. 기본 조회는 삭제하지 않는다.
적용은 유효한 UUID 관리 디렉터리, 체크섬 확인된 archive·manifest·정규식에 맞는 검증 영수증만
지우며 임의 파일·링크·junction·알 수 없는 항목이 있으면 거절한다. 휴지통 복원이 아니므로
삭제된 관리 백업은 도구로 되돌릴 수 없다. 후보를 검토하고 다른 필요한 검증 백업을 확보한다.
프로필의 통상 교체는 이전 DB 이미지를 제거하며 예전 백업 사본은 최대 30일 정책을 따른다.

## 검증·범위

단위 검사는 규격·투명도·실제 바이트 합·한도·차액·잠금/해제·삭제 경쟁·안전한 계획·백업 파기를
검증한다. 실제 MongoDB HTTP 검사는 원본 보존, 썸네일 규격, ETag/권한, 한도 초과 무변경,
중복 작성 차단, 삭제 중인 업로드 거절, 고아 정리·보강과 멱등성을 확인한다.
브라우저는 버전별 썸네일 교체와 늦은 응답 무시, 기존 PNG 등록·카드판·오프라인 흐름을 확인한다.

현재 개발 DB·사용자 사진·기존 백업에는 정리/보강/파기를 실행하지 않았다. 자동 검증은 UUID
임시 DB와 임시 백업 파일만 사용한다. 실제 사용자·태블릿·백업 운영 훈련은 A0 현장 게이트와 별도다.

2026-10-23 제한 검증: 로컬 백엔드 단위 검사 369개 중 367개 통과, Windows 심볼릭 링크
권한에 의존하는 2개 제외. 별도 임시 MongoDB의 이미지 HTTP 통합 검사 14개는 모두 통과했다.
새 회귀 검사는 가로/세로로 긴 이미지 보강, 원본·화면용 무변경, 투명도·비율 유지,
조회 전용 모드의 ID 전용 projection, 보강 모드의 원본 제외와 한 문서 단위 읽기를 확인한다.
임시 MongoDB는 검사 후 정리했다. 중단했던 `verify:full`과 브라우저 재검증은 실행하지
않았으므로 A1-04 전체 완료로 처리하지 않는다.

같은 날 사용자 실행 전체 검증 결과를 확인했다. 위 제한 검증 이후 실행한
`.local-validation/2026-10-22T15-07-43.390Z-985a93130f254fa08de37278be8a9756/summary.json`은
`mode: full`, `status: passed`, 309초다. 정책 28·백엔드 369·Node 96·React 116·MongoDB 73·
Chromium 39개로 총 721개가 제외 없이 통과했고 빌드·임시 환경 정리도 성공했다.
긴 이미지 보강 회귀와 이전 프로필 응답 기대값 실패 2건의 해결도 포함한다.
이 결과로 위 전체 검증 보류를 해소하고 A1-04 로컬 구현 범위를 완료 처리한다.
실제 사용자·기기·운영 승인이나 기존 DB·백업 유지보수를 실행한 결과는 아니다.
