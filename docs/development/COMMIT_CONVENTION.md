# 커밋 메시지 규칙

커밋 메시지는 제목, 본문(선택), 꼬리말(선택)의 세 부분으로 작성합니다.

```text
Type : Subject

Body

Footer
```

## 개발 종료 시 커밋

- 사용자 요청에 따라 개발 작업을 마칠 때는 별도 요청을 기다리지 않고 커밋합니다.
- 한 기능의 코드·관련 수정·검증·문서를 함께 묶어 기능 완성 시 한 번 커밋합니다.
  중간 수정이나 파일·문서 단위의 커밋으로 쪼개지 않습니다. 문서만 요청한 경우에는
  완결된 문서 작업을 한 단위로 묶습니다. 작업과 무관한 기존 변경사항은 포함하지 않습니다.
- 검증 실패·중단·미실행 사항은 본문과 작업 문서에 남깁니다. 기능 구현이 끝났으나
  검증이 남은 경우 상태를 명시해 커밋할 수 있지만 중간 체크포인트를 기본으로 만들지
  않으며 TODO 완료나 검증 통과·배포 승인으로 표시하지 않습니다.
- 커밋 후 작업 트리와 커밋 결과를 확인하고, 커밋이 불가능하면 사유를 알립니다.
- 원격 푸시나 기존 커밋 이력 변경은 별도 요청이 있을 때만 진행합니다.

## Type 규칙

| Type | 설명 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `style` | 코드 포맷 변경, 세미콜론 누락 등 코드 동작의 변경이 없는 경우 |
| `refactor` | 프로덕션 코드 리팩터링 |
| `test` | 테스트 코드 추가 또는 리팩터링처럼 프로덕션 코드의 변경이 없는 경우 |
| `design` | CSS 등 사용자 UI 디자인 변경 |
| `init` | 프로젝트 초기 생성 |
| `rename` | 파일 또는 폴더 이름을 수정하거나 옮기는 작업만 수행한 경우 |
| `remove` | 코드 또는 파일을 삭제하는 작업만 수행한 경우 |
| `comment` | 필요한 주석을 추가하거나 변경한 경우 |
| `chore` | 빌드 스크립트, 이미지, 패키지 매니저 등 기타 관리 작업 |

## Subject 규칙

- 50자 이내로 작성합니다.
- Type은 영어로, 제목은 한글로 작성합니다.
- 유형과 설명 사이는 공백을 포함한 ` : `로 구분합니다.
- 명령문을 사용합니다.
- 마침표와 특수 문자를 사용하지 않습니다.
- 간결하고 요점이 드러나는 개조식 구문으로 작성합니다.

## Body 규칙

- 한 줄을 72자 이내로 작성합니다.
- 변경 사항과 변경 이유를 최대한 상세히 작성합니다.
- 어떻게 변경했는지보다 무엇을, 왜 변경했는지 설명합니다.

## Footer 규칙

- 이슈 번호는 `#이슈번호` 형식으로 작성합니다.
- 이슈가 여러 개라면 쉼표(`,`)로 구분합니다.
- 다음 이슈 트래커 유형 중 하나를 사용합니다.

| 유형 | 설명 |
| --- | --- |
| `Related to` | 해당 커밋과 관련되었지만 아직 해결되지 않은 이슈. PR 병합 시 자동으로 닫히지 않음 |
| `Resolves` | 해당 커밋으로 해결한 이슈. PR 병합 시 자동으로 닫힘 |
| `Ref` | 참고할 이슈. PR 병합 시 자동으로 닫히지 않음 |

## 작성 예시

```text
feat : 개인 맞춤 카드 추천 API 추가

사용자의 카드 사용 이력을 기반으로 다음 카드를 추천하도록
추천 결과 조회 API를 추가한다

Resolves: #12
Related to: #15, #18
```
