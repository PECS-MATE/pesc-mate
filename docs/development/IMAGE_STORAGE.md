사용자가 업로드한 원본과 화면용 WebP·썸네일을 구분해 로컬 MongoDB에 저장합니다. 화면용 이미지는 형식·크기·해상도·디코딩 검사를 거쳐 메타데이터를 제거합니다. 용량 한도·동시 쓰기 잠금·ETag·사진 버전 충돌·삭제 연계를 유지합니다. 촬영 변환본과 다중 카드 분리본을 등록하면 그 결과 파일이 등록 원본이며, 전체 촬영 사진을 서버에 따로 보관하는 것은 아닙니다.

### 업로드 이미지 형식 검증과 메타데이터 제거

현재 A1-04의 화면/썸네일 규격·캐시·용량 한도·고아 정리·백업 수명은
[로컬 이미지 저장 안정화](IMAGE_STORAGE.md#local-image-storage)를 함께 따른다. 아래 날짜별 검증 기록은
각 개발 단위의 당시 범위이며, 현재 정책이 후속 규격/캐시 규칙을 대체한다.

<a id="image-upload-normalization--적용-범위"></a>
#### 적용 범위

카드 `POST /api/cards/submissions`와 프로필 `POST /api/profile/image`는 공통
`backend/app/services/card_submissions.py::_normalize_image`를 사용한다.
기존 5MiB 이하·가로/세로 128~4096px·전체 16,000,000픽셀 이하 제한을 유지한다.
Pillow·WebP 지원은 현재 로컬 컨테이너의 Pillow 12.3.0에서 검증했다.

정규화와 원본 보관은 **신규 업로드 처리**에만 적용한다. 기존 DB 이미지·원본 파일명·백업·
정적 카드/프로필 자산은 일괄 재인코딩하거나 삭제하지 않는다. schema_version·
이미지 API URL·접근 권한·공개 카드 검수 상태도 변경하지 않는다.

<a id="image-upload-normalization--입력-검증"></a>
#### 입력 검증

| 실제 파일 계열 | 확인하는 시그니처 | 허용 선언 MIME |
|---|---|---|
| JPEG | `FF D8 FF` | `image/jpeg` |
| PNG | `89 50 4E 47 0D 0A 1A 0A` | `image/png` |
| WebP | 선두 `RIFF`, 8~11바이트 `WEBP` | `image/webp` |

확장자나 짧은 헤더만으로 파일을 승인하지 않는다. 다음 단계를 모두 거친다.

1. 선언 MIME·입력 크기·파일 시그니처를 확인한다. JPEG/PNG/WebP 외 형식, 빈 입력, 5MiB 초과를 거절한다.
2. Pillow가 읽은 실제 포맷도 시그니처/MIME과 같아야 한다. `verify()`로 파일 구조를 검사하고 크기·전체 픽셀 수를 확인한다.
3. 다시 열어 첫 프레임을 실제 디코딩한다. 헤더만 붙인 가짜 파일·중간이 잘린 파일·JPEG 끝이 손상되어 실제 디코딩이 실패하는 입력을 거절한다.
4. Pillow의 압축 해제 폭탄 경고/오류도 거절한다. 이 경고 처리는 헤더 검사뿐 아니라 재열기·디코딩 과정에도 적용한다.

불일치/손상/범위 초과는 422다. 안전성 검사 공급자에 보내거나 카드·감사 문서를
만들지 않으며 프로필도 교체하지 않는다. 기존 프로필이 있으면 그대로 유지한다.
카드 카테고리·동의/권한 등의 기존 검사는 이미지 처리보다 먼저 실행될 수 있다.

MIME은 현재 정해진 세 문자열을 받으며 임의 MIME 파라미터·HEIC·GIF·SVG 등을
자동 추정해 허용하지 않는다. 올바른 PNG 내용/MIME이면 파일명이 `.jpg`여도 처리하며,
반대로 파일명이 `.png`여도 JPEG 내용에 PNG MIME을 선언하면 거절한다.

<a id="image-upload-normalization--픽셀-보존과-메타데이터-제거"></a>
#### 픽셀 보존과 메타데이터 제거

2026-10-23 신규 카드의 선택형 `image_edits`를 추가했다. 기본 정규화는 기존과 같고,
사용자가 선택한 경우에만 EXIF 방향 적용 뒤 중앙 정사각형 자르기·90도 단위 회전·
밝기 보정을 적용한다. 원본 바이트는 그대로 보관한다. 순서·범위·검증 상태는
[사진 일괄 등록과 보정](CARD_MANAGEMENT.md#bulk-card-import-history)을 따른다. 프로필에는 보정을 적용하지 않는다.

- EXIF 방향을 먼저 픽셀에 적용한 뒤 방향 태그를 제거한다. 사진 방향까지 버리는 것이 아니다.
- 팔레트 PNG와 RGB 색상 키의 `tRNS` 투명도도 RGBA로 변환한다. 기존 A 채널·부분 투명도도 유지한다.
- 변환 이미지의 EXIF와 `info`를 비우고, WebP 저장 옵션 `exif=b''`, `icc_profile=b''`, `xmp=b''`를 명시한다. 인코더 기본값에 메타데이터 제거를 맡기지 않는다.
- EXIF GPS·촬영 기기·촬영 시각, XMP, ICC, PNG 텍스트/작성자와 JPEG 주석을 출력 이미지에 복제하지 않는다. 원본 뒤의 부가 바이트도 새 WebP에 이어 붙이지 않는다.
- 출력은 기존과 같은 quality 88·method 4의 단일 프레임 WebP다. APNG/애니메이션 WebP도 기존 동작대로 첫 프레임만 사용한다. 나머지 프레임 전체의 콘텐츠 검수를 했다는 뜻은 아니다.
- 신규 카드에는 사용하지 않던 `original_filename`을 저장하지 않는다. 반환/저장 표시 파일명은 기존 `card-image.webp`를 유지한다. 내부 함수 인자는 호환성을 위해 유지한다.

방향 적용은 [Pillow ImageOps](https://pillow.readthedocs.io/en/stable/reference/ImageOps.html#PIL.ImageOps.exif_transpose),
WebP의 EXIF/ICC/XMP 저장 옵션은 [Pillow 파일 형식 문서](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html#webp)를 참고한다.
명시 옵션과 출력 바이트 검사를 함께 사용하며 의존성 전체 버전을 고정/갱신한 작업은 아니다.

안전성 검사는 **정규화된 WebP**와 `image/webp`만 받는다. 선택 보정 시에는 잘라내지 않은
전체 프레임을 먼저 검사하고 보정 프레임도 검사한다. 어느 쪽이든 차단이면 저장하지 않고
전체 프레임의 수동 검토 결과를 보정 프레임 통과로 상향하지 않는다. 이미지가 통과하면 같은
바이트를 DB의 화면용 이미지에 저장하고 이미지 조회 API가 반환한다. 공급자 미설정/차단 시 카드의
수동 검토 정책과 프로필의 fail-closed 정책은 기존대로 유지한다.

이 작업은 보이는 픽셀 속 얼굴·이름·주소를 익명화하거나 악성 파일 전반을 검사하는
기능이 아니다. 화면용 WebP의 ICC 제거 시 색상 관리 정확도나 무손실 픽셀 보존을 보증하지 않는다.
외부 이미지 안전성 검사에 대한 실제 공급자/전송 동의·운영 정책은 별도 검토 사항이다.

<a id="image-upload-normalization--자동-검증"></a>
#### 자동 검증

`backend/tests/image_fixtures.py`가 실제 EXIF GPS/기기/방향·ICC·XMP·텍스트를 가진
합성 JPEG/PNG/WebP를 생성한다. 개인 사진이나 바이너리 fixture를 저장소에 추가하지 않는다.

`backend/tests/test_image_normalization.py`의 기존 14개 정규화 시험은 입력에 메타데이터가 실제
들어 있음을 먼저 확인한 뒤 출력에서 사라지는지 검사한다. Pillow로 재열어 검사할
뿐 아니라 별도 RIFF 파서로 `EXIF`·`XMP `·`ICCP`·애니메이션 청크가 없는지도 확인한다.
EXIF 6번 방향의 크기/색상 위치, 팔레트/색상 키/부분 투명도, MIME 교차 조합,
시그니처와 디코더 포맷 불일치, 헤더 가짜·손상·크기·픽셀·압축 해제 제한을 포함한다.
인코더에 전달되는 `info`/EXIF와 세 메타데이터 옵션도 직접 확인한다.

`backend/integration_tests/test_image_uploads.py`는 실제 multipart·Bearer
인증·FastAPI 검증·MongoDB 저장·이미지 응답을 사용한다. 외부 안전성 HTTP 전송만
대체하고 그 요청에도 정규화된 바이트만 전달되는지 확인한다. 다른 아동 접근 차단,
손상/위장/과대 입력의 공급자 미호출·감사 기록 미생성·기존 프로필 보존도 검증한다.

각 통합 시험은 `pesc_mate_image_test_<UUID>` DB만 생성한다. 정리 전 UUID 전체와
원래 설정 DB와의 불일치를 확인한 뒤 자신의 합성 DB만 삭제한다. 실제 외부 공급자에
사진을 보내지 않으며 기존 사용자 이미지에 대한 일괄 마이그레이션을 실행하지 않는다.
현재 `npm run verify:full`의 MongoDB 통합 단계에 자동 포함된다.

backend 의존성과 테스트 MongoDB 연결을 준비한 뒤 backend 디렉터리에서 실행한다.

```powershell
python -m unittest discover -s tests -t . -p "test_*.py"
python -m unittest discover -s integration_tests -p "test_*.py" -v
```

원본 보관 단위 당시에는 백업 보존·파기, 화면용·썸네일 규격, 캐시·한도·고아 정리를
별도 TODO로 남겼다. 후속 A1-04 구현은 위 로컬 이미지 저장 문서에 기록하며 실제 기기 검수는 별도다.

2026-10-18 로컬 컨테이너의 전체 단위 테스트 **288개**, 실제 임시 MongoDB 통합
테스트 **32개**, Windows Chrome 브라우저 전체 **25개**(단일 worker)를 통과했다.
신규 이미지 시험은 단위 14개·DB/API 통합 6개이며, 브라우저에서는 기존 개인 PNG
등록과 아동 고정 카드판 반영도 다시 확인했다. 테스트용 합성 DB만 정리했고 기존
사용자 이미지는 일괄 변경하지 않았다. 프런트엔드 소스·단위 테스트·빌드와 원격 CI,
실제 외부 이미지 안전성 공급자·태블릿·실제 사진 검수는 이번 결과에 포함하지 않는다.

<a id="image-upload-normalization--원본-보관--2026-10-22-사용자-결정"></a>
#### 원본 보관 — 2026-10-22 사용자 결정

로컬 구동을 기준으로 현재 MongoDB 영구 볼륨을 그대로 사용한다. S3·오브젝트 스토리지,
외부 업로드 서비스나 별도 파일 디렉터리를 추가하지 않는다.

- 카드의 `card_submissions.original_image`, 프로필의 `users.profile.original_image`에
  입력 원본 바이트, 검증된 `content_type`, `size_bytes`, `sha256`을 저장한다. 파일명은 보관하지 않는다.
- 원본은 EXIF GPS·기기·촬영 시각, 부가 데이터와 애니메이션의 후속 프레임까지 포함할 수 있다.
  공개·표시·검사용 이미지가 아니며 후속 프레임 전체를 안전성 검수했다는 뜻도 아니다.
- 이미지 API·목록·인증·프로필 응답과 개인정보 JSON 내보내기에는 원본을 반환하지 않는다.
  안전성 공급자에는 정규화 WebP만 전송한다. 별도 원본 다운로드 API는 제공하지 않는다.
- 기존 본문 문서와 같은 쓰기로 원본을 저장한다. 신규 컬렉션·독립 원본 파일·다중 쓰기 보상
  절차가 필요 없고, 카드 문서 삭제 또는 프로필 전체 교체/삭제에 원본도 함께 제거된다.
- 프로필은 현재 사진의 원본 하나만 유지한다. 새 사진·기본 캐릭터 전환 시 이전 원본은 남기지 않는다.
  거절·DB 저장 실패 때는 기존 문서를 유지한다. 카드 비활성화는 삭제가 아니므로 원본을 유지한다.
- 원본+정규화 이미지가 15MiB를 넘으면 422로 거절해 MongoDB 16MiB 문서 제한 아래에
  메타데이터 여유를 둔다. 기존 입력 5MiB 제한은 유지한다. 사용자·전체 용량 할당량은 별도 TODO다.
- 로그인·현재 인증 사용자 조회에서는 두 이미지 바이너리를 DB projection으로 제외한다.
  원본 보관 때문에 인증 요청마다 원본을 추가 전송하지 않는다.
- 개인정보 전체 삭제는 카드 문서와 프로필을 제거하므로 원본도 삭제된다. 전체 DB 백업에는
  원본도 포함되므로 백업 파일 접근을 제한해야 한다. 내려받은 백업은 개인정보 삭제로 자동
  수정·파기하지 않으며 백업 수명 정책 완료로 간주하지 않는다.
- 기존 업로드의 버린 원본은 복구·추정 생성하지 않는다. 스키마 기준 버전 1에 선택 필드를
  추가하며 기존 사용자 데이터의 일괄 변환·삭제는 하지 않는다.

원본 동일성·해시·크기와 합계 크기 거절 단위 검사 2개를 추가했다. 실제 MongoDB 시험에는
원본 바이트 보존, 정규화 WebP만 제공/전송, 인증·목록·JSON 내보내기 비노출, 공개 카드의
원본 비노출, 다른 아동 접근 차단, 프로필 대체·기본 전환·개인정보 삭제를 포함한다.

## A1-04 로컬 이미지 저장 안정화

<details>

<a id="local-image-storage--a1-04-로컬-이미지-저장-안정화"></a>
### A1-04 로컬 이미지 저장 안정화

2026-10-23 기준. 클라우드 저장소·파일 업로드 디렉터리·이미지 CDN 없이 현재 MongoDB 영구
볼륨을 사용한다. 이미지 바이트는 소유 카드 또는 현재 프로필 문서 안에 보관한다.
원본 보관과 정규화의 세부 검증은 [이미지 정규화](IMAGE_STORAGE.md#image-upload-normalization)를 따른다.

<a id="local-image-storage--규격과-원본"></a>
#### 규격과 원본

| 용도 | 최대 가로·세로 | 저장 위치 | 전달 |
|---|---|---|---|
| 원본 | 입력 128~4096px, 최대 16,000,000픽셀, 5MiB | `original_image` | API·외부 검사·JSON 내보내기 제외 |
| 카드 화면용 | 1280×1280px 이내 | `image.data` | 기본 이미지 API |
| 카드 썸네일 | 256×256px 이내 | `thumbnail.data` | `?variant=thumbnail` |
| 프로필 화면용 | 512×512px 이내 | `profile.image_data` | 기본 프로필 이미지 API |
| 프로필 썸네일 | 128×128px 이내 | `profile.thumbnail_data` | `?variant=thumbnail` |

기본은 비율·방향·투명도를 유지하며 작은 입력을 확대하거나 강제로 자르지 않는다.
신규 카드에 사용자가 명시한 선택 보정은 화면용과 썸네일에만 적용한다.
[일괄 등록 사진 보정](CARD_MANAGEMENT.md#bulk-card-import-history)의 중앙 자르기·회전·밝기는 원본을 변경하지 않으며
기존 카드·프로필·정적 자산·과거 백업을 일괄 보정하지 않는다.
화면용 WebP quality 88/method 4, 썸네일 WebP quality 82/method 4다.
EXIF·GPS·ICC·XMP·텍스트는 화면용과 썸네일에서 제거한다. 보관 원본은 입력 바이트와
MIME·크기·SHA-256을 그대로 유지하므로 촬영 위치·기기 정보가 남을 수 있다.
단일 프레임 화면용을 검사·제공하며 원본의 애니메이션 후속 프레임까지 승인했다는 뜻은 아니다.

원본+화면용은 15MiB 이하이고 작은 썸네일·문서 메타데이터를 위한 여유를 남긴다.
기존 정상 업로드를 읽을 때 필드를 강제로 추가하거나 원본을 추정 복구하지 않는다.
프로필은 현재 원본 하나만 보관한다. 사진 교체·기본 캐릭터 전환은 기존 세 변형을 함께 대체한다.
개인정보 전체 삭제는 소유 카드 문서와 프로필을 삭제하므로 원본·화면용·썸네일도 함께 제거된다.

<a id="local-image-storage--생성캐시무효화와-권한"></a>
#### 생성·캐시·무효화와 권한

썸네일은 업로드 때 한 번 생성해 DB에 저장하는 파생 캐시다. 매 조회마다 변환하지 않고,
파일명이나 캐시 키별 별도 사본을 쌓지 않는다. 카드 목록과 Avatar는 `thumbnail_url`을 우선
사용하고, 이전 API/데이터에 이 필드가 없으면 기존 이미지 URL을 사용한다.
프로필 교체 URL은 새 버전, 카드 썸네일은 콘텐츠 해시 버전을 포함한다. 예전 버전 URL도
삭제한 원본이나 예전 사진을 제공하는 경로가 아니라 항상 현재 권한·현재 문서를 확인한다.

화면용/썸네일 GET은 `Cache-Control: private, no-cache`, 콘텐츠 SHA-256 ETag,
`Vary: Authorization`을 반환한다. 같은 ETag 요청은 **인증과 최신 접근 권한·존재 확인 후에만**
304다. 삭제·비활성·권한 해제 시 이전 ETag가 있어도 304로 우회하지 못한다.
원본 variant는 제공하지 않으며 지정할 수 없는 variant는 422다.

브라우저의 기존 AAC 오프라인 스냅샷에는 화면용/썸네일만 들어가고 원본은 전송하지 않는다.
연결 시 최신 목록·버전을 다시 읽고, 로그아웃·개인정보 삭제 시 기존 사용자 캐시 제거를 따른다.
오프라인의 이미 표시한 이미지나 다른 기기·이미 내려받은 파일까지 즉시 회수하는 기능은 아니다.
권한이 필요한 서버 캐시는 매 네트워크 요청마다 재검사하며 이 한계는 실제 기기 검수 대상이다.

<a id="local-image-storage--저장-한도와-동시성"></a>
#### 저장 한도와 동시성

기본값은 사용자별 200MiB, 서비스 전체 2048MiB다. `IMAGE_USER_LIMIT_MIB`,
`IMAGE_TOTAL_LIMIT_MIB`로 로컬 Compose에서 조정한다. 사용자 한도 ≤ 전체 한도 ≤ 1TiB의
양수만 허용하며 잘못된 설정은 이미지 쓰기를 503으로 막는다. 단위는 MiB다.

한도는 활성 DB에 실제 들어 있는 원본·화면용·썸네일의 BSON 바이너리 바이트 합이다.
임시/비활성/공개 카드도 원래 소유자에게 합산하고 프로필도 포함한다. 정적 번들 PNG,
DB 메타데이터·할당 파일·저널·백업·클라이언트 캐시는 이 이미지 한도의 대상이 아니다.
백업은 아래 별도 수명 정책을 따른다. OS 전체 디스크 할당량을 설정했다는 뜻은 아니다.

업로드·프로필 교체·개인정보 이미지 삭제·정리/보강은 DB의 유일한 `image-writes` 잠금으로
직렬화한다. 두 집계에서 현재 실제 바이트를 측정해 기존 프로필 교체의 차액만 더한다.
한도 초과는 413이고 새 이미지를 쓰지 않는다. 이미 초과한 기존 데이터라도 용량 감소는 허용한다.
다른 쓰기 진행 시 409이며 카드 읽기·이미지 조회·기본 말하기는 이 잠금을 기다리지 않는다.
이미지 삭제가 업로드 처리 중 일어나면 삭제 시각과 동의를 다시 확인해 늦은 원본 재생성을 거절한다.

잠금에는 만료/TTL을 주지 않는다. 멈췄던 과거 작성자가 만료 후 다시 쓰면서 한도를 우회할 수
없도록 하기 위해서다. 프로세스가 죽으면 잠금이 남을 수 있으므로 모든 작성자를 중단하고
아래 명시적 복구를 한다. 일반 정상/예외 경로는 자신의 토큰으로 잠금을 해제한다.
이는 서비스 프로세스 간 보장이고 수동 DB 수정까지 방지하는 권한 장치는 아니다.

<a id="local-image-storage--고아-탐지정리와-기존-썸네일-보강"></a>
#### 고아 탐지·정리와 기존 썸네일 보강

독립 이미지 파일이 없으므로 문서가 없는 파일이 따로 남을 수 없다. 파일시스템을 훑거나
사용자 PNG·정적 자산·임의 디렉터리를 삭제하지 않는다. 유지 도구는 소유 계정이 없는 카드
문서와 기본 프로필에 남은 불필요한 이미지 바이트를 탐지한다.

backend 디렉터리 또는 backend 컨테이너에서 실행한다. 기본은 읽기 전용이다.

```powershell
python -m app.image_maintenance audit --database pesc_mate
python -m app.image_maintenance backfill --database pesc_mate
python -m app.image_maintenance clear-lock --database pesc_mate
```

실행 중인 API/작성자를 실제로 중단한 뒤, 확인한 DB에만 적용한다. 운영 문서의 백업·복원
안전 절차도 따른다. `--writers-stopped`는 실행 중단을 대신하지 않는 운영자 확인이다.

```powershell
python -m app.image_maintenance audit --database pesc_mate --apply --confirm-database pesc_mate --writers-stopped
python -m app.image_maintenance backfill --database pesc_mate --apply --confirm-database pesc_mate --writers-stopped
python -m app.image_maintenance clear-lock --database pesc_mate --apply --confirm-database pesc_mate --writers-stopped --lock-token <조회한-정확한-토큰>
```

`audit --apply`는 고아 카드 문서와 기본 프로필의 이미지 필드만 제거한다. 일반 계정·살아 있는
카드·다른 파일은 삭제하지 않는다. 소유자를 다시 확인하고 삭제 이전 백업을 무효화한다.
`backfill --apply`는 기존 검증 가능 이미지에서 썸네일만 만든다. 원본/기존 화면용은 덮어쓰지 않는다.
썸네일이 없는 문서는 읽기 API에서 기존 화면용으로 대체하므로 보강 전에 앱이 중단되지 않는다.
보강은 원본을 새로 만들어 내지 않고 손상·한도 초과 항목은 skipped로 집계한다.

계획 조회와 `audit`는 이미지 바이트를 읽지 않고 ID만 조회한다. 실제 보강 때도 원본이나
계정 전체를 가져오지 않고 필요한 화면용 이미지·형식·URL·소유 정보만 한 문서씩 읽는다.
업로드의 최소 변 길이 128px 검사는 유지한다. 다만 이미 저장된 화면용 이미지는 비율 유지
축소로 짧은 변이 128px 미만일 수 있으므로 보강에 한해 최소 변 길이 1px를 허용한다.
예를 들어 4096×128px 업로드는 프로필 화면용 512×16px, 썸네일 128×4px가 된다.
시그니처·MIME·디코딩·바이트·최대 변·픽셀 수 검사와 메타데이터 제거는 그대로 적용한다.

종류별 기본 100개, `--batch-size` 1~500개로 제한한다. 제한에 도달한 종류가 있으면 계획을
다시 조회하고 필요한 만큼 반복한다. 여러 종류의 합계는 이 종류별 상한보다 많을 수 있다.
출력은 건수·기술 잠금 상태만 담으며 사진·이름·파일 경로·개인 원문을 출력하지 않는다.

<a id="local-image-storage--이미지-삭제와-로컬-백업-수명"></a>
#### 이미지 삭제와 로컬 백업 수명

관리 대상은 `.local-backups/backup_<UUID>/`의 체크섬·manifest가 검증되는 전체 DB 백업이다.
원본도 포함하므로 로컬 관리자만 접근하도록 보관한다. 백업 최대 보존 기간은 생성 후 30일이다.
개인정보 전체 삭제·파괴적 이미지 정리는 DB에 단조 증가 삭제 시각을 먼저 기록한다.
재동의하더라도 이 기술 시각은 지우지 않는다.

복원 도구는 소스 DB의 최신 삭제 시각을 확인하여 삭제 이전에 만든 백업이나 30일 만료 백업의
복원을 차단한다. 한 사람 삭제에도 해당 시점 이전의 전체 DB 백업을 보수적으로 무효화한다.
새 백업을 만들고 검증해야 한다. 소스 DB 상태를 확인할 수 없거나 시각이 잘못되면 우회 복원하지 않는다.
복원 대상은 기존과 같이 새로운 격리 DB만 허용하며 개발/운영 DB에 덮어쓰지 않는다.

백업 파일의 실제 파기는 호스트에서 계획 확인 후 명시적으로 실행한다. 앱 컨테이너가 호스트
백업 디렉터리를 자동 삭제하거나 내려받은 사본·외부 복제본을 원격 삭제하는 기능은 아니다.

```powershell
python backend/app/mongo_backup.py purge --database pesc_mate
python backend/app/mongo_backup.py purge --database pesc_mate --apply --confirm-backup-root <.local-backups의-정확한-절대경로> --writers-stopped
```

두 번째 명령 전에는 백업 생성/복원 작성자도 중단한다. 기본 조회는 삭제하지 않는다.
적용은 유효한 UUID 관리 디렉터리, 체크섬 확인된 archive·manifest·정규식에 맞는 검증 영수증만
지우며 임의 파일·링크·junction·알 수 없는 항목이 있으면 거절한다. 휴지통 복원이 아니므로
삭제된 관리 백업은 도구로 되돌릴 수 없다. 후보를 검토하고 다른 필요한 검증 백업을 확보한다.
프로필의 통상 교체는 이전 DB 이미지를 제거하며 예전 백업 사본은 최대 30일 정책을 따른다.

<a id="local-image-storage--검증범위"></a>
#### 검증·범위

단위 검사는 규격·투명도·실제 바이트 합·한도·차액·잠금/해제·삭제 경쟁·안전한 계획·백업 파기를
검증한다. 실제 MongoDB HTTP 검사는 원본 보존, 썸네일 규격, ETag/권한, 한도 초과 무변경,
중복 작성 차단, 삭제 중인 업로드 거절, 고아 정리·보강과 멱등성을 확인한다.
브라우저는 버전별 썸네일 교체와 늦은 응답 무시, 기존 PNG 등록·카드판·오프라인 흐름을 확인한다.

현재 개발 DB·사용자 사진·기존 백업에는 정리/보강/파기를 실행하지 않았다. 자동 검증은 UUID
임시 DB와 임시 백업 파일만 사용한다. 실제 사용자·태블릿·백업 운영 훈련은 A0 현장 게이트와 별도다.

2026-10-23 제한 검증: 로컬 백엔드 단위 검사 369개 중 367개 통과, Windows 심볼릭 링크
권한에 의존하는 2개 제외. 별도 임시 MongoDB의 이미지 HTTP 통합 검사 14개는 모두 통과했다.
새 회귀 검사는 가로/세로로 긴 이미지 보강, 원본·화면용 무변경, 투명도·비율 유지,
조회 전용 모드의 ID 전용 projection, 보강 모드의 원본 제외와 한 문서 단위 읽기를 확인한다.
임시 MongoDB는 검사 후 정리했다. 중단했던 `verify:full`과 브라우저 재검증은 실행하지
않았으므로 A1-04 전체 완료로 처리하지 않는다.

같은 날 사용자 실행 전체 검증 결과를 확인했다. 위 제한 검증 이후 실행한
`.local-validation/2026-10-22T15-07-43.390Z-985a93130f254fa08de37278be8a9756/summary.json`은
`mode: full`, `status: passed`, 309초다. 정책 28·백엔드 369·Node 96·React 116·MongoDB 73·
Chromium 39개로 총 721개가 제외 없이 통과했고 빌드·임시 환경 정리도 성공했다.
긴 이미지 보강 회귀와 이전 프로필 응답 기대값 실패 2건의 해결도 포함한다.
이 결과로 위 전체 검증 보류를 해소하고 A1-04 로컬 구현 범위를 완료 처리한다.
실제 사용자·기기·운영 승인이나 기존 DB·백업 유지보수를 실행한 결과는 아니다.

이 모듈 이동 후에는 사용자 지시로 검증을 실행하지 않았다.
기존 수치를 이동 후 동작이나 실사용 성능의 근거로 사용하지 않는다.
