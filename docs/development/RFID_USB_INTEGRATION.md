# USB RFID 연결과 장치 로그

> 공용 칩을 먼저 등록하려면 [관리자 전용 칩 등록 페이지](RFID_CHIP_REGISTRATION.md)를 사용한다.
> 아동별 개인 태그 연결은 아래 기존 보호자 흐름을 유지한다.

현재 우선 연결 방식은 **Windows PC의 Chrome/Edge + USB**다. 기존 Wi-Fi 경로는 선택 기능으로 보존한다.
USB 방식에는 Arduino Wi-Fi 비밀번호·장치 ID·장치 키·사설망 포트 개방이 필요하지 않다.

## USB만 꽂았는데 웹에 표시되지 않았던 이유

이전 구현은 보드가 Wi-Fi API로 상태를 보내야 웹이 표시하는 구조였다. USB 연결은 Windows의 COM
포트를 만들지만 웹의 Wi-Fi 장치 목록에 자동 등록하지 않는다. 이제 브라우저가 Web Serial로 직접
USB를 읽는다. Docker 컨테이너가 COM 포트를 열거나 별도 Python 중계 서버를 설치하지 않는다.

브라우저의 포트 선택은 사용자가 **USB 장치 연결** 버튼을 눌러야 시작한다. 허용한 포트 수가 0이어도
버튼에서 포트를 선택할 수 있다. 이전에 권한을 준 포트만 `getPorts()`로 조회한다.
[Chrome Web Serial 안내](https://developer.chrome.com/docs/capabilities/serial)와
[Web Serial 명세](https://serial.spec.whatwg.org/)의 권한·스트림 해제 규칙을 따른다.
보안 출처와 `navigator.serial` 지원 여부를 실제 실행 시 확인한다. 일반 사설 IP의 HTTP는 USB 연결
화면에 지원 안내를 표시한다. 같은 PC의 `http://127.0.0.1:5173` 또는 HTTPS를 사용한다.

```text
RC522 → Arduino → USB 115200bps → 브라우저의 연결 버튼/시리얼 읽기
  → 로그인한 아동 범위의 UID 매핑 조회 → 읽은 카드/위치 표시
  → 명시적 문장 추가 또는 배열 적용 → 기존 문장 생성·확인·TTS
브라우저 장치 상태 → POST /api/rfid/usb/events → backend 장치 로그
```

## 바로 연결하기

1. 앱을 `docker compose up -d`로 실행하고 PC에서 `http://127.0.0.1:5173`을 연다.
2. Arduino IDE의 시리얼 모니터·플로터와 다른 탭의 USB 연결을 닫는다. 업로드도 포트를 점유하므로
   업로드할 때는 웹의 **USB 연결 해제**를 누른다.
3. 기존 진단 스케치가 `RC522 Version: 0x82`, `RFID Reader Connected`, `UID: …`를 출력하면 그대로
   사용 가능하다. 원본 사용자 파일은 수정하거나 커밋에 포함하지 않는다.
4. 보호자 **RFID 카드판**에서 연결 아동을 선택하고 **USB 장치 연결**을 눌러 Arduino 포트를 고른다.
   이번 확인 환경의 포트는 COM4다. 번호는 다른 PC/재연결 때 달라질 수 있어 코드에 고정하지 않는다.
5. 카드를 대면 태그 등록 입력란에 UID가 들어간다. 기존 그림카드를 골라 **태그 연결 저장**을 누른다.
   USB에는 아래 Wi-Fi 장치 등록 양식을 사용할 필요가 없다. 등록에는 기존 `cards_manage`·동의,
   지원 화면에는 `board_manage` 권한이 필요하다.
6. 보호자에서 포트를 해제한 뒤 아동 계정의 **그림으로 말하기 → USB 장치 연결**을 사용한다.
   같은 포트를 여러 브라우저/계정에서 동시에 열지 않는다.
7. 카드를 순서대로 읽고 **읽은 카드를 문장에 추가**를 누른다. 기존 문장 뒤에 추가하며 총 12장을 넘으면
   기존 문장과 읽기 목록을 보존하고 안내한다. 문장 생성·확인·읽기는 기존 버튼을 사용한다.

태그 등록 후에는 **USB 태그 연결 다시 조회**로 미등록 상태를 갱신할 수 있다. 보호자 화면에서 등록을
저장한 뒤에는 현재 메모리의 읽기 목록도 다시 조회한다. UID는 브라우저 메모리와 등록 필드에만 두고
원시 스캔의 오프라인 캐시·자동 발화·학습 기록·별도 스캔 이력은 만들지 않는다.
USB 입력의 매핑 조회에는 로컬 API가 필요하다. 서버 중단/기존 앱의 오프라인 상태까지 USB 입력을
보장하지 않으며 기본 화면 카드 선택·기본 말하기는 기존 정책을 유지한다.

## USB 전용 펌웨어

`hardware/arduino/rfid-usb-board/rfid-usb-board.ino`는 Wi-Fi 설정 없이 JSON Lines를 출력한다.
UNO R4 WiFi 보드 코어와 MFRC522·SPI만 필요하며 기본은 `RFID_READER_COUNT=1`이다.
한 개를 실제 검수한 뒤 두 개·세 개로 늘린다. SS는 D10/D8/D7, RST는 D9/D6/D5다.
전원·신호 레벨·공유 MISO·안테나 간섭 조건은 [기존 배선 제안](RFID_WIFI_INTEGRATION.md#예정-배선표--실물-검수-필요)을
따른다. USB로 통신 방식을 바꾼 것이 전기적/RF 검증을 대신하지 않는다.

예시 UID는 실제 태그가 아닌 합성 값이다.

```json
{"protocol_version":1,"type":"snapshot","boot_id":"synthetic-boot","event_id":1,"reader_count":1,"readers":[{"reader_id":1,"status":"PRESENT","uid":"01020304"}]}
```

- 한 줄은 1024자까지이며 부분 수신·CRLF를 조합한다. 과도한 줄은 다음 개행까지 버린다.
  미완성 줄은 연결 해제 시 버리고 임의 문자열을 카드나 일반 로그로 해석하지 않는다.
- JSON은 버전·리더기 개수/순서·상태·UID 형식·동일 UID의 여러 위치 감지를 검사한다.
  같은 부팅의 중복/역순 이벤트는 무시하고 새 부팅은 이전 USB 읽기 목록을 비운다.
  boot_id는 스트림 구분용 nonce이며 인증 비밀이 아니다.
- 리더기 1개는 새 PRESENT 전환을 순서대로 모은다. heartbeat만으로 카드를 반복 추가하지 않는다.
  제거 후 같은 카드를 다시 제시하면 다시 추가할 수 있다. 수집한 목록을 제거만으로 지우지는 않는다.
- 리더기 2·3개는 현재 위치 순서를 표시하고 **USB 배열을 문장에 적용**으로 기존 문장을 교체한다.
  기존 초안이 있으면 확인한다. EMPTY는 제외하고 ERROR/미등록/사용 불가 상태는 적용하지 않는다.
- 펌웨어는 순차 안테나 켜기·WUPA/선택/HALT를 사용한다. 같은 UID 2회 성공 시 PRESENT,
  TIMEOUT 4회 이상이면서 마지막 성공 후 1200ms 이상이면 EMPTY다. 버전 0x82만으로 거절하지 않는다.
  시간 간격은 목표값이며 간섭/전원에 의한 제거 오판은 실제 검수가 필요하다.
- 기존 `UID:` 진단 모드는 800ms 이내 같은 UID의 빠른 중복만 막는다. 이 출력만으로 실제 카드 유지·
  제거를 증명할 수 없다. 세 위치·유지/제거가 필요하면 USB JSON 펌웨어를 업로드하고 검수한다.

## 장치 로그와 API

화면의 **장치 로그**에 연결·해제·버전·리더기 응답·카드 읽기·미등록·형식 오류를 표시한다.
최근 40개만 메모리에 유지하며 동일 상태 로그는 짧은 시간 동안 제한한다. 임의 시리얼 문자열과
UID 원문은 장치 로그에 표시하지 않는다. 아동 화면에는 UID 등록 입력란도 없다.
연결·해제·연결 실패는 빠르게 반복해도 누락하지 않는다. 포트 권한을 처음 허용한 뒤 감지 목록도 다시 조회한다.
탭/메뉴/계정 변경으로 컴포넌트를 떠나면 읽기를 취소하고 잠금을 해제한 뒤 포트를 닫는다.
끊긴 상태와 20초간 응답이 없는 상태에서는 적용을 막는다.

| 경로 | 동작 |
|---|---|
| POST /api/rfid/usb/resolve?user_id=… | Bearer 세션의 본인/board_manage 연결 범위로 정규화 UID 1~12개 조회. card_id·label·상태만 응답 |
| POST /api/rfid/usb/events?user_id=… | 같은 권한으로 허용된 action 열거값만 받아 204. UID·계정·시리얼 내용·장치 키를 받지 않음 |

USB resolve는 장치 키를 요구하지 않으며 DB의 최신 장치 상태나 의사소통/학습 기록을 쓰지 않는다.
동의 철회 후에도 기존 매핑 조회로 기록 없는 말하기를 지원하며 새 매핑 저장에는 동의가 필요하다.
장치 로그 전송 실패가 카드 선택·기본 말하기를 막지 않으며 로그 재전송 대기열도 만들지 않는다.
Docker의 backend 로그에는 아래처럼 **브라우저가 보고한 상태**만 기록한다. 서버가 COM 포트를 직접
감지했다는 뜻이 아니다. MongoDB `attach: false`·`logging.driver: none` 설정은 유지한다.

```text
{"event":"rfid_usb","source":"browser","action":"connected"}
{"event":"rfid_usb","source":"browser","action":"tag_read"}
{"event":"rfid_usb","source":"browser","action":"disconnected"}
```

```powershell
docker compose logs -f --tail 100 backend frontend
```

## 검증 기록

- Node USB 파서·중복·부분 수신·포트 해제/재연결·권한 오류 7개 통과.
- 호스트 RFID 백엔드 단위 6개 통과. 첫 명령은 작업 디렉터리에 맞지 않는 실행 파일 경로로
  시작하지 못했으며 올바른 경로로 재실행했다. 테스트 실패를 통과로 취급하지 않는다.
- 기존 RFID/새 USB 화면의 개별 React 검사 9개 통과. 연속 조회/늦은 응답 검사는 전체 실행에 추가했다.
- R4 USB 펌웨어 컴파일은 코어 1.6.0·MFRC522 1.4.12·Arduino CLI 1.5.1로 통과했다.
  Flash 66,364바이트(25%)·RAM 7,312바이트(22%)이며 보드 업로드는 미실행이다.
  MFRC522의 renesas_uno 아키텍처 미선언 경고가 남아 있어 실물 호환을 보장하지 않는다.
- 첫 전체 실행은 기존 App·BulkCardImport·SupportRecords 검사에서 5초 시간 초과 4개와
  준비되지 않은 기록 패널 조회 1개가 실패했다. USB 화면 6개는 통과했으나 전체 React는
  191개 통과/5개 실패로 전체 성공이 아니다. MongoDB·브라우저 단계는 미실행, 임시 환경 정리는 통과했다.
  당시 Arduino 컴파일도 동시 실행 중이었으며 컴파일 종료 후 제한 시간을 변경하지 않고 재실행했다.
- 컴파일 종료 후 재실행에서도 기존 App·BulkCardImport 검사 3개가 5초 시간 초과됐다.
  193개 통과/3개 실패였으며 해당 실행 역시 MongoDB·브라우저 단계에 도달하지 못했다.
  로컬 Docker에서 jsdom 작업자가 과도하게 병렬 실행되는 부담을 줄이도록 Vitest `maxWorkers: 2`로
  제한했다. [작업자 수 설정](https://vitest.dev/config/maxworkers)에 따른 변경이며 파일별 격리·검사 내용·
  5초 제한은 유지한다. 변경 후 아래 전체 결과로 재확인했다.
- 실제 COM4를 115200bps로 열고 닫는 것을 확인했다. 최초 DTR 미설정 확인에서는 출력이 없었고,
  DTR 설정 후 4줄 중 `RC522 Version: 0x82`·`RFID Reader Connected`를 수신했다.
  UID 원문은 출력/저장하지 않았다. 이 확인에서 태그 프레임은 0개로 카드 인식은 **미확인**이다.

전체 `npm run verify:full` 최종 성공 결과는 다음과 같다. 881개와 빌드·임시 스택/볼륨 정리를 통과했다.

`.local-validation/2026-10-27T15-15-48.505Z-0c58d5d50cc14644aea221ca96934416/summary.json`이다.
