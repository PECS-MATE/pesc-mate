# USB RFID 연결과 장치 로그

현재: 사용자 화면 왼쪽 메뉴의 **기기 연결**에서 Arduino 포트 하나를 선택한다.
USB 보드에 연결한 리더기 1~3개로 등록된 카드를 태그하면 **나의 문장**에 추가한다.
사용자 연결 메뉴에는 연결 상태·연결/해제·실패 안내만 표시한다. 보호자 등록 로그는 유지한다.
홈에서 추가하면 말하기 화면으로 이동한다. 설정·다른 활동·음성 재생 중에는 추가하지 않는다.
이 문서의 과거 검증 기록은 당시 구현 기준이며 현재 실물 검수 완료를 의미하지 않는다.
검증 범위는 [활동 UX 기록](USER_INTERFACE.md#activity-ux)을 따른다.

> 공용 칩을 먼저 등록하려면 [관리자 전용 칩 등록 페이지](RFID_USB_INTEGRATION.md#rfid-chip-registration)를 사용한다.
> 아동별 개인 태그 연결은 아래 기존 보호자 흐름을 유지한다.

## 태그 순서와 동시 입력 자동 발화 — 2026-11-13

- 기본 3리더기 펌웨어에서도 1개만 정상 연결되어 있으면 해당 리더기로 사용할 수 있다.
  다른 위치의 ERROR는 표시하되 정상 위치의 태그 입력 전체를 막지 않는다.
- **순차 태그는 감지 순서**다. 3번 → 1번 → 2번으로 태그하면 문장판도 그 순서다.
- 첫 새 태그 감지부터 **150ms 고정 구간**에 들어온 서로 다른 리더기의 새 입력은
  한 묶음으로 처리한다. 묶음 안에서만 1 → 2 → 3번 순서로 정렬한다.
  같은 리더기의 연속 입력은 별도 묶음이다. 후속 입력마다 구간을 연장하지 않는다.
- 한 장 태그는 화면만 갱신한다. 두 장 이상 동시 입력이 모두 등록된 카드로 확인되면
  문장판에 추가하고 **현재 문장판 전체를 한 번 자동 발화**한다.
  기존 문장 뒤에 추가하며, 문장판의 고른 카드명을 순서대로 이어 읽는다.
  AI 문장 생성으로 순서를 바꾸지 않으며 기존 문장 생성 버튼은 유지한다.
- 미등록·사용 불가 카드가 섞이면 사용 가능한 카드만 추가하고 자동 발화는 하지 않는다.
  12장 한도를 넘는 묶음은 일부만 추가하거나 발화하지 않고 기존 문장을 유지한다.
- JSONL 스냅샷에서 계속 올려둔 카드는 반복 추가하지 않는다. 제거 후 재태그는 새 입력이다.
  예전 진단용 UID 출력은 제거 상태를 보내지 않으므로 기존 800ms 중복 억제에 의존한다.
  실사용의 유지·제거 판별은 USB JSONL 펌웨어를 사용한다.
- 매핑 조회는 묶음별로 직렬 처리하여 서버 응답 속도가 태그 순서를 바꾸지 않게 한다.
  연결 해제·계정/화면 전환·수동 문장판 편집 이후의 오래된 묶음은 적용하지 않는다.
  RFID 추가 자체로 생긴 문장판 갱신은 다음 정상 입력을 취소하지 않는다.
- 기기 연결 클릭에서 기존 음성 플레이어의 오디오 잠금을 해제한다.
  자동 재생이 브라우저 정책으로 거부되면 기존 재생 실패·다시 재생 경로를 사용한다.
  실제 자동 발화의 성공과 음성 품질은 기기에서 확인해야 한다.

동시 여부는 브라우저에 전달된 감지 시점을 기준으로 판단한다. MCU 순회·USB 버퍼링의
영향을 포함하므로 물리적으로 카드를 놓은 정확한 시각의 측정값은 아니다.
이 규칙은 사용자 화면의 USB 자동 추가 경로에 적용하며, 기존 Wi-Fi 관리 화면의
현재 배열 확인·수동 적용과 등록 화면의 UID 입력은 유지한다. 펌웨어는 변경하지 않았다.

### 이번 자동 검증

- USB 입력/연결·새 묶음 큐·컴포넌트 입력·문장판/음성 연결·기존 App 인증·
  음성 플레이어 관련 7개 파일의 고유 검사 48개가 통과했다.
  입력 큐 용량 초과 시 묶음 전체 거부를 추가하고 해당 9개 검사를 재실행했으며,
  미등록 안내 순서 보완 후 USB 컴포넌트 8개 검사도 재실행해 통과했다.
- `git diff --check`도 통과했다. 가상 시리얼·가짜 시계·합성 UID와 매핑 응답을 사용했다.
  실제 리더기 1/2/3개·동시 배치·재연결·Chrome/Edge 자동 재생은 미검수다.
- 빌드·펌웨어 컴파일/업로드·전체 백엔드 및 MongoDB 검사는 실행하지 않았다.

## 보호자 장치 확인 — 세 리더기

- 기본 ‘기기 연결’ 화면에는 USB 연결/해제, ‘장치 상태 확인’, 리더기 1·2·3의 상태만 표시한다.
  태그 연결·장치 키·로그 등 기존 관리 기능은 ‘태그·장치 설정’에서 연다.
  화면을 전환하면 이전 USB 세션을 닫아 두 화면이 같은 포트를 동시에 열지 않는다.
- USB 연결만으로 초록불을 켜지 않는다. 확인 버튼이 새로운 요청 ID와 함께
  `STATUS <request_id>`를 보내고, 펌웨어가 각 리더기의 VersionReg를 새로 읽어 응답한다.
  요청 ID가 일치하는 결과만 표시한다. 이 검사는 SPI 통신 응답 확인이며 실제 카드 인식·RF 성능은
  카드 태그로 별도 확인해야 한다. 물리적으로 선이 꽂힌 모든 핀의 상태를 직접 측정하는 기능은 아니다.
- 정상은 초록+‘정상’, 오류는 오류색+‘비정상’, 미확인/누락은 회색으로 표시한다.
  8초 응답 대기 후에는 미확인으로 남기고, 20초 지난 결과는 재확인 필요로 바꾼다.
  USB 분리 시 이전 결과를 바로 지운다. 1·2개만 보고한 펌웨어로 3개 정상을 표시하지 않는다.
- `diagnostics` JSON 응답은 UID를 포함하지 않고 문장·태그 매핑·사용 기록으로 전달하지 않는다.
  기본 진단 화면은 백엔드에 장치/로그 조회나 쓰기를 하지 않는다.
- USB용·진단용 스케치는 모두 3개로 변경했다. SS D10/D8/D7, RST D9/D6/D5다.
  **기존 보드에 새 스케치를 다시 업로드해야 상태 확인 요청에 응답한다.**
  문장 연동에는 `hardware/arduino/rfid-usb-board/rfid-usb-board.ino`를 사용한다.

### 세 리더기 확인 검증

- 프런트엔드 빌드·`git diff --check` 통과. 기존 큰 JS 청크 경고 유지.
- 순수 JS 검사에서 진단 프레임 형식/ID/순서 거부, 리더기 3 레거시 출력,
  기존 3개 snapshot 처리 유지, 진단이 카드 입력으로 처리되지 않음과 요청 명령을 확인했다.
- 격리 Chrome/모의 Web Serial 포트로 연결만으로 정상 아님, 세 정상, 일부 오류,
  3번 누락, 이전 요청 응답 무시, 시간 초과, 결과 만료, USB 분리 시 정상 제거를 확인했다.
  기본 화면의 관리 API 호출 없음과 고급 관리 전환 시 포트 닫힘, 1440/390/320px 배치도 확인했다.
- 실행 가능한 Arduino CLI를 확인하지 못해 R4 대상 펌웨어 컴파일·업로드는 미실행이다.
  실제 세 리더기 배선·SPI 응답·카드 인식·iPad·스크린리더 검수는 미실행이며 정상 완료로 표시하지 않는다.

### 두 리더기 변경 검증 — 2026-11-02

- 진단 스케치는 사용자 제공 코드 기반으로 SS 10/8·RST 9/6·115200bps를 적용했다.
  UID 출력은 웹이 리더기 번호를 잃지 않도록 한 줄의 `Reader N UID:` 형식으로 보완했다.
- 실사용 JSONL 스케치의 기본 리더기를 2개로 변경하고 사용 중인 SS 핀만 초기화한다.
  두 입력은 기존 사용자 자동 추가 경로를 공유한다. 백엔드·태그 매핑·TTS API는 변경하지 않았다.
- 일회성 Node 확인으로 번호별 UID 정규화·800ms 개별 중복 억제·시간 경과 재입력·
  이전 UID 출력 호환·버전 오류 해석·두 위치 JSON 순서·중복 이벤트 무시·부분 줄 수신을 확인했다.
  테스트 파일은 추가하지 않았고 장치·DB 쓰기는 하지 않았다.
- 프런트엔드 빌드와 변경분 공백 검사 통과. 기존 500kB 청크 경고는 유지된다.
- 현재 PATH에서 arduino-cli를 찾지 못했다. 이번 두 스케치의 보드 대상 컴파일·업로드·
  실물 두 리더기 동시/교대 태그·RF 간섭·브라우저/문장/TTS 종단 검수는 미실행이다.
  이전 컴파일 통과 기록을 이번 버전 검증으로 간주하지 않는다.
- MFRC522의 초기화·SPI 선택·안테나·카드 상태 동작은
  [라이브러리 원본](https://github.com/miguelbalboa/rfid/blob/master/src/MFRC522.cpp)을 참고했다.

현재 우선 연결 방식은 **Windows PC의 Chrome/Edge + USB**다. 기존 Wi-Fi 경로는 선택 기능으로 보존한다.
USB 방식에는 Arduino Wi-Fi 비밀번호·장치 ID·장치 키·사설망 포트 개방이 필요하지 않다.

## USB만 꽂았는데 웹에 표시되지 않았던 이유

이전 구현은 보드가 Wi-Fi API로 상태를 보내야 웹이 표시하는 구조였다. USB 연결은 Windows의 COM
포트를 만들지만 웹의 Wi-Fi 장치 목록에 자동 등록하지 않는다. 이제 브라우저가 Web Serial로 직접
USB를 읽는다. Docker 컨테이너가 COM 포트를 열거나 별도 Python 중계 서버를 설치하지 않는다.

브라우저의 포트 선택은 사용자가 **USB 장치 연결** 버튼을 눌러야 시작한다. 허용한 포트 수가 0이어도
버튼에서 포트를 선택할 수 있다. 이전에 권한을 준 포트만 `getPorts()`로 조회한다.
화면의 포트 수는 PC의 물리적 USB 장치 수가 아니라 이 브라우저에 권한을 준 포트 수다.
포트 선택 실패와 선택 후 열기 실패를 구분해 안내한다. 열기 실패 시에는 Arduino IDE의 시리얼
모니터·플로터와 다른 브라우저 탭의 연결을 닫고 재시도한다. 사용자 취소는 오류로 기록하지 않는다.
[Chrome Web Serial 안내](https://developer.chrome.com/docs/capabilities/serial)와
[Web Serial 명세](https://serial.spec.whatwg.org/)의 권한·스트림 해제 규칙을 따른다.
보안 출처와 `navigator.serial` 지원 여부를 실제 실행 시 확인한다. 일반 사설 IP의 HTTP는 USB 연결
화면에 지원 안내를 표시한다. 같은 PC의 `http://127.0.0.1:5173` 또는 HTTPS를 사용한다.

```text
RC522 → Arduino → USB 115200bps → 브라우저의 연결 버튼/시리얼 읽기
  → 로그인한 아동 범위의 UID 매핑 조회 → 나의 문장에 자동 추가
  → 순차 한 장은 화면 갱신 / 동시 여러 장은 순서대로 한 번 자동 발화
브라우저 장치 상태 → POST /api/rfid/usb/events → backend 장치 로그
```

## 바로 연결하기

1. 앱을 `docker compose up -d`로 실행하고 PC에서 `http://127.0.0.1:5173`을 연다.
2. Arduino IDE의 시리얼 모니터·플로터와 다른 탭의 USB 연결을 닫는다. 업로드도 포트를 점유하므로
   업로드할 때는 웹의 **USB 연결 해제**를 누른다.
3. 실사용에는 `rfid-usb-board.ino`를 업로드한다. 두 리더기 진단은 `card_reader_test.ino`를 사용한다.
   기존 단일 `UID:` 출력도 호환되지만 유지·제거는 알 수 없다.
4. 보호자 **RFID 카드판**에서 연결 아동을 선택하고 **USB 장치 연결**을 눌러 Arduino 포트를 고른다.
   이번 확인 환경의 포트는 COM4다. 번호는 다른 PC/재연결 때 달라질 수 있어 코드에 고정하지 않는다.
5. 카드를 대면 태그 등록 입력란에 UID가 들어간다. 기존 그림카드를 골라 **태그 연결 저장**을 누른다.
   USB에는 아래 Wi-Fi 장치 등록 양식을 사용할 필요가 없다. 등록에는 기존 `cards_manage`·동의,
   지원 화면에는 `board_manage` 권한이 필요하다.
6. 보호자에서 포트를 해제한 뒤 아동 계정의 왼쪽 메뉴에서 **기기 연결**을 사용한다.
   같은 포트를 여러 브라우저/계정에서 동시에 열지 않는다.
7. 정상 연결된 1~3개 리더기에서 태그하면 **나의 문장**에 추가된다.
   한 장은 화면만 갱신하며, 150ms 안의 여러 리더기 입력은 묶어서 한 번 자동 발화한다.
   기존 문장 뒤에 추가하며 총 12장을 넘으면 문장 전체를 유지하고 안내한다.
   문장 생성·확인·수동 말하기 버튼도 계속 사용할 수 있다.

문장 생성 시 로컬 Ollama 응답 대기는 기본 10초까지다. 그 안에 응답하지 않으면 규칙 기반
문장으로 저장하며, 문장 표시 후 통계 갱신은 별도로 진행한다. 프런트엔드의 일반 API 요청
시간 제한은 15초다. 모델 응답 지연과 실제 카드 입력·발화 속도는 실기기에서 미검증이다.

## 이번 변경 검증 기록

- 사용자 요청에 따라 자동 테스트·빌드·브라우저 및 실물 칩 검증은 실행하지 않았다.
- 코드와 문서의 차이만 확인했다. 실물 연결, 태그 표시, 문장 생성 시간은 사용자 검증이 필요하다.

태그 등록 후에는 **USB 태그 연결 다시 조회**로 미등록 상태를 갱신할 수 있다. 보호자 화면에서 등록을
저장한 뒤에는 현재 메모리의 읽기 목록도 다시 조회한다. UID는 브라우저 메모리와 등록 필드에만 두고
원시 스캔의 오프라인 캐시·자동 발화·학습 기록·별도 스캔 이력은 만들지 않는다.
USB 입력의 매핑 조회에는 로컬 API가 필요하다. 서버 중단/기존 앱의 오프라인 상태까지 USB 입력을
보장하지 않으며 기본 화면 카드 선택·기본 말하기는 기존 정책을 유지한다.

## USB 전용 펌웨어

`hardware/arduino/rfid-usb-board/rfid-usb-board.ino`는 Wi-Fi 설정 없이 JSON Lines를 출력한다.
UNO R4 WiFi 보드 코어와 MFRC522·SPI만 필요하며 기본은 `RFID_READER_COUNT=2`다.
현재 두 리더기의 SS는 D10/D8, RST는 D9/D6이다. 세 번째 핀은 현재 사용하지 않는다.
전원·신호 레벨·공유 MISO·안테나 간섭 조건은 [기존 배선 제안](RFID_WIFI_INTEGRATION.md#예정-배선표--실물-검수-필요)을
따른다. USB로 통신 방식을 바꾼 것이 전기적/RF 검증을 대신하지 않는다.

예시 UID는 실제 태그가 아닌 합성 값이다.

```json
{"protocol_version":1,"type":"snapshot","boot_id":"synthetic-boot","event_id":1,"reader_count":1,"readers":[{"reader_id":1,"status":"PRESENT","uid":"01020304"}]}
```

- 한 줄은 1024자까지이며 부분 수신·CRLF를 조합한다. 과도한 줄은 다음 개행까지 버린다.
  미완성 줄은 연결 해제 시 버리고 임의 문자열을 카드나 일반 로그로 해석하지 않는다.
- JSON은 버전·리더기 개수/순서·상태·UID 형식·동일 UID의 여러 위치 감지를 검사한다.
  같은 부팅의 중복/역순 이벤트는 무시하고 새 부팅은 이전 USB 읽기 목록을 비운다.
  boot_id는 스트림 구분용 nonce이며 인증 비밀이 아니다.
- 사용자 자동 추가 모드는 리더기별 새 PRESENT를 문장에 추가한다. 같은 상태 유지·heartbeat는
  반복 추가하지 않고 EMPTY 이후 재태그는 새 입력이다. 동시에 새로 인식되면 1 → 2 순서다.
  두 위치에 같은 UID가 잡히거나 ERROR가 포함된 프레임은 추가하지 않는다.
- 보호자의 수동 읽기 목록에서 리더기 1개는 새 PRESENT 전환을 순서대로 모은다. heartbeat만으로 카드를 반복 추가하지 않는다.
  같은 칩 UID는 현재 읽기 목록에 한 번만 담는다. 떼었다 다시 대거나 일시적으로 EMPTY가 돼도
  목록이 유지되는 동안 중복 추가하지 않는다. 목록 비우기·문장 적용 후에는 다시 읽을 수 있다.
  서로 다른 칩이 같은 그림카드에 연결된 경우는 각각 별개 입력으로 취급한다.
  수집한 목록을 칩 제거만으로 지우지는 않는다.
- 보호자의 수동 입력에서 리더기 2·3개는 현재 위치 순서를 표시하고 **USB 배열을 문장에 적용**으로 기존 문장을 교체한다.
  기존 초안이 있으면 확인한다. EMPTY는 제외하고 ERROR/미등록/사용 불가 상태는 적용하지 않는다.
- 펌웨어는 순차 안테나 켜기·WUPA/선택/HALT를 사용한다. 같은 UID 2회 성공 시 PRESENT,
  TIMEOUT 4회 이상이면서 마지막 성공 후 1200ms 이상이면 EMPTY다. 버전 0x82만으로 거절하지 않는다.
  시간 간격은 목표값이며 간섭/전원에 의한 제거 오판은 실제 검수가 필요하다.
- 진단 모드는 `Reader 1 UID: …`와 `Reader 2 UID: …`를 지원하고 리더기별로 800ms 중복을 억제한다.
  기존 `UID:`도 지원하지만 리더기 1로 간주한다. 진단 출력만으로 유지·제거를 증명할 수 없다.
  두 리더기의 유지·제거를 구분하려면 USB JSON 펌웨어를 업로드하고 검수한다.

## 장치 로그와 API

2026-10-29 단일 리더기 중복 보정: 같은 칩을 떼었다 다시 대거나 일시적인 EMPTY 뒤 재인식해도
현재 읽기 목록에는 UID당 한 번만 유지한다. 기존 10장처럼 이미 쌓인 목록은 화면의
**USB 읽기 목록 비우기**로 비운 뒤 다시 읽는다. 이 변경의 테스트·빌드·실물 브라우저
확인은 사용자 요청에 따라 미실행이다.

2026-10-29 안내 개선: 권한을 준 포트가 0개여도 선택창을 열 수 있음을 화면에 표시한다.
선택 후 포트 열기 실패는 점유 가능성을 안내하며, 서버에는 기존 `connect_failed` 상태만
전송한다. 실제 장치의 연결 상태를 서버가 직접 판정하지 않는다. 이 변경의 테스트·빌드와
실물 브라우저 확인은 사용자 요청에 따라 미실행이다.

화면의 **장치 로그**에 연결·해제·버전·리더기 응답·카드 읽기·미등록·형식 오류를 표시한다.
최근 40개만 메모리에 유지하며 동일 상태 로그는 짧은 시간 동안 제한한다. 임의 시리얼 문자열과
UID 원문은 장치 로그에 표시하지 않는다. 아동 화면에는 UID 등록 입력란도 없다.
연결·해제·연결 실패는 빠르게 반복해도 누락하지 않는다. 포트 권한을 처음 허용한 뒤 감지 목록도 다시 조회한다.
탭/메뉴/계정 변경으로 컴포넌트를 떠나면 읽기를 취소하고 잠금을 해제한 뒤 포트를 닫는다.
끊긴 상태와 20초간 응답이 없는 상태에서는 적용을 막는다.

| 경로 | 동작 |
|---|---|
| POST /api/rfid/usb/resolve?user_id=… | Bearer 세션의 본인/board_manage 연결 범위로 정규화 UID 1~12개 조회. card_id·label·상태만 응답 |
| POST /api/rfid/usb/events?user_id=… | 같은 권한으로 허용된 action 열거값만 받아 204. UID·계정·시리얼 내용·장치 키를 받지 않음 |

USB resolve는 장치 키를 요구하지 않으며 DB의 최신 장치 상태나 의사소통/학습 기록을 쓰지 않는다.
동의 철회 후에도 기존 매핑 조회로 기록 없는 말하기를 지원하며 새 매핑 저장에는 동의가 필요하다.
장치 로그 전송 실패가 카드 선택·기본 말하기를 막지 않으며 로그 재전송 대기열도 만들지 않는다.
Docker의 backend 로그에는 아래처럼 **브라우저가 보고한 상태**만 기록한다. 서버가 COM 포트를 직접
감지했다는 뜻이 아니다. MongoDB `attach: false`·`logging.driver: none` 설정은 유지한다.

```text
{"event":"rfid_usb","source":"browser","action":"connected"}
{"event":"rfid_usb","source":"browser","action":"tag_read"}
{"event":"rfid_usb","source":"browser","action":"disconnected"}
```

```powershell
docker compose logs -f --tail 100 backend frontend
```

### 관리자 공용 RFID 칩 등록

현재 PC는 USB 연결을 사용한다. 기존 아동별 RFID 설정과 별도로 운영 권한 담당자가
**칩을 하나씩 읽어 공용 그림카드에 미리 연결하는 페이지**를 추가했다.
사용자 선택에 따라 공용 칩은 모든 아동에게 적용하고 개인 사진 카드는 기존 아동별 매핑을 유지한다.

<a id="rfid-chip-registration--사용하는-순서"></a>
#### 사용하는 순서

1. 공용 콘텐츠 운영 권한(`support_staff` + `content_manage`)이 있는 계정으로 로그인한다.
   기본 로컬 시연 환경의 `admin`이 해당 계정이다. 새 역할을 만들거나 일반 담당자에게 자동 부여하지 않는다.
2. 왼쪽 **RFID 칩 등록** 메뉴를 연다. 아동을 먼저 연결/선택하거나 Wi-Fi 장치를 등록할 필요가 없다.
3. Arduino IDE의 시리얼 모니터를 닫고 **USB 장치 연결**에서 Arduino 포트를 선택한다.
   브라우저 권한·안전한 출처·115200bps와 기존 `UID:`/USB JSON 지원은 [USB 연동 안내](RFID_USB_INTEGRATION.md)를 따른다.
4. 칩을 하나만 대면 **인식한 칩 UID**에 값이 고정된다. 다른 칩을 대더라도 확인 중인 UID는 바뀌지 않는다.
5. 카드명/분류를 검색해 공용 그림카드를 고르고 그림과 `UID → 카드명`을 확인한다.
   이미 등록된 UID는 현재 연결을 표시한다. 같은 연결의 중복 저장은 하지 않는다.
6. **칩 등록 저장** 또는 **칩 연결 변경**을 누른다. 로그인한 운영 계정의 세션과
   `content_manage` 권한으로 저장하며, 칩마다 비밀번호를 다시 입력하지 않는다.
7. 저장 완료 후 칩을 떼고 **다음 칩 인식**을 누른다. 선택 카드와 UID를 비운 뒤 다음 칩을 읽는다.
8. 목록에서 UID/카드명으로 검색해 수정·해제할 수 있다. 최근 50개를 우선 표시하고 전체 등록 수도 보여 준다.

기존 기본 카드 또는 승인된 공용 카드 중에서 선택한다. 개인 카드·승인 대기·반려·비활성 카드는
공용 후보에 포함하지 않는다. 미리보기 로딩/오류를 구분하고 카드명과 선택 내용도 표시한다.

<a id="rfid-chip-registration--등록과-실제-말하기의-분리"></a>
#### 등록과 실제 말하기의 분리

USB 등록 모드는 UID만 전달한다. 아동 태그 조회·문장 대기열·문장 생성·발화·학습 기록을 만들지 않는다.
여러 위치의 칩이 동시에 읽히면 한 칩씩 올리라는 안내를 표시한다. 장치 상태 로그는 관리자 권한의
경로로 전송하며 일반 로그에 UID/비밀번호를 넣지 않는다.

저장한 공용 매핑은 USB와 기존 Wi-Fi 조회 모두에서 사용한다. 우선순위는 **아동별 개인 매핑 →
관리자 공용 매핑 → 미등록 안내**다. 개인 연결을 해제하면 공용 연결이 다시 적용된다.
공용 카드가 비활성화되거나 개인 카드로 바뀌면 공용 조회는 사용 불가가 된다. 원래 소유 아동도
이 경로로 개인 카드를 우회 사용하지 못하며, 별도 개인 매핑은 기존 정책대로 처리한다.

<a id="rfid-chip-registration--api권한저장"></a>
#### API·권한·저장

모든 경로 앞에 `/api`가 붙고 기존 Bearer 세션을 사용한다.

| 메서드/경로 | 동작 |
|---|---|
| GET /rfid/admin/catalog | 운영 권한으로 공용 카드와 UID 등록 목록 조회, no-store |
| PUT /rfid/admin/bindings | 로그인 세션 + 운영 권한. uid·card_id·expected_revision |
| POST /rfid/admin/usb/events | 운영 권한으로 허용된 USB 상태 action만 로그에 남기고 204 |

`card_id=null`은 해제다. 신규는 `expected_revision=null`, 기존은 조회한 revision을 보낸다.
등록/변경/해제는 공유 쓰기 잠금 안에서 계정 상태·운영 권한·공용 카드 범위·버전을 확인한다.
삭제 후 재등록도 새 revision을 만들며 충돌은 409다. 오류 뒤에는 현재 칩과 선택 카드를 보존하고
목록 새로고침으로 실제 등록 상태를 확인하게 한다. 자동 쓰기 재시도는 없다.

공용 칩은 5000개 한도다. `rfid_shared_bindings`의 `_id`는 정규화 UID이며 card_id·revision·updated_at·
schema_version을 저장한다. 카드명/사진은 복제하지 않는다. 최신순 색인과 문서 스키마 기준선에 포함한다.
기존 로컬 BSON 백업 범위에 포함되지만 새 운영 백업 복원 훈련을 완료한 것으로 취급하지 않는다.

공용 칩은 플랫폼 자산이므로 아동 개인정보 내보내기/삭제로 전체 매핑을 내보내거나 지우지 않는다.
아동의 개인 매핑은 기존 삭제 정책을 따른다. 감사는 기존 privacy_audit_logs에 운영자 범위의
rfid_shared_saved/removed와 UID 해시를 기록하고 원시 UID는 넣지 않는다.

아동·보호자·운영 권한 없는 담당자는 메뉴와 공용 관리 API를 사용할 수 없다. 공용 칩 사용이
개인 카드 열람·아동 기록 조회·운영 권한 관리 책임자 권한을 부여하지 않는다.

#### 변경

- 아동의 USB 흐름에서 별도의 `실물 카드로 말하기`·태그 목록·적용 버튼을
  제거했다. 태그를 등록 카드로 조회한 뒤 나의 문장 뒤에 직접 추가한다.
- 홈에서 태그하면 기존 문장을 유지한 채 말하기 화면으로 이동한다.
  연결·해제 버튼은 상단 연결 메뉴 안에 유지한다.
- 사용자 연결 표시는 `기기 연결`·`기기 연결됨`으로 간소화했다.

  음성 준비 상태는 사용자 연결 메뉴에서 제거했다. 보호자 등록 로그는 유지한다.
  오프라인 대체 음성의 백그라운드 준비와 재생 실패 안내는 유지한다.
- 기존 보호자/관리자의 리더기·칩 등록·수동 적용 흐름은 변경하지 않는다.
  이번 자동 추가는 브라우저 USB 입력에 적용하며 서버/API를 삭제하지 않는다.
- 정상 단일 리더기 펌웨어는 계속 올려둔 카드의 반복 상태를 무시한다.
  떼었다가 다시 대면 새 태그로 취급하므로 같은 단어를 다시 추가할 수 있다.
- 진단용 UID 출력은 기존 800ms 중복 억제를 사용한다. 카드 유지/제거가 없는
  진단 출력으로 물리적 재태깅 여부를 완벽하게 판단할 수 있다고 보장하지 않는다.
- 여러 위치 입력도 문장을 교체하지 않고 새로 인식된 카드만 추가한다.
  카드 제거가 이미 담은 문장을 지우지는 않는다.
- 조회 중 새 태그는 순서를 유지해 모으고 최신 배치로 조회한다. 정상 카드만
  추가하고 미등록/사용 불가·문장 12장 초과는 오류 안내한다.
- 계정·화면·문장·동의/연결 상태가 달라진 조회 응답은 뒤늦게 반영하지 않는다.
  메뉴/설정·연습 등 비활성 화면과 발화 중·숨긴 탭·오프라인에서는 추가하지 않는다.
- 리더기 오류·잘못된 프레임·연결 해제는 진행 중인 추가를 무효화한다.
- 빠른 연속 조회가 React 반영보다 앞서도 이전 문장을 덮어쓰지 않도록 현재
  문장 참조를 동기 갱신한다. 태그 자체가 문장 생성이나 TTS를 자동 실행하지는 않는다.

## 1. 이번에 완성할 것

실물 그림 카드의 RFID 태그를 하나씩 읽으면 웹의 **선택 문장**에 대응하는 카드가 쌓이고,
사용자가 내용을 확인해 문장을 만들고 PC 스피커로 말할 수 있는 로컬 시연을 완성한다.
리더기가 그림을 인식하는 것이 아니라 **태그 UID와 앱 카드 ID의 연결**로 동작한다.

```text
실물 그림 카드 + RFID 태그
  → RC522 → UNO R4 WiFi → USB 시리얼
  → PC 웹 앱 → 현재 아동의 UID 매핑 → 기존 선택 문장
  → 문장 생성·확인 → 기존 기기 TTS → PC 스피커
```

기본 입력 예시는 ‘나 → 물 → 마시다’다. 한 리더기에 카드를 한 장씩 대며,
놓여 있는 여러 카드의 공간 순서를 한 번에 읽는 카드판은 만들지 않는다.
고정 카드판의 슬롯을 바꾸지 않고 현재 선택한 문장에만 추가한다.

첫 발화 트리거는 **기존 화면 버튼**이다. 마지막 스캔을 추측하거나 일정 시간이 지나면
자동으로 발화하지 않는다. 전용 ‘말하기/한 장 취소/비우기’ 태그는 기본 흐름 완성 후 선택 확장이다.
조합은 현재 한도인 12장까지 유지하며, 초과 시 기존 선택을 보존하고 안내한다.

## 2. 실행 구조와 제외 범위

- 웹은 같은 PC의 `http://127.0.0.1:5173`에서 연다. 시리얼은 Web Serial로 브라우저가 직접
  읽고 Docker의 백엔드가 COM 포트를 열지 않는다. 별도 Python 중계 서버는 이번 범위에서 제외한다.
- Web Serial은 사용자가 버튼으로 포트를 선택해야 하며, 지원 브라우저·안전한 출처를 실행 시
  확인한다. localhost/loopback은 안전한 출처로 취급되지만 일반 LAN HTTP를 같은 조건으로
  가정하지 않는다. [Chrome 안내](https://developer.chrome.com/docs/capabilities/serial),
  [MDN Web Serial](https://developer.mozilla.org/en-US/docs/Web/API/Web_Serial_API),
  [안전한 출처](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts).
- 사용자 확인 환경은 Windows Chrome/Edge지만 실제 지원 판정은 `navigator.serial`·권한·
  포트 열기로 확인한다. 브라우저 이름만으로 실제 기기 동작을 완료 표시하지 않는다.
- Arduino는 카드 읽기와 이벤트 전송만 한다. 문장 생성·음성 출력·로그인은 웹/기존 서버가 담당한다.
- R4의 Wi-Fi/Bluetooth, 태블릿/휴대폰 중계, Arduino 자체 스피커, 카드 데이터 쓰기,
  카메라/OCR, 추가 학습 게임, 클라우드 배포와 유료 TTS는 제외한다.
- Ollama는 필수 경로가 아니다. MVP 검수에서는 기존 `OLLAMA_ENABLED=false` 설정으로 규칙
  경로부터 확인한다. 자연스러운 문장을 임의로 자동 확정하거나 기존 의미 보존 정책을 완화하지 않는다.
- 동의 전·네트워크 실패 때는 기존 **선택 카드 그대로 말하기**로 대체한다. 자연스러운 문장 생성과
  기록 저장을 위해 기존 서버의 동의 검사를 우회하거나 별도 기록 API를 만들지 않는다.
- 새 태그 매핑은 우선 서버에 저장하고 현재 로그인 세션의 메모리에서 사용한다. 서버 연결이
  끊겨도 이미 읽은 매핑과 카드가 있으면 사용할 수 있지만, 오프라인 새 로그인·매핑 미준비 상태의
  실물 입력까지 보장하지 않는다. 이 경우 화면 카드 선택·기본 발화를 유지한다. 새로운 UID 영구
  캐시·원시 스캔 대기열은 이번에 추가하지 않는다.

## 3. 현재 기반과 첫 착수 조건

- [x] 보드·우선 시연 환경 확인: UNO R4 WiFi + Windows Chrome/Edge.
- [x] 기존 선택 문장, 최대 12장, 취소/순서 수정, 문장 생성·확인, 기기 TTS 구현 확인.
- [x] 사용자 작업 트리의 `hardware/arduino/card-reader-test/card_reader_test.ino` 확인:
  `SPI.h`, `MFRC522.h`, SS 10/RST 9, `Serial.begin(115200)`, UID와 3초 상태 출력.
- [ ] 실제 RC522 모듈·태그 종류, 전원/배선, R4 보드 코어·라이브러리 버전 확인.
- [ ] UNO R4 WiFi 대상 컴파일·업로드·UID 읽기 확인. 스케치 존재를 동작 성공으로 취급하지 않는다.

**전기적 연결을 먼저 확인한다.** [UNO R4 WiFi](https://docs.arduino.cc/hardware/uno-r4-wifi/)의
GPIO는 5V이며 [MFRC522 데이터시트](https://www.nxp.com/docs/en/data-sheet/MFRC522.pdf)는
저전압 전원/입출력 조건을 정한다. 모듈의 실제 회로·전압 사양과 SPI 신호의 레벨 변환 필요 여부를
확인하기 전 5V 직결을 가정한 배선이나 업로드를 안내하지 않는다. 핀 번호는 현재 코드 설정일 뿐
실제 배선 확인을 대신하지 않는다. MFRC522 라이브러리의 R4 호환성도 대상 컴파일로 확인한다.

현재 폴더명 `card-reader-test`와 파일명 `card_reader_test.ino`는 서로 다르다.
[Arduino 스케치 규칙](https://docs.arduino.cc/arduino-cli/sketch-specification/)에 맞춰 주 스케치와
폴더 이름을 일치시키는 작업을 MVP-01에 포함한다. 계획 단계에서는 사용자 파일을 이동·수정하지 않는다.

## 4. 기능별 TODO와 구현 순서

### MVP-01 — 카드 읽기와 안정된 이벤트 출력

- [ ] 배선·전압과 R4 호환성 확인 후 스케치 이름을 정리한다.
- [ ] 기존 진단용 문구와 UID 출력에서 웹이 읽을 버전 있는 JSON Lines 이벤트로 정리한다.
- [ ] 초기 준비/연결 오류와 카드 감지를 별도 이벤트로 구분한다. 상태 문구를 카드로 해석하지 않는다.
- [ ] 하나의 물리적 제시마다 한 번 처리하고, 같은 카드를 제거한 뒤 다시 대면 의도된 반복을 허용한다.
  무조건 500ms만 기다리거나 같은 UID를 영구 무시하는 방식으로 완료하지 않는다.
- [ ] 부팅/연결 세션과 증가하는 이벤트 번호를 정의해 재전송과 새 제시를 구분한다.
- [ ] 실제 태그 3장과 같은 태그 유지·제거·재제시·다른 태그 전환 결과를 기록한다.

완료 조건: R4에서 서로 다른 카드의 UID를 읽고 한 제시/한 이벤트와 의도된 재제시를 구분한다.
카드별 실제 UID나 아동 정보는 예제/로그로 Git에 넣지 않는다.

### MVP-02 — 웹에서 리더기 연결·수신

- [ ] 사용자가 ‘리더기 연결’로 포트를 선택하고 준비/연결/해제/오류 상태를 확인한다.
- [ ] 115200bps를 현재 스케치와 맞추되 진단 도구의 포트 점유·취소·열기 실패를 안내한다.
- [ ] 분할 수신·한 번에 여러 줄·CRLF·잘못된 JSON·과도한 길이·알 수 없는 버전을 처리한다.
- [ ] 중복 이벤트 번호와 과거 세션 이벤트는 버리고, 새 세션의 번호 초기화는 정상 처리한다.
- [ ] 연결 직후 준비 핸드셰이크로 제시 상태를 다시 맞춘다. 이미 놓인 카드의 유령 입력을 막는다.
- [ ] 한 페이지에서 한 수신 루프만 유지하고 해제·페이지 이탈·로그아웃 때 reader/port를 정리한다.
- [ ] 다른 탭/앱의 포트 점유를 조용히 재시도하지 않고 안내한다. 권한 취소도 기본 말하기를 막지 않는다.

완료 조건: 사용자가 선택한 리더기의 유효한 이벤트만 받으며 끊김·재연결에 카드가 임의 추가되지 않는다.
이 단계만으로 수신한 UID를 문장에 넣거나 자동 발화하지 않는다.

### MVP-03 — 실물 태그 등록과 문장 카드 입력

- [ ] 보호자/담당자가 `cards_manage` 연결 권한으로 대상 아동을 고르고 태그를 스캔해 앱 카드에 연결한다.
- [ ] UID는 이름/파일명이 아니라 기존 `card_id`에 연결한다. 펌웨어에 카드 뜻·아동별 매핑을 하드코딩하지 않는다.
- [ ] 한 아동 안에서 한 UID는 한 카드에만 연결하고 중복 변경은 명시 확인한다. 여러 태그가 같은 카드를
  가리키는 것은 허용한다. 생성·교체·삭제와 충돌 처리, 변경자·시각 감사를 같은 기능으로 구현한다.
- [ ] 매핑 조회·쓰기에서 현재 역할·아동 연결·카드 사용 가능 상태를 재검사한다. UID로 로그인하거나
  다른 아동의 매핑을 찾지 않는다. 등록 화면의 스캔이 아동의 문장에 들어가지 않도록 모드를 분리한다.
- [ ] 아동의 ‘그림으로 말하기’에서 입력을 직접 활성화한 때만 현재 계정의 등록된 카드를 순서대로 담는다.
- [ ] 미등록·삭제/비활성 카드와 최대 12장 초과는 안내만 하고 기존 문장·고정 위치는 유지한다.
- [ ] 보이지 않는 탭·다른 화면·계정 전환·로그아웃·권한 만료 때 입력을 비활성화하고 남은 이벤트를 버린다.
- [ ] 매핑은 개인정보 범위에 포함해 내보내기·삭제·캐시 정리·보존 정책을 정의한다. 원시 UID를
  일반 접속/CRUD 로그에 추가하지 않고 등록에 필요한 표시만 제한적으로 제공한다.
- [ ] 동의가 없으면 기존 매핑을 현재 로그인에서 조회·사용할 수 있는 범위와 신규 등록/서버 저장 거절을
  분리한다. 기록 없는 스캔 선택을 유지하고 미등록 태그를 몰래 저장하지 않는다.

완료 조건: 같은 PC에서 등록한 실물 카드 3장을 순서대로 대면 해당 아동의 선택 문장에 정확히 담긴다.
UID는 인증 비밀이 아니다. [MFRC522 라이브러리 안내](https://github.com/miguelbalboa/rfid)의
UID 복제 주의에 따라 계정/권한 확인 수단으로 사용하지 않는다.

### MVP-04 — 선택 문장 생성·확인·TTS 완주

- [ ] RFID 입력도 기존 선택 문장 갱신 경로를 사용해 카드 수정·생성 결과 무효화·취소 동작을 통일한다.
- [ ] 문장 생성 중 스캔을 임시 정지하고, 선택이 바뀐 경우 늦은 이전 생성 응답을 적용하지 않는다.
- [ ] 동의·서버 연결이 있을 때 기존 규칙 기반 문장 생성과 내용 확인 후 기기 TTS를 연결한다.
- [ ] 동의 전·생성/서버 실패 시 카드와 텍스트를 보존하고 선택 카드 그대로 발화할 수 있다.
- [ ] 문장 끝은 화면 버튼으로 결정한다. 자동 발화/자동 비우기 없이 완료 뒤 다음 입력을 사용자가 선택한다.
- [ ] 음량 0·한국어 음성 없음·재생 실패에 안내/재시도를 제공하고 긴급·복구 표현을 계속 사용할 수 있다.
- [ ] 실제 의사소통만 기존 동의/저장 정책으로 남긴다. 등록 스캔·상태 조회·학습 결과는 발화 기록과 합치지 않는다.
- [ ] 지원 기기의 Chrome과 Edge에서 직접 재생·중지·재연결까지 검수한다. 스텁 결과를 실제 음성으로 취급하지 않는다.

완료 조건: 실물 입력 → 문장 확인 → 실제 PC 음성 출력이 이어지고, 장애 때도 기본 말하기가 남는다.
Arduino 자체 스피커·Wi-Fi 전송을 구현한 것으로 취급하지 않는다.

## 5. MVP 완료 게이트

- [ ] 같은 카드 유지 시 중복 없음, 제거 후 재제시와 명시된 반복 카드 처리 확인.
