# 중요 운영 작업 재인증

2026-10-19 기준 A2-01의 재인증 대상은 **담당자 계정 권한·접근 설정과 공용 콘텐츠 변경**이다.
로그인 세션만으로 다음 쓰기를 실행할 수 없으며 작업 요청마다 로그인한 본인 비밀번호를 받는다.

| 대상 | API | 재인증 주체 |
|---|---|---|
| 담당자 운영 권한 부여·회수 | `PUT /api/admin/accounts/{id}/content-permission` | 서버에 지정한 관리 책임자 |
| 담당자 비활성화·활성화·접근 만료 | `PUT /api/admin/accounts/{id}/access` | 서버에 지정한 관리 책임자 |
| 공용 카드 승인·반려·비활성·재활성 | `PATCH /api/admin/card-submissions/{id}` | `content_manage` 보유 담당자 |
| 카테고리 생성 | `POST /api/admin/categories` | `content_manage` 보유 담당자 |
| 카테고리 이름·순서·활성 변경 | `PATCH /api/admin/categories/{id}` | `content_manage` 보유 담당자 |

계정 관리의 책임자 보호·버전·감사 정책은 [운영 권한 관리](ACCOUNT_PERMISSION_MANAGEMENT.md)를 따른다.
읽기 API·지표·알림에는 비밀번호를 추가하지 않는다. 기본 의사소통, 개인 카드 등록, 학습,
아동별 지원 연결 및 개인정보 내보내기·삭제의 기존 흐름도 이번 단위에서 변경하지 않는다.
이는 민감한 모든 개인정보 작업의 추가 인증이나 법정대리인 본인 확인까지 완료했다는 뜻이 아니다.

## 서버 검증

- 공용 콘텐츠 쓰기 본문에는 `password`가 필수다. 1~128자 SecretStr이며 응답에 반환하거나
  문서·감사 로그에 저장하지 않는다. 누락/잘못된 형식·알 수 없는 필드는 422다.
- 세션의 현재 계정 인증 외에 계정 문서를 다시 읽어 활성·만료·권한 버전을 확인하고,
  현재 `content_manage` 권한을 검사한 뒤 저장된 비밀번호 해시와 비교한다.
  비밀번호가 맞아도 역할·운영 권한이 없으면 실행할 수 없다.
- 콘텐츠 작업 전체는 별도 `content-operation:` 계정/IP 실패 제한을 공유한다.
  잘못된 비밀번호는 403, 한도 초과는 429다. 기본 한도/창은 기존 `LOGIN_MAX_FAILURES`와
  `LOGIN_LOCK_MINUTES`를 사용한다. 성공 시 해당 실패 제한만 초기화한다.
  계정 권한 관리의 `account-permission:` 및 일반 로그인 제한과는 구분한다.
- 계정/제한 저장소를 확인하지 못하면 503으로 중단하고 콘텐츠 쓰기를 시작하지 않는다.
  이미 콘텐츠 저장을 시도한 뒤 발생한 다른 503은 미반영을 보장하지 않는다. 현재 상태를
  다시 조회하고 사유를 확인하며 자동 재전송하지 않는다.
- 성공 후에도 권한 상승 토큰이나 재인증 유예 세션을 만들지 않는다. 다음 작업에도
  비밀번호가 필요하다. 기존 Bearer 세션이나 계정 권한을 새로 부여하지 않는다.
- 정상·오류 쓰기 응답은 `Cache-Control: no-store`다. 비밀번호는 URL·쿼리·로그용 헤더에
  넣지 않으며 기존 입력 검증 오류 필터도 원문 input을 제거한다.

비밀번호 재확인은 같은 인증 요소를 다시 확인하는 기능이며 MFA·일회용 거래 서명·재전송
방지 보증이 아니다. 이미 인증을 마친 진행 중 요청을 원격 취소하는 기능도 아니다.
운영 배포에는 HTTPS와 데모 자격 증명 제거가 필요하다. 이 구현이 개발용 HTTP를 안전한
인터넷 운영 환경으로 바꾸지는 않는다. 실제 운영 승인·추가 인증 수단 결정은 별도다.

## 확인 화면

공용 콘텐츠 작업은 대상·변경 내용의 스냅샷을 확인 창에 표시한다. 변경 버튼을 누르는
것만으로 요청하지 않으며 비밀번호를 입력하고 `확인 후 실행`을 눌러야 전송한다.
취소하면 검토 사유·카테고리 초안은 유지한다. 계정 권한 관리의 기존 재인증 폼은 유지한다.

비밀번호는 확인 창의 일시적인 입력과 해당 요청에서만 사용한다. 제출 직후 입력을 비우고
창을 닫으며, 취소·Escape·오프라인·계정/화면/프로필 전환·세션 종료·창 컴포넌트 종료 시
대기 중 확인을 폐기한다. 저장소 변경 이벤트도 취소로 처리한다. 오프라인 대기열이나
IndexedDB/localStorage에 저장하지 않는다. 실패 후 재시도할 때도 빈 입력에서 시작한다.
로그인 성공 시 기존 로그인 비밀번호 입력도 비운다.

네이티브 modal dialog가 배경 조작을 막으며 Tab·Shift+Tab의 처음/끝 경계를 명시적으로
순환시켜 비활성 버튼을 건너뛴다. 시작 시 비밀번호로
포커스를 이동하고 종료 후 원래 버튼이 남아 있으면 포커스를 복원한다. 확인 중에는 변경할
내용을 뒤에서 수정할 수 없고, 다른 로그인으로 바뀐 뒤 도착한 응답은 새 화면에 반영하지 않는다.

## 검증

- `backend/tests/test_reauthentication.py`: 현재 계정/권한 재검사, 잘못된 비밀번호,
  제한 상태·저장소 오류 차단, 새 권한·세션을 만들지 않는 동작.
- `backend/integration_tests/test_account_permissions.py`: UUID 격리 DB와 실제 Bearer 인증으로
  대상 쓰기 3종, 매 작업 필수 입력, 역할/권한 차단, 오류·429 시 데이터 미변경,
  성공 후 제한 초기화·세션 버전 회수·비밀번호 비노출을 확인한다.
- `Reauthentication.test.jsx`, `App.test.jsx`: 확인 창·초안 유지·필수 입력·취소·계정/화면
  전환·오프라인·컴포넌트 종료 및 카드/카테고리 전송 내용을 확인한다.
- `operational-alerts.spec.js`: 실제 공용 카드 승인 흐름에서 키보드 포커스·Escape 취소,
  틀린 비밀번호 403과 대기 수 유지, 빈 입력 재시도·정상 승인까지 검사한다.
  이 시험의 계정·비밀번호·카드는 개발용 합성 데이터이며 운영 자격 증명을 사용하지 않는다.

구현 판단은 [OWASP 민감 기능 재인증](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html),
[OWASP 거래 승인](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)을
참고했다. 비밀번호 재확인을 더 강한 별도 거래 인증과 동일시하지 않는다.

### 2026-10-19 로컬 검증 결과

- 백엔드 단위 307개, UUID 격리 MongoDB 통합 53개 통과.
- 프런트엔드 Node 단위 95개·React 컴포넌트 58개, 총 153개 통과. 초기 브라우저 검사의
  역방향 Tab 경계를 보완한 뒤 컴포넌트 전체를 다시 실행했다.
- 포커스 보완 후 실제 재인증 브라우저 집중 검사 1개와 최종 프로덕션 빌드,
  Windows Chrome·로컬 스택의 전체 브라우저 E2E 30개를 단일 worker로 통과했다.
- Docker 엔진을 시작하고 기존 이미지·데이터를 유지해 로컬 개발 스택을 재기동했다.
  HTTP 서비스와 MongoDB 포트는 `127.0.0.1` 바인딩이며 운영 배포·외부 공개는 하지 않았다.
- 실제 계정의 운영 권한·접근 만료·책임자 설정과 이미지 자산은 변경하지 않았다.
  원격 CI 성공은 이 변경의 push/PR 이후 별도로 확인해야 한다.
