# 운영 권한 관리

## 책임자와 최소 인원

공용 카드·카테고리를 운영하는 `content_manage`와 운영 권한을 부여하는 책임자를
분리한다. 기존 AAC 사용자·보호자·담당자 역할은 유지하며 새 관리자 역할은 만들지 않는다.

- 책임자는 서버 환경 변수 `ACCOUNT_PERMISSION_MANAGER_IDS`에 명시한 **기존 담당자 계정 ID**다.
  쉼표로 여러 ID를 지정할 수 있고 공백은 제거한다. 사용자명·이름 부분 일치는 허용하지 않는다.
- 기본값은 비어 있다. 설정하지 않으면 관리 메뉴를 표시하지 않고 관리 API도 403으로 차단한다.
  기존 `admin`이나 `content_manage` 보유자에게 이 권한을 자동 부여하지 않는다.
- 권한 관리 기능을 사용하려면 유효한 담당자 책임자 최소 1명을 지정한다. 교대·복구를 위한
  별도 대체 책임자도 권장한다. 책임자 지정·교체는 승인된 서버 설정 변경 절차로만 수행한다.
  API로 책임자 목록·역할을 변경할 수 없으므로 API 호출로 마지막 책임자를 제거할 수 없다.
- 설정에 포함된 책임자는 계정 비활성화·만료 지정도 거절한다(자신과 다른 책임자 모두).
  책임자 교체 시 승인된 대체자의 활성·로그인 가능 상태부터 확인하고 서버 설정에서 이전
  책임자 지정을 제거한 뒤 접근을 회수한다. 이미 잘못 차단된 책임자 복구에는 다른 유효한
  책임자와 승인된 설정 변경이 필요하다. 기본 설정을 자동으로 켜거나 실제 책임자를 지정하지 않는다.
- 콘텐츠 운영 담당자는 일시적으로 0명일 수 있다. 이때 공용 검수·수정은 중단되지만
  기본 의사소통은 유지되며 책임자가 다시 운영 담당자를 지정한다. 이 정책은 책임자와
  콘텐츠 운영 담당자를 같은 인원으로 세지 않는다.
- 아동 연결·개인 이미지·의사소통·학습 기록의 열람 권한은 추가하지 않는다.

이 작업에서는 실제 계정의 책임자 지정이나 운영 권한 부여·회수·비활성화·만료 변경을 실행하지 않았다.
실제 책임자·대체자 승인과 운영 배포 검사 연동은 별도 운영 준비 항목이다.

## 활성화와 화면

승인한 기존 담당자의 정확한 계정 ID를 확인한 뒤 로컬 호스트 환경에 지정한다.
다음은 자리표시자 예시이며 그대로 실행하지 않는다.

```powershell
$env:ACCOUNT_PERMISSION_MANAGER_IDS = '<승인된 담당자 계정 ID>'
docker compose up -d backend
```

컨테이너 환경 변수 변경은 소스 자동 재시작만으로 반영되지 않으므로 backend 재생성이
필요하다. 실제 세션 진행 중 재생성하지 않는다. HTTPS·비밀키·DB 인증을 갖춘 운영 환경을
이 명령으로 구성했다는 뜻은 아니다. 개발용 데모 비밀번호로 외부 서비스를 운영하지 않는다.

책임자로 다시 로그인하면 `운영 권한 관리` 메뉴가 표시된다. 대상 담당자 아이디를 정확히
조회하고 현재 권한·버전을 확인한 뒤, 변경 사유와 **책임자 자신의 비밀번호**로 변경한다.
계정 전체 목록이나 아동 계정을 조회하는 화면은 제공하지 않는다. 비밀번호를 저장·캐시하거나
감사 기록에 넣지 않으며 제출 즉시 입력칸을 비운다. 오프라인·화면 종료 시 조회 상태도 폐기한다.

## API와 세션

| 경로 | 동작 |
|---|---|
| `GET /api/admin/accounts/lookup?username=...` | 담당자 ID·아이디·이름·콘텐츠 권한·버전·활성/만료·책임자 보호 여부 조회 |
| `PUT /api/admin/accounts/{id}/content-permission` | `content_manage`, `expected_revision`, `password`, `reason`으로 변경 |
| `PUT /api/admin/accounts/{id}/access` | `account_active`, `access_expires_at`, `expected_revision`, `password`, `reason`으로 접근 변경 |
| `GET /api/admin/accounts/{id}/permission-audit` | 대상 운영 권한 변경 시도 최근 50건 조회 |

관리 API의 정상·오류 응답은 `Cache-Control: no-store`이며 인증된 책임자만 호출한다.
쓰기 요청은 알 수 없는 필드·문자열 boolean·음수/boolean 버전·공백 사유를 거절한다.
비밀번호 재확인 실패는 별도 `account-permission:` 계정/IP 키로 기존 실패 제한을 사용한다.
MFA나 독립적인 강한 거래 인증을 구현한 것은 아니다.

동일한 `expected_revision`의 동시 변경은 한 번만 반영하고 다른 요청은 409로 차단한다.
현재와 같은 권한 요청은 변경·세션 버전 증가·감사 이벤트 생성 없이 응답한다.
기존 알 수 없는 계정 권한은 삭제하지 않고 `content_manage`만 변경한다.

권한 변경과 `permission_revision` 증가를 같은 사용자 문서에서 원자적으로 반영한다.
모든 인증 요청은 세션의 버전과 현재 계정 버전을 비교하므로 대상의 기존 모든 세션은
다음 요청부터 401이다. 회수 후 재부여해도 이전 세션이 되살아나지 않는다.
누락 버전은 기존 호환용 0이며 잘못된 버전은 허용하지 않는다. 만료 세션 자료 자체는 기존 TTL로
정리한다. 이미 권한 확인을 마친 진행 중 요청을 강제 중단하거나 다른 기기 화면을 푸시로
닫지는 않는다. 대상 기기에서 다시 로그인해야 하며 자기 권한 변경 시 관리 화면도 로그아웃한다.
데모 계정 동기화는 기존 계정의 변경한 운영 권한을 덮어쓰지 않는다.

## 담당자 비활성화·접근 만료

이 관리 기능은 `support_staff` 계정만 대상으로 한다. 아동·보호자 계정, 아동별 연결의
기간·권한·기관 소속을 이 API로 변경하지 않는다. A2-03의 기관 변경 회수 절차는 별도다.

- `account_active` 누락은 true, `access_expires_at` 누락/null은 기한 없음이다.
  잘못된 DB 값은 허용하지 않고 503으로 차단한다. 기존 계정 일괄 수정은 필요하지 않다.
- 비활성화는 새 로그인과 기존 토큰의 다음 인증 요청을 차단한다. 로그인 오류는 잘못된
  비밀번호와 같은 일반 401로 반환해 상태를 노출하지 않는다. 계정·아동 연결·기록은 삭제하지 않는다.
- 만료 시각은 시간대가 있는 미래 시각만 받으며 UTC·밀리초 정밀도로 저장한다.
  화면의 입력·표시는 기기 현지 시간이다. 서버 시계가 만료 시각 이상이면 거절한다.
  UTC로 읽히는 MongoDB naive datetime도 처리하며 신규 세션은 만료 시각까지로 제한한다.
- 만료는 요청 시 검사하므로 예약 작업·TTL 삭제 지연과 무관하다. 기존 세션 삭제나 만료 시점의
  감사 이벤트를 예약하는 기능은 아니다. 설정 변경 전후만 기존 감사 컬렉션에 기록한다.
- 활성 변경·기한 설정/연장/해제는 운영 권한과 같은 버전/CAS·재인증·실패 제한을 사용한다.
  실제 변경은 기존 세션 전부를 무효화한다. 재활성화·기한 해제 후에도 새 로그인해야 한다.
- 비활성/만료 상태에는 콘텐츠 운영 권한을 부여할 수 없지만 기존 권한 회수는 가능하다.
  재활성화는 기존 콘텐츠 권한·아동 연결을 보존한다. 책임자는 재활성화 전 이 권한을 검토하고
  필요하면 별도 연결 권한 관리로 회수해야 한다. 이를 기관 이동 자동 회수로 간주하지 않는다.
- 지원자 화면은 현재 토큰의 인증 요청이 401이면 서버 로그아웃 응답을 기다리지 않고
  지원 자료를 비우고 로그인 화면으로 이동한다. 과거 토큰의 지연 응답이나 로그인 실패는
  새 세션을 종료하지 않는다. AAC 사용자의 오프라인 의사소통 보드는 이 이벤트로 삭제하지 않는다.
  푸시·주기적 감시가 없으므로 요청 전 화면이나 이미 진행 중인 요청을 원격 취소하지 않는다.

## 감사와 불확실한 결과

별도 `account_permission_audit_logs`에 처리자·대상 ID, 변경 전후 값과 버전,
사유·시각·처리 상태를 저장한다. 아동 자료·토큰·비밀번호·해시는 포함하지 않는다.
`action=content_permission`은 전후 boolean, `action=account_access`는 전후
`{account_active, access_expires_at}`를 저장한다. 기존 action 없는 기록은 콘텐츠 권한으로 표시한다.
기존 스키마 버전 1에 선택 필드를 추가하며 기존 감사 기록·체크포인트는 수정하지 않는다.

1. 감사 의도 `prepared` 저장에 실패하면 계정은 변경하지 않는다.
2. 버전·권한 비교 조건이 맞을 때만 권한·버전·`last_account_permission_change`를 한 번에 갱신한다.
3. 감사 상태를 `applied` 또는 `conflict`로 확정한다.

MongoDB 독립 실행 구성을 지원하며 두 컬렉션 사이 트랜잭션은 사용하지 않는다.
통신 단절·확정 실패의 503이나 `prepared`는 **롤백·미반영을 뜻하지 않는다**. 자동 재전송하지
말고 대상의 현재 버전·권한과 감사 ID를 재조회한다. 최신 변경 ID는 대상 계정에도 남는다.
불확실한 기록을 임의로 성공/실패로 수정하거나 정리하지 말고 승인된 유지보수 절차로 대조한다.
자동 재조정·불변 외부 보관·기록 푸시 경보는 별도 작업이다.

새 감사 컬렉션도 [감사 보관·무결성 도구](AUDIT_RETENTION_INTEGRITY.md)의 대상이다.
기존 네 컬렉션 체크포인트는 기존 범위만 검증하고 `verified_legacy_scope`와 제외 컬렉션을
반환한다. 이를 새 컬렉션 정리의 승인 근거로 사용할 수 없고, 전체 다섯 컬렉션의 새 서명이
필요하다. 기존 서명 파일을 수정하거나 실제 감사 로그를 이번 개발에서 정리하지 않는다.

구현 판단의 근거는 [MongoDB 단일 문서 원자성과 조건부 갱신](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/),
[OWASP 민감 기능 재인증](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)이다.
계정 변경 시 세션을 다시 검증하는 기준은
[OWASP 세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)를 참고한다.

- `backend/integration_tests/test_account_permissions.py`: 실제 인증·격리 MongoDB의 역할 차단, 재인증 제한,
  동시 수정, 권한 부여·회수·재부여·기존 세션 차단·데모 동기화 유지.
- React 관리 화면과 App 메뉴 테스트: 입력·사유·버전·비밀번호 비보관, 오류 후 재조회,
  자기 변경·세션 만료·오프라인 전환·늦은 응답 차단.
- 접근 검사 단위·실제 MongoDB 통합 테스트: 기존 필드 호환, UTC/만료 경계, 차단·재활성화,
  세션 기간 제한·과거 토큰 재사용 차단, 책임자 잠금 방지, 콘텐츠 변경과의 동시 충돌,
  감사/쓰기/확정 실패·데모 동기화 보존. React 테스트는 기기 현지 시각 변환·기한 해제도 확인한다.
- 새 권한 관리 화면과 설정을 연결한 실제 책임자 브라우저 승인 검수는 별도다.
  기존 역할·의사소통·학습 E2E 통과를 새 관리 흐름의 실제 운영 승인으로 취급하지 않는다.
- 공용 콘텐츠 쓰기까지 확대한 [중요 운영 작업 재인증](OPERATION_REAUTHENTICATION.md)은
  작업마다 본인 비밀번호를 확인한다. 이는 MFA·개인정보 작업 전체의 추가 인증은 아니다.
- 책임자 변경의 배포 전 검증과 운영 승인, 별도의 강한 추가 인증은 남아 있다.
  A2-01 전체와 TRACK A 배포 게이트를 완료한 것은 아니다.

### 2026-10-19 접근 관리 구현 시점 검증 결과

다음은 접근 관리 구현 시점의 결과다. 이후 공용 콘텐츠 쓰기까지 확대한 최신 실행 결과는
[중요 운영 작업 재인증](OPERATION_REAUTHENTICATION.md)의 로컬 검증 결과를 따른다.

- 백엔드 전체 단위 테스트 301개, UUID 격리 MongoDB 통합 테스트 48개 통과.
- 프런트엔드 단위 95개·React 컴포넌트 46개, 총 141개와 프로덕션 빌드 통과.
- Windows Chrome·로컬 스택의 기존 브라우저 E2E 30개를 단일 워커로 통과했다.
  세션 만료 전 시작한 지원 조회의 늦은 성공/401 응답이 새 로그인 화면을 덮어쓰지 않는
  React 회귀 검사를 추가한 최종 코드로 브라우저 전체를 재실행했다.
- 새 운영 권한 API는 합성 계정·별도 DB의 실제 인증으로, 새 관리 화면은 React 테스트로
  검증했다. 실제 책임자 설정을 켠 관리 화면 브라우저 검수나 운영 승인은 수행하지 않았다.
- 실제 계정의 운영 권한·책임자 설정·감사 서명/보관 정리를 변경하지 않았다.
