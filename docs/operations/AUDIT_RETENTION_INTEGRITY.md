# 감사 로그 보관과 무결성 검증

## 현재 범위와 보관 기준

`python -m app.audit`는 로컬/승인된 유지보수 환경에서 명시적으로 실행하는 CLI다.
앱 시작·로그인·일반 API가 자동으로 서명하거나 기간 만료 자료를 지우지 않는다.
감사 로그는 기존 생성 경로에서 insert하고, 일반 수정/삭제 API는 제공하지 않는다.
운영 권한 변경의 의도 로그만 내부 변경 절차가 `prepared`에서 `applied`/`conflict`로 확정한다.
개인정보 삭제와 아래 승인된 보관 정리는 명시적 삭제 예외다.

| 대상 | 담긴 내용 | 보관·삭제 기준 |
|---|---|---|
| `privacy_audit_logs` | 지원 연결·권한 변경, 본인 삭제 완료 기록 | 승인된 감사 보관 기간. 본인 삭제 시 과거 이력을 지우고 최소 삭제 완료 기록 1건 생성 |
| `board_audit_logs` | 카드판 변경 전후 값·revision | 승인된 감사 보관 기간 또는 본인 데이터 삭제 |
| `learning_audit_logs` | 학습 설정 변경 전후 값 | 승인된 감사 보관 기간 또는 본인 데이터 삭제 |
| `card_audit_logs` | 카드 처리·검수 이력 | 승인된 감사 보관 기간 또는 소유 카드의 본인 데이터 삭제 |
| `account_permission_audit_logs` | 담당자 운영 권한 변경 의도·전후 값·처리 결과 | 승인된 감사 보관 기간. 불확실한 prepared 결과는 먼저 대조하고 정리를 승인 |

정리 기간은 `--days 30`, `90`, `365`, `1095` 중 **운영자가 승인받아 명시한 값**만
사용한다. 기본 기간은 없으며 일괄 적용 시 위 다섯 컬렉션에 같은 기간을 사용한다.
이 선택지는 기존 앱의 기간 표현과 맞춘 기술 옵션이지 법정 보관 기간의 결정이 아니다.
기관별 기간·목적·삭제 처리 기한·정기 실행 주기는 PRIVACY·LEAD가 운영 전 확정해야 한다.
현재 설치에서는 자동 정리/스케줄러/감사 TTL을 켜지 않았다. 실행하지 않으면 기간만으로
삭제되지 않으므로, 문서 작성만으로 주기적 보관 관리가 운영된다고 취급하지 않는다.

사용자 개인정보 화면의 `retention_days`는 기존 의사소통·학습 이용 기록 설정이고
이 전체 감사 정리 명령의 권한/일정/기간을 자동으로 결정하지 않는다. 명령은 문장·학습
시도·연결 상태·계정·개인정보 설정을 정리 대상으로 삼지 않는다. 삭제 완료 시각은 기존
`privacy_settings`에도 남으며 계정 폐기·백업 삭제는 별도 정책이 필요하다.

새 `audit_retention_scan`은 일반 조회 인덱스다. 자동 삭제 TTL은 추가하지 않았다.
MongoDB TTL은 만료 후보를 백그라운드에서 삭제하므로 승인·백업 없이 기존 컬렉션에
설치하지 않는다. [MongoDB TTL 동작](https://www.mongodb.com/docs/manual/core/index-ttl/)

## 위변조 탐지 방식과 한계

`seal`은 지정 DB의 다섯 컬렉션에서 기준 시각 `through` 이하의 문서를 `_id` 순서로
읽고 BSON 타입을 보존하는 canonical Extended JSON으로 SHA-256 지문을 계산한다.
한 문서씩 처리하며 원문 목록을 파일이나 출력에 복제하지 않는다. 컬렉션별 건수·지문,
DB 이름·기준 시각·seal UUID·키 식별자를 별도 32바이트 비밀키의 HMAC-SHA256으로
인증한다. 서명 비교는 [Python `hmac.compare_digest`](https://docs.python.org/3.12/library/hmac.html)를 사용한다.

2026-10-18 운영 권한 감사 컬렉션을 추가했다. 기존 네 컬렉션의 정상 서명은 기존 범위만
`verified_legacy_scope`로 검증하며 `uncovered_collections`를 반환한다. 이 서명을 다섯 컬렉션
정리에 사용하면 `checkpoint_scope_incomplete`로 차단한다. 원본 서명을 보관하고 전체 범위의
새 체크포인트를 승인된 절차로 생성해야 한다. 기존 서명을 새 범위로 조용히 확장하지 않는다.

- `verify`는 파일의 HMAC·DB 이름·seal ID를 먼저 검사한 뒤 같은 범위의 DB 지문을 비교한다. 문서 수정·삭제·과거 시각의 삽입·컬렉션 이동·기준 시각 밖으로의 날짜 변경을 탐지한다.
- 체크포인트 이후 시각의 정상 신규 로그는 이전 검사의 범위 밖이다. 신규 자료도 보호하려면 승인된 주기로 새 체크포인트를 만든다. 체크포인트 전 이미 일어난 변경의 진실성은 증명하지 못한다.
- 서명 생성은 writer 중단 확인이 필요하고 두 번의 스캔 결과가 같아야 한다. 단일 MongoDB의 원자적 스냅샷이나 DB 잠금을 구현한 것은 아니다. `--writers-stopped`는 운영자의 선언이다.
- 날짜 누락·잘못된 BSON 타입은 조용히 제외하지 않고 차단한다. 서명 시 미래 시각도 차단한다. 최대 50만 문서, 조회별 2초, 두 스캔 전체 클라이언트 제한 30초다. 초과 시 범위를 임의로 줄여 성공 처리하지 않는다.
- 서명 파일에는 사용자 ID·행 ID·변경 전후 값·이유·이미지·키 원문이 없다. 지문·건수·DB 이름도 운영 메타데이터이며 완전한 익명 자료라고 가정하지 않는다.
- 개인정보 삭제·승인된 보관 정리·명시적 schema 마이그레이션도 이전 지문과 불일치를 만든다. **불일치는 변경 탐지이지 불법 변조 확정이 아니다.** 이전 파일을 수정하지 말고 승인된 작업 증거와 새 기준선을 함께 남긴다.
- 앱은 DB의 감사 문서를 물리적으로 불변으로 만들지 않는다. DB 관리자 쓰기를 막는 최소 권한 계정·WORM/불변 저장소·외부 체크포인트 등록·자동 검증 알림은 미구현이다.
- 비밀키와 신뢰하는 체크포인트 식별 기록이 DB 관리자에게서 분리돼 있어야 의미가 있다. 호스트/서명 프로세스/키까지 침해되면 방어하지 못하며 파일 삭제·과거 파일로의 통째 교체는 별도 외부 보관·ID 기록으로 막아야 한다. DB에 파일과 키를 같이 넣지 않는다.

## 키와 파일 준비

키·체크포인트는 일반 API나 backend 상시 서비스에 넣지 않고 **유지보수 일회용 CLI에만**
읽기/쓰기 접근을 부여한다. 저장 위치 `AUDIT_STORE_DIR`는 심볼릭 링크/정션이 없는
절대 경로이며 마지막 디렉터리 이름이 `.local-audit`여야 한다. 이 이름은 Git 제외다.
외부 key 파일 경로는 `AUDIT_HMAC_KEY_FILE`로만 주고 명령행/화면/문서에 키를 넣지 않는다.

backend 의존성이 있는 Python 환경, backend 디렉터리에서 실행하는 형식 예시다.
자리표시자를 승인된 실제 경로로 바꾸기 전 실행하지 않는다.

```powershell
$env:AUDIT_STORE_DIR = '<승인된 절대 경로>\.local-audit'
python -m app.audit keygen
python -m app.audit keygen --apply
$env:AUDIT_HMAC_KEY_FILE = Join-Path $env:AUDIT_STORE_DIR 'signing.key'
```

`keygen` 기본은 계획뿐이며 `--apply`는 OS 난수로 새 키를 만든다. 키/파일은 독점
생성하고 기존 것을 덮어쓰지 않는다. POSIX 파일 모드 600·디렉터리 700을 요청하지만
Windows ACL·디스크 암호화·접근자/대체자·키 백업은 담당자가 별도 확인해야 한다.
새 설치 키를 실제 사용자 DB용으로 이번 개발에서 만들지 않았다. 테스트용 임시 키만 사용했다.

Compose를 사용하는 경우 **저장 디렉터리를 호스트에 영구 마운트한 일회용 프로세스**에서
실행해야 한다. 기본 backend 컨테이너는 이 키/디렉터리를 마운트하지 않는다. 예를 들어
승인된 호스트 `.local-audit`를 `/app/.local-audit`로 연결하고 `AUDIT_STORE_DIR` 및
`AUDIT_HMAC_KEY_FILE=/app/.local-audit/signing.key`를 전달한다. 저장 없이 `run --rm`으로
생성한 키/체크포인트는 컨테이너 종료 시 사라질 수 있으므로 운영 증거로 사용하지 않는다.
실제 Compose 파일 조합·DB 환경·읽기/쓰기 마운트 권한을 따로 검토한다.

키 교체는 새 승인된 저장 위치에서 새 키를 생성해 이후 서명에 사용한다. 과거 체크포인트
검증에는 과거 키가 필요하므로 해당 키의 접근 제한·보존 기간도 함께 관리한다. 도구는
키를 DB에 저장하거나 자동 교체/폐기하지 않으며 고정 예시 키나 랜덤 임시 키로 대체하지 않는다.

## 서명·검증과 승인된 보관 정리

1. TECH·PRIVACY·LEAD가 DB, 감사 목적/기간, 영향, 유지보수 시간, 접근자와 실행자를 승인한다. 다른 writer·정리 프로세스·수동 변경을 멈춘다. 기기의 문장·대기열을 지우지 않는다.
2. [마이그레이션 백업·격리 복구](MIGRATION_BACKUP_RECOVERY.md)에 따라 유효한 백업과 복원 검증을 확보한다. 개인 삭제 데이터가 든 백업을 무작정 재적용하지 않는다.
3. 서명을 만들고 `verify`가 통과하는지 확인한다. 기존 서명이 불일치하면 원인 확인 없이 새 파일로 덮어 문제를 감추지 않는다.
4. 기간을 명시한 기본 정리 계획에서 컬렉션별 후보 수를 검토한다. `created_at < 현재 UTC - days`만 후보이며 정확한 경계 시각의 행은 보존한다.
5. 단 하나의 승인된 `--apply` 프로세스를 실행한다. `--backup-ref`는 복원 확인된 백업의 불투명한 참조 코드이며 도구가 실제 백업 파일을 자동 확인하지는 않는다.
6. 완료 후 새 서명을 검증하고 삭제 수·이전/의도/새 seal ID·백업 참조·승인을 제한된 기록에 남긴다. 기존 파일을 덮어쓰거나 지우지 않는다.

```powershell
$auditDb = '<승인된 DB 이름>'
python -m app.audit seal --database $auditDb
python -m app.audit seal --database $auditDb --apply --confirm-database $auditDb --writers-stopped
$auditSeal = '<반환된 seal_id>'
python -m app.audit verify --database $auditDb --seal-id $auditSeal
$auditDays = 90 # 형식 예시일 뿐, 실제 승인된 기간으로 변경
python -m app.audit retain --database $auditDb --days $auditDays
$auditBackupRef = '<복원 확인된 backup_id>'
python -m app.audit retain --database $auditDb --days $auditDays --apply --confirm-database $auditDb --writers-stopped --backup-ref $auditBackupRef --seal-id $auditSeal
```

DB는 항상 명시하고 `admin/config/local`과 임의 namespace를 허용하지 않는다.
apply는 대상 이름 일치·writer 중단·백업 참조·인증된 사전 seal이 모두 필요하다.
기준 seal이 삭제 cutoff보다 오래되었으면 적용하지 않는다. 기본 batch 500·최대 1000,
max-batches 1000·최대 10000이며 총 예상 묶음 수가 상한을 넘으면 삭제 전에 차단한다.
각 묶음은 `_id`만 읽고 삭제 시에도 날짜 조건을 다시 검사하며 클라이언트 제한 10초를 둔다.

삭제 전 `retention_intent` 서명을 먼저 파일에 기록하므로 파일 기록 실패 시 삭제를
시작하지 않는다. 완료 후 `retention` 서명에 기간·cutoff·실제 삭제 수·백업 참조·이전/의도
seal ID를 넣어 인증한다. 모두 삭제된 경우에도 0건의 서명된 완료 증거가 생긴다.
오류는 고정 코드와 확인 가능한 삭제 건수·intent ID만 출력한다. 부분 실패·응답 유실은
자동 취소하지 않으며 실제 반영 수가 불확실할 수도 있다. writer를 닫은 채 intent·원본
서명·DB·백업을 보존하고 원인을 검토한 뒤 승인된 새 기준선/재시도를 준비한다.
도구에는 분산 잠금·무중단 정리·자동 잠금 해제·자동 백업 복원이 없다.

종료 코드 0은 계획/서명/검증/완료 중 본문 `mode`·`status`를 함께 확인한다. 실패 1,
인자 오류 2다. 감사 내용이나 키의 원문을 오류/서버 로그로 내보내지 않는다.

## 삭제와 연결 상태 보존

본인 데이터 삭제는 과거 `privacy_audit_logs`를 사용자 범위로 지우고 새 최소
`personal_data_deleted` 한 건을 남긴다. 다른 사용자의 감사 이력은 유지한다.
보드·학습·소유 카드 감사 삭제도 기존 범위를 유지한다. 법적 보존/분쟁 보존 예외를
구현하거나 확정한 것은 아니므로 실제 적용 전 별도 검토가 필요하다.

데모 초기화는 이미 있는 연결을 수정하지 않고, 최초 연결도 `$setOnInsert`만 쓴다.
권한 회수 이력이 기간 정리로 사라져도 비활성 연결을 되살리거나 사용자별로 축소한
권한을 기본값으로 덮어쓰지 않는다. 운영에서도 권한 상태는 감사 로그 보존에 의존하지 않는다.

## 검증과 운영 미완료 범위

`backend/tests/test_audit.py`는 확인 인자·기간·경로·키·HMAC·파일 변조·날짜·상한·
기본 무변경·오류 비노출·비 TTL 인덱스를 검증한다. 실제 MongoDB의
`backend/integration_tests/test_audit.py`는 5개 컬렉션의 legacy/Binary/Int64와 기존 4개 범위 서명 호환,
수정·누락·과거 삽입·컬렉션 이동, 경계 시각 보존·0건 완료·재실행·부분 실패,
권한 회수 유지·다른 사용자 개인정보 이력 보존을 확인한다. 각 시험은 자기 소유
