# 인증 MongoDB와 DB별 앱 계정

2026-10-20 A2-02 첫 개발 단위로 독립적인 `compose.secure-db.yaml` 구성을 추가했다.
기본 `compose.yaml`의 개발용 무인증 DB·볼륨은 그대로 유지한다. 이 구성을 기존 파일에
`-f`로 합치거나 기존 데이터 볼륨에 연결하지 않는다. 실제 운영 전환·데이터 이전은 수행하지 않았다.

## 연결과 권한

| 대상 | 범위 |
|---|---|
| MongoDB | 인증 필수, 호스트 포트 없음, 내부 DB 네트워크만 연결 |
| 앱 DB 사용자 | 해당 DB의 `readWrite` 한 역할, `SCRAM-SHA-256` 인증 |
| 관리 사용자 | MongoDB 초기 설정용 `admin`의 root, 백엔드에 자격 증명 미전달 |
| 백엔드 | 앱 사용자/비밀번호 파일만 마운트, API `127.0.0.1:8001`, 데모 생성·외부 모델 비활성 |
| 데이터 | 별도 프로젝트의 `mongodb_secure_data` 볼륨, 기존 `mongodb_data` 미사용 |

`readWrite`는 앱의 CRUD·인덱스 생성에 필요한 DB 단위 권한이다. 해당 DB 안의 컬렉션 전체를
읽고 변경·삭제할 수 있으며 컬렉션별로 더 세분화한 역할이나 감사 불변성을 구현한 것은 아니다.
다른 DB에 대한 읽기/쓰기와 사용자 관리 권한은 주지 않는다. 백업·복구·DB 사용자 관리는
별도의 승인된 운영 계정/도구로 수행한다. 관리 비밀번호를 앱 연결에 재사용하지 않는다.

이 구성에는 웹 프런트엔드·HTTPS 게이트웨이가 없다. HTTP API는 로컬 검증용이다.
운영 전체 구성, 내부 DB 연결의 TLS, OS/컨테이너 계정 강화, 비밀 관리 서비스와 보안 승인까지
완료한 것이 아니며 인터넷에 공개하지 않는다. 앱 계정 역할과 MongoDB 계정 역할도 별개다.

## 파일 기반 설정

승인된 비밀 저장소에서 다음 네 파일을 준비한다. 비밀번호 원문을 코드·Compose 본문·URI·
명령 인수·CI 자격 증명에 넣지 않는다. 저장소 밖의 접근 제한 디렉터리를 권장한다.
로컬 Compose의 file secret은 파일 마운트이며 파일 자체의 암호화나 자동 교체를 제공하지 않는다.
호스트 ACL·디스크 보호·백업 접근 통제는 별도로 적용한다.

| 파일명 | 규칙 |
|---|---|
| `mongodb_root_username` | 영문 시작, 영문/숫자/`_`/`-` 3~64자, 앱 사용자와 다름 |
| `mongodb_root_password` | 공백 없는 ASCII 가시 문자 32~256자, 앱 비밀번호와 다름 |
| `mongodb_app_username` | 영문 시작, 영문/숫자/`_`/`-` 3~64자, root/admin 금지 |
| `mongodb_app_password` | 공백 없는 ASCII 가시 문자 32~256자, 암호학적 난수 권장 |

앱 파일은 ASCII, 끝의 CR/LF는 제거한다. 1,024바이트 초과·내부 개행·빈 값·잘못된 파일을
거절한다. 관리용 두 파일은 공식 이미지 초기화 도구와의 해석 차이를 막기 위해 BOM·CR/LF가
없는 단일 값이어야 한다. 예제용 고정 비밀번호는 제공하지 않는다. 아래는 승인된 신규 환경용 자리표시자다.

```powershell
$env:PESC_SECURE_SECRETS_DIR = '<승인된 네 파일이 있는 절대 경로>'
$env:SECURE_MONGODB_DATABASE = '<새 앱 데이터베이스 이름>'
docker compose -f compose.secure-db.yaml up -d --build --wait
```

기본 프로젝트 이름은 `pesc-mate-secure`, DB 기본값은 `pesc_mate_secure`다.
`SECURE_BACKEND_PORT` 기본 8001은 항상 loopback에만 연결한다. 앱 DB 이름은 ASCII 영문/
숫자/`_`/`-` 1~63자이며 첫 글자로 `-`는 허용하지 않는다. admin/config/local은 금지한다.
기본 개발 스택은 기존 `docker compose up` 방식으로 사용하며 자동으로 인증 구성으로 바뀌지 않는다.

정상 종료는 **같은 프로젝트·파일**로 `docker compose -f compose.secure-db.yaml down`을 사용한다.
실제 데이터가 있는 환경에서는 `down --volumes`를 실행하지 않는다.

## 백엔드 설정과 오류 차단

`MONGODB_REQUIRE_AUTH=true`, `MONGODB_HOST`, `MONGODB_DATABASE`,
`MONGODB_USERNAME_FILE`, `MONGODB_PASSWORD_FILE`을 지정한다. 포트는 `MONGODB_PORT`
(기본 27017)이며 이 모드는 단일 호스트/IPv4 연결이다. authSource는 대상 DB와 같아야 한다.
`MONGODB_AUTH_SOURCE`를 명시한다면 DB와 동일해야 하고, 관리 DB로 바꿀 수 없다.

이 모드에서 `MONGODB_URI`도 함께 주면 거절한다. 설정 누락·잘못된 플래그·파일·DB·호스트·
포트는 요청 수신/백그라운드 인덱스 작업 전에 시작을 중단한다. 원문 값은 오류에 넣지 않는다.
각 `_FILE` 변수가 하나라도 있으면 필수 모드 플래그가 없어도 파일 설정 전체를 검증한다.
따라서 파일 오류 때 무인증 URI/localhost로 자동 전환하지 않는다.

드라이버에는 사용자·비밀번호를 별도 인자로 전달하며 비밀번호를 URI에 조합하지 않는다.
프로세스당 연결 풀 캐시는 유지한다. 필수 모드/파일 설정이 없는 기존 개발·통합 검사는 기존
`MONGODB_URI`와 기본 연결 동작을 유지한다. 파일을 교체한 뒤에는 앱 프로세스를 재시작해야 한다.

## 초기 생성·교체·복구 주의사항

초기 사용자 생성은 공식 Mongo 이미지의 **비어 있는 데이터 디렉터리에서만** 실행된다.
기존 데이터 디렉터리에서는 init 스크립트나 파일 교체만으로 DB 사용자/비밀번호가 바뀌지 않는다.
설정이 잘못되면 앱 인증/헬스체크가 실패한다. 기존 볼륨 삭제로 해결하지 않는다.
최초 초기화가 중간 실패하면 일부 DB/관리 사용자만 생성됐을 수 있으며 자동 복구를 보장하지 않는다.

실제 비밀번호 교체는 승인된 관리 계정으로 DB 자격 증명을 변경하고 파일과 앱 재시작 순서를
맞추는 별도 작업이다. 무중단 교체·관리 계정 분실 복구·백업 검증은 이번 자동화 범위가 아니다.
기존 DB 이전은 [백업·격리 복구 절차](MIGRATION_BACKUP_RECOVERY.md)를 검토한 후 별도 승인·
중단 계획·복원 리허설을 거쳐 진행한다. 새 구성 시작을 기존 데이터 이전으로 간주하지 않는다.

## 로컬 자동 검증

Docker Desktop/Engine과 PowerShell 7이 있는 저장소 루트에서 다음을 실행한다.

```powershell
pwsh -NoProfile -File scripts/validate-authenticated-mongodb.ps1
```

이 명령은 운영 자격 증명을 받지 않는다. 매번 난수 비밀번호, UUID 프로젝트/DB/볼륨,
임의 loopback 포트를 사용한다. 임시 파일은 Git 제외된 `.local-security-tests/auth-<UUID>`에
만들며 Windows는 현재 사용자와 SYSTEM의 ACL, Linux는 700 디렉터리/600 파일을 적용한다.
비밀번호 내용은 출력하지 않는다. 앱 이미지에는 비밀 디렉터리를 빌드 컨텍스트로 전달하지 않는다.

실제 서버에서 정상 CRUD·모든 인덱스·API 가입/로그인, 정확한 DB별 역할과 root 파일 미전달,
무인증 접속·잘못된 비밀번호·다른 DB 쓰기·사용자 관리 차단을 검증한다.
일반 `backend/integration_tests`는 기존 로컬/CI DB의 UUID 격리 검증이며 인증 DB 경계를 대신하지 않는다.

종료 시 자기 프로젝트 라벨의 테스트 볼륨과 정확한 임시 디렉터리만 확인해 삭제한다.
이는 테스트 DB/자격 증명의 의도적인 폐기이며 복구하지 않는다. 빌드 이미지/캐시는 남는다.
정리에 실패하면 자격 증명을 보존하고 해당 UUID 프로젝트의 수동 검토를 안내한다.
실제 운영 프로젝트·기존 개발 볼륨·실제 사용자는 정리 대상으로 선택하지 않는다.

2026-10-20 사용자 요청으로 `Authenticated MongoDB boundaries`를 포함한 원격 CI
워크플로우를 제거했다. 같은 검증은 로컬 `npm run verify:security`로 직접 실행한다.
초기화 정책 Node 테스트는 역할·자격 증명 재사용·관리 파일의 CRLF 차단·안전한 오류를 확인한다.
이 검증 스크립트와 초기화 정책 테스트는 삭제하지 않았다. 과거 CI 오류의 원인을 수정하거나
원격 실행이 성공했다고 간주하지 않으며, 아래 실행 결과는 당시의 로컬 검증 기록이다.

구성 근거는 [Mongo 공식 이미지의 초기화와 파일 자격 증명](https://hub.docker.com/_/mongo),
[MongoDB 기본 역할](https://www.mongodb.com/docs/manual/reference/built-in-roles/),
[Compose file secrets](https://docs.docker.com/compose/how-tos/use-secrets/)다.

## 2026-10-20 로컬 실행 결과

- 백엔드 전체 단위 318개, 기존 UUID 격리 MongoDB 통합 53개 통과.
- 독립 인증 DB 검증 7개와 초기화 정책 Node 테스트 4개 통과. 실제 인증 DB 검증은
  관리 파일 줄바꿈 규칙·전체 인덱스·정리 경로 보호를 반영한 최종 구성으로 재실행했다.
- 기존 재연결 동기화 중복 호출을 별도 수정하고 프런트엔드 단위 95개·React 컴포넌트
  60개(총 155개)와 프로덕션 빌드를 통과했다. 실패했던 브라우저 흐름은 3회 연속 통과했다.
- 수정 후 기존 로컬 스택의 전체 브라우저 30개도 통과했다. 이는 기존 모드의 호환성 회귀
  검사이며, 새 인증 DB 경계는 앞의 별도 인증 DB 테스트 7개로 검증했다.
- 각 인증 검증의 임시 컨테이너·볼륨·자격 증명은 종료 후 정리했고 기존 개발 DB는 유지했다.
- Windows 로컬 실행 결과다. 새 CI 작업의 원격 Ubuntu 결과, 실제 운영 전환·기존 데이터
  이전·운영 자격 증명 교체는 실행하지 않았다. 이미지 자산도 변경하지 않았다.
