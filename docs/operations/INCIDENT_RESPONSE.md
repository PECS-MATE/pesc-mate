# 장애 대응 절차와 연락 체계

> 적용: 현재 로컬 개발·신뢰된 사설망 검수 환경. 문서 기준일: 2026-10-17.
> 절차 문서화 완료와 실제 현장 대응 준비 완료는 다르다. 아래 담당자 지정·연락 시험·
> 장애 모의훈련은 미완료이며, 이를 마치기 전 현장 파일럿 게이트를 통과시키지 않는다.

## 1. 먼저 지킬 원칙

1. 핵심 의사소통을 우선한다. 학습·추천·문장 생성 장애 때문에 카드 선택이나 기본 표현을 막지 않는다.
2. 사용 중인 기기를 무조건 새로고침·로그아웃하지 않는다. 작성 중 문장과 기기 대기 기록이 있을 수 있다.
3. 화면에 남은 그림·텍스트, 준비된 기본 음성이나 사전에 확인한 실물 카드 등 익숙한 대안을 제공한다. 현장 진행자가 지원 가능 여부를 확인하고 무리한 사용을 중단한다.
4. 원인을 확인하기 전에 DB·볼륨·사이트 데이터를 지우지 않는다. 같은 UUID의 재전송 원칙을 유지한다.
5. 확인하지 못한 출처와 표본이 없는 지표를 정상으로 판단하지 않는다. 요청 ID와 실제 영향 범위를 함께 확인한다.

## 2. 장애 등급

영향을 기준으로 사람이 잠정 등급을 지정한다. 의심되는 정보 접근·데이터 손상은
확정될 때까지 높은 등급으로 취급한다. 운영 알림의 `info`·`warning`과 장애 등급은 다르다.

| 등급 | 판단 기준·예시 | 현장 조치와 연락 |
|---|---|---|
| SEV1 차단 | 핵심 의사표현이 불가능하고 확인된 대안도 없음, 다른 아동의 기록·개인 이미지 노출 의심, 조용한 데이터 손상·소실 의심 | 영향을 받는 세션 중단, 현장 지원 유지. 기술 담당·대응 총괄 즉시 호출, 정보 접근 문제는 개인정보·보안 담당도 동시 호출 |
| SEV2 높음 | 여러 기기의 로그인·카드 조회·저장 실패, MongoDB 불가, 대기 기록을 계속 전송하지 못하지만 현재 기기의 의사소통 대안은 가능 | 신규 검수 세션 시작 보류, 영향 기기는 검증된 대안만 사용. 기술 담당·대응 총괄 호출 |
| SEV3 부분 | AI 문장 생성만 실패해 규칙·선택 발화 가능, 한 기기의 TTS 문제지만 화면·기본 음성 대안 가능, 검수·운영 지표 일부 조회 불가 | 실패 기능만 피하고 대안을 확인. 운영 담당 접수 후 기술 담당에게 전달 |
| SEV4 대기 | 공용 카드 검수 대기·지연, 우회 가능한 시각 불편 등 현재 핵심 과업에 영향 없음 | 운영 작업으로 등록·담당 배정. 영향이 커지면 즉시 상향 |

`health=degraded`라도 원인을 확인한다. 선택형 AI만 불가하면 보통 SEV3이지만,
같은 시점에 의사표현까지 불가하면 SEV1·SEV2 판단이 우선이다. 반복 실패 알림이
3회 발생했다고 자동으로 SEV1이 되거나, 알림이 없다고 장애가 해소되는 것은 아니다.

## 3. 담당자와 비공개 연락망

실명·전화·개인 이메일·토큰은 저장소나 공개 이슈에 적지 않는다. 운영 책임자가
접근 제한된 연락망에 실제 담당자·주/예비 연락 수단·사용 가능 시간을 등록하고,
현장 진행자에게 기기·서비스 장애 중에도 확인 가능한 방법으로 전달한다.
연락망은 이 앱의 로그인과 운영 알림 화면에만 의존해서는 안 된다.

| 역할 코드 | 책임 | 담당자·대체자 / 연락망 위치 | 연락 시험 |
|---|---|---|---|
| FIELD 현장 진행 | 사용자 지원, 영향 세션 중단, 기기 상태·대안 확인 | 미지정 / 비공개 연락망 미등록 | 미실행 |
| LEAD 대응 총괄 | 등급 확정, 담당 조정, 상황 공유, 재개 승인 | 미지정 / 비공개 연락망 미등록 | 미실행 |
| TECH 기술 담당 | API·DB·기기 경로 진단, 증거 보존, 승인된 수정·재시작 | 미지정 / 비공개 연락망 미등록 | 미실행 |
| OPS 콘텐츠 운영 | 공용 카드 검수, 운영 알림 확인, 검수 대기 정리 | 미지정 / 비공개 연락망 미등록 | 미실행 |
| PRIVACY 개인정보·보안 | 접근 범위·민감 증거 통제, 필요한 별도 검토 조정 | 미지정 / 비공개 연락망 미등록 | 미실행 |

한 사람이 여러 역할을 맡을 수 있으나 사전에 명시하고 대체 연락 경로를 확보한다.
위 표는 계정 역할이나 권한을 자동 부여하지 않는다. `content_manage`만으로 다른
아동의 개인 기록 열람이나 법적 판단 권한이 생기지 않는다.

세션 전 LEAD가 연락망 버전·접근 위치·담당자와 대체자의 사용 가능 시간을 확인한다.
이름과 연락처를 공개 Git에 채우는 대신 비공개 연락망의 문서 식별자와 시험 결과를
승인된 내부 기록에 남긴다. 실제 담당자가 정해지지 않으면 현장 검수를 시작하지 않는다.

### 호출·응답·상향

다음은 파일럿 연락 훈련용 초안 목표이며 서비스 SLA, RTO 또는 24시간 당직 약속이 아니다.
실제 담당자와 운영 시간이 정해진 뒤 수행 가능성을 확인해야 한다.

- SEV1: 발견 즉시 LEAD·TECH에 동시 연락한다. 5분 안에 수신 확인이 없으면 대체자에게 별도 수단으로 연락한다. 개인정보 관련이면 PRIVACY도 동시에 포함한다. 15분마다 또는 영향 변경 즉시 상황을 갱신한다.
- SEV2: 발견 후 15분 안에 LEAD·TECH 수신 확인을 목표로 한다. 응답이 없으면 대체자에게 상향하고, 30분마다 또는 영향 변경 시 갱신한다.
- SEV3·SEV4: 운영 시간 안에 OPS가 접수·담당·다음 확인 시각을 기록한다. 다음 현장 세션 전에 미해결 영향과 우회 방법을 공유한다.
- 연락 실패·운영 시간 밖이라도 안전한 지원을 확인할 수 없다면 영향 세션을 재개하지 않는다. 연락망의 승인된 대체 경로를 사용하며 무응답을 해결로 처리하지 않는다.

수신자는 사고 번호·담당 역할·다음 확인 시각을 답한다. 발신자는 단순 발송이 아니라
수신 확인 여부·시각을 기록한다. 실제 호출·이슈 작성·외부 발송은 담당자가 승인된
채널에서 수행하며, 이 문서나 운영 알림이 자동 발송하지 않는다.

## 4. 초기 확인 순서

1. 발생 시각·시간대, 기기/환경 코드, 실패 과업, 영향 범위, 대안 가능 여부를 기록하고 잠정 등급을 정한다.
2. 재시작 전에 배포 커밋, 컨테이너 실행 상태, 헬스 결과, 필요한 요청 ID·요약 지표를 보존한다. API·동기화 지표는 재시작 시 초기화된다.
3. PC 직접 API → PC 프런트엔드 프록시 → 해당 기기 순서로 비교한다. PC 성공만으로 태블릿 연결이나 음성 성공을 보장하지 않는다.
4. 아래 증상별 절차로 원인을 좁힌다. 개인정보 경계 문제는 재현을 위해 타인의 실제 데이터를 추가 조회하지 않는다.
5. 수정·재시작·권한 변경은 담당자와 승인 범위를 확인한 뒤 수행한다. 결과와 중단 영향을 기록한다.

### 읽기 전용 점검 명령

저장소 루트의 PowerShell에서 실행한다. 아래 주소는 현재 로컬 기본 구성이다.
다른 환경은 승인된 주소·Compose 파일 조합을 확인하고 사용한다. 출력은 공유 전 점검한다.

```powershell
git rev-parse --short HEAD
docker compose ps
curl.exe --silent --show-error --max-time 8 --include http://127.0.0.1:8000/api/health
curl.exe --silent --show-error --max-time 8 --include http://127.0.0.1:5173/api/health
docker compose exec -T mongodb mongosh --quiet --eval 'JSON.stringify({ok:db.adminCommand({ping:1}).ok})'
```

헬스의 HTTP 코드와 본문을 함께 본다. `curl.exe`는 `--fail` 없이 HTTP 503 본문도
출력하므로 종료 코드 0만으로 정상 판정하지 않는다. 연결 오류·시간 초과는 출력과
종료 코드를 별도로 확인한다. DB ping은 연결만 확인하며 데이터 정합성 검증이 아니다.

| 관측 | 의미와 다음 확인 |
|---|---|
| 200 / `ok` | 서버 의존성 준비 상태. 해당 기기에서 핵심 과업은 별도 확인 |
| 200 / `degraded`, `checks.ollama=unavailable` | 선택형 AI 장애. 규칙·선택 발화와 기기 음성 대안 확인 |
| 503 / `unavailable`, `checks.mongodb=unavailable` | 필수 DB 경로 실패. Compose 상태·DB ping 확인, 신규 저장 성공을 약속하지 않음 |
| `checks.tts=client_side` | 서버에서 음성 확인 불가. 기기 음량·한국어 음성·기본 WAV 실제 재생 확인 |
| 직접 API 성공, 프록시 실패 | 프런트엔드 서비스와 내부 프록시 연결 확인 |
| PC 성공, 태블릿 실패 | 같은 사설망·PC 사설 IPv4·검수용 5173 바인딩·비공개망 방화벽 규칙 확인 |
| 운영 알림 200 / `partial` | 출처 일부 조회 불가. 실패 출처를 정상 0건으로 취급하지 않음 |

태블릿용 구성은 `compose.yaml`과 `compose.tablet.yaml`을 함께 사용한다. 점검 명령도
같은 `-f` 조합을 유지한다. API 8000·DB 27018을 외부에 열거나 공용망 방화벽을
해제해 해결하지 않는다. LAN HTTP는 완전 오프라인·PWA 검증 환경이 아니다.

### 요청 추적과 운영 지표

브라우저 Network의 **실패 요청**에서 `X-Request-ID` 또는 오류 본문의
`error.request_id`만 가져온다. 요청 본문·Authorization·Cookie·응답 전체·HAR을 공유하지 않는다.
서버가 처리한 오류는 공통 요청 ID가 붙지만, 서버에 도착하지 않은 통신 실패나
상위 프록시 응답에는 없을 수 있다. 이 경우 없는 ID를 만들어 동일 요청이라고 주장하지 않는다.

```powershell
docker compose logs --since 15m --tail 300 backend | Select-String -SimpleMatch '<확인한 요청 ID>'
```

꺾쇠 부분을 확인한 UUID로 바꾼다. 기본 로그는 요청 ID·경로 템플릿·상태·처리 시간만
포함하지만 주변 시작 로그나 외부 라이브러리 출력은 다를 수 있다. 필요한 줄만 골라
민감 정보 유무를 다시 확인한다. DB CRUD 로그와 MongoDB 내부 로그는 기본 억제를 유지한다.

운영 권한 계정으로 화면의 `운영 알림`과 아래 읽기 전용 API를 확인한다. 토큰을
명령행·문서·스크린샷에 넣지 말고 기존 인증 세션의 Network에서 필요한 수치만 확인한다.

- `/api/admin/alerts`: 출처별 조회 성공 여부, 확인 시각, 대기·반복 실패 알림
- `/api/admin/metrics`: 프로세스별 최근 최대 15분 HTTP 오류·처리 시간
- `/api/admin/tts-metrics?hours=1`: 최근 1시간 요청의 저장된 최종 재생 보고
- `/api/admin/offline-sync-metrics`: 프로세스별 최근 최대 15분 신규·중복·실패·미처리

지표의 분모와 예외는 [운영 알림](../development/OPERATIONAL_ALERTS.md)과 연결된
개별 지표 문서를 따른다. 화면을 닫으면 알림 감시도 멈추며 외부 당직 호출을 대신하지 않는다.

## 5. 증상별 조치와 보호할 상태

| 증상 | 우선 확인·대안 | 하지 않을 조치 |
|---|---|---|
| 로그인 지연·실패 | 실행 상태, DB ping, 요청 ID와 401·403·503 구분. 기존 기기의 확인된 오프라인 대안 확인 | 계정 전체 삭제, 무차별 로그인 반복, 데모 비밀번호로 강제 변경 |
| AI 문장 생성 실패 | Ollama 준비 상태와 규칙 폴백 확인. 선택 카드·텍스트를 유지하고 선택 카드 그대로 발화 | 카드 순서 초기화, 모델 장애만으로 전체 서비스 중단 |
| 기기 음성 실패 | 해당 기기 음량·음성 설정, 저장된 기본 음성·텍스트 확인. 실제 출력은 사람이 확인 | 헬스 200이나 TTS 성공 보고만으로 소리가 들린다고 판정 |
| 동기화 실패·미완료 | 남은 건수와 서버 실패·중복·미처리 구분. 재연결 후 기존 `기록 동기화 다시 시도`로 같은 UUID 재전송 | 로그아웃, 사이트 데이터 삭제, 대기열 삭제, 새 UUID로 같은 이력 재작성 |
| 카드판 저장 409 | 초안 보존, 최신 구성 확인 후 권한 있는 담당자가 변경 내용을 조정 | 버전 검사 우회, DB 직접 덮어쓰기 |
| 공용 카드 대기 | 실제 대기·날짜 확인, 권한 있는 담당자의 정상 검수 | 알림을 없애기 위한 일괄 승인·임의 삭제 |
| 다른 아동 데이터 노출 의심 | 영향 세션 중단, PRIVACY·TECH 호출, 증거 접근 제한. 담당자가 승인한 경계 격리 검토 | 실제 타인 데이터로 반복 재현, 공개 이슈에 원문·이미지 첨부 |

로그아웃은 대기 기록을 삭제할 수 있으므로 복구의 첫 단계가 아니다. 사용자의
동의·권한을 우회해 대기 기록을 서버로 강제 복사하지 않는다. 테스트 계정과 운영
사용자의 기록을 구분한다. 보안상 접근 차단과 데이터 보존이 충돌하면 담당자가
위험·영향·승인 범위를 기록하고 판단한다.

재시작이 필요하면 증거 수집 후 TECH·LEAD가 대상 서비스·중단 영향을 확인한다.
이 문서는 자동 재시작·DB 복구·일괄 세션 폐기·계정 잠금을 제공하지 않는다.
`docker compose down -v`, 볼륨 삭제·초기화, 전체 데이터 삭제는 장애 해소 절차로
사용하지 않는다. [기준선 마이그레이션 도구](../development/DATA_SCHEMA_MIGRATIONS.md)와
[로컬 백업·격리 복구](MIGRATION_BACKUP_RECOVERY.md)는 제공하지만 운영 백업 정책·
내용 변환·자동 롤백·실제 전환 리허설은 미완료다. 이전 코드로 강제 되돌리거나
임의 복구 명령을 실행하지 않고 별도 승인·계획을 받는다.
법적 판단·외부 통지 필요성은 PRIVACY가 필요한 별도 검토를 조정하며 이 문서로 확정하지 않는다.

## 6. 복구 확인과 종료

- 헬스와 영향 경로를 다시 확인한다. 캐시된 화면만 보거나 실패 수가 만료된 것을 복구 증거로 삼지 않는다.
- 해당 기기에서 카드 탐색·선택·기본 긴급/복구 표현·실제 소리 출력을 확인한다. 작성 중 문장·고정 보드가 유지돼야 한다.
- 동기화 장애는 동일 UUID의 서버 확인과 기기 남은 건수를 확인한다. 대기열을 지워 0건을 만드는 것은 복구가 아니다.
- 권한 문제는 승인된 테스트 계정으로 허용·비허용 경계를 재검증하고 실제 사용자 노출 증거는 제한된 저장소에 보관한다.
- LEAD는 FIELD의 확인과 TECH의 원인·조치·남은 위험을 받아 영향 세션 재개 여부를 기록한다. 개인정보 관련은 PRIVACY 검토를 함께 받는다.
- 담당자가 없거나 복구를 확인하지 못했으면 미해결로 남기고 영향을 받는 세션을 재개하지 않는다.

사고 기록은 승인된 비공개 위치에 보관하고 공개 이슈에는 익명 요약과 수정 커밋만
남긴다. 사후 검토에서 원인, 탐지 공백, 사용자 영향, 후속 작업·담당·기한을 정리한다.

```text
사고 번호 / 환경·기기 코드 / 발생 시각·시간대:
잠정·확정 등급 / 영향 과업·범위 / 확인된 대안:
최소 증거: 요청 ID, 경로 템플릿, 상태, 수치·시각, 배포 커밋:
담당 역할 / 호출·수신 확인·대체 연락 시각 / 다음 확인 시각:
승인된 조치·대상 / 데이터·대기 기록 보호 / 결과:
복구 검증 / 재개 승인 / 남은 위험:
원인·후속 작업 / 담당·기한 / 제한된 증거 위치:
```

서버 로그와 이 기록에 실명·발화 원문·토큰·개인 이미지·전체 내보내기 파일을 넣지 않는다.
민감 증거가 꼭 필요하면 별도 제한된 절차를 사용한다.

## 7. 적용 전 확인

- [ ] 역할별 실제 담당·대체자와 사용 가능 시간 확정
- [ ] 앱과 독립된 비공개 연락망 전달, 수신 확인·상향 연락 시험
- [ ] 실제 기기의 의사소통 대안과 세션 중단·재개 책임자 확인
- [ ] 테스트 전용 환경의 장애 모의훈련 및 결과 검토
- [ ] 로컬 백업·격리 복구 도구를 운영 백업·자동 롤백·계정 차단 완료로 오인하지 않도록 공유

현재 점검 증거와 미실행 훈련은 [장애 대응 검증 기록](../validation/INCIDENT_RESPONSE_VALIDATION.md)에 구분한다.
마이그레이션 전 백업과 실패 시 되돌리기는 [로컬 백업·격리 복구 절차](MIGRATION_BACKUP_RECOVERY.md)를 따른다.
감사 무결성 불일치는 [감사 보관·검증 절차](AUDIT_RETENTION_INTEGRITY.md)에 따라 기존
서명과 승인된 삭제/변경 증거를 보존하고 조사한다. 불일치를 감추기 위해 원본 서명을 덮어쓰지 않는다.
