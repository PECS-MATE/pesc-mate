# PECS MATE DB 질문 대비

현재 코드 기준의 발표 답변입니다. 굵은 문장부터 답하고 꼬리질문에 설명을 붙입니다.
실제 운영 DB의 인덱스 상태나 부하 성능까지 확인한 자료는 아닙니다.

## 1. 왜 관계형 DB 대신 MongoDB를 사용했나요

**카드 정보와 생성 결과처럼 구조가 다른 데이터를 문서 단위로 저장하기 위해 선택했습니다.**
문장 기록에는 카드 순서, 당시의 카드 정보, 생성 결과와 검증 정보를 함께 담습니다.
이런 데이터를 문서로 표현하도록 구현했습니다. 관계형 DB로도 구현할 수 있으며,
MongoDB가 항상 더 빠르다는 비교 실험을 한 것은 아닙니다.

## 2. 어떤 데이터를 저장하나요

**계정, 사용자 카드, 칩 매핑, 문장 생성 기록과 설정을 저장합니다.**

| 컬렉션 | 역할 |
|---|---|
| `users`, `auth_sessions` | 계정과 로그인 세션 |
| `card_submissions` | 사용자 등록 카드와 승인 상태 |
| `rfid_bindings` | 사용자별 UID와 카드 연결 |
| `rfid_shared_bindings` | 공용 UID와 카드 연결 |
| `communication_sessions` | 선택한 카드 순서와 문장·생성·검증 기록 |
| `privacy_settings`, `board_layouts`, `tts_settings` | 개인정보·보드·음성 설정 |

이 밖에 보호자 연결, 학습 기록, 감사 로그 등의 컬렉션도 있습니다.

## 3. 기본 카드도 모두 DB에서 가져오나요

**기본 카드 목록은 코드에 있고, 사용자 등록 카드는 DB에서 관리합니다.**
따라서 모든 카드가 하나의 DB 컬렉션에 들어 있다고 설명하지 않습니다.
서버에서 기본 목록과 접근 가능한 등록 카드를 확인해 사용합니다.

## 4. 카드 ID만 저장하면 되는데 당시 카드 정보도 왜 저장하나요

**나중에 카드가 바뀌어도 당시 어떤 카드로 문장을 만들었는지 확인하기 위해서입니다.**
생성 기록에 카드 ID와 순서, 사용자 카드의 당시 정보 등을 함께 담습니다.
현재 카드를 조회하기 위한 참조와 당시 기록을 설명하기 위한 정보를 함께 사용합니다.

## 5. 중복 데이터는 어떻게 막나요

**고유 인덱스와 요청 ID를 사용하고, 충돌하면 기존 값이나 오류를 반환합니다.**
사용자 이름은 고유 인덱스, 개인 칩 매핑은 `(user_id, uid)` 고유 인덱스로 보호합니다.
공용 칩 매핑은 UID를 문서 `_id`로 사용합니다.
문장 생성 기록은 요청 ID를 `_id`로 사용해 같은 요청의 중복 저장을 처리합니다.

꼬리질문: 같은 카드에 칩 여러 개를 연결할 수 있나요?

현재 공용카드 선택 화면은 이미 매핑된 카드를 제외하지만,
DB에 `card_id` 고유 제약을 둔 것은 아닙니다. UID 중복 방지와 카드별 하나만 허용하는
제약은 다릅니다. 화면 필터만으로 DB의 일대일 관계가 보장된다고 답하지 않습니다.

## 6. 두 담당자가 동시에 매핑을 수정하면 어떻게 되나요

**수정할 때 읽었던 revision을 비교하고, 이미 바뀌었다면 409 충돌을 반환합니다.**
공용 매핑 변경은 기존 revision을 확인하고 조건부 수정·삭제를 수행합니다.
관련 쓰기에는 DB 기반 공유 잠금도 사용합니다. 매핑 revision은 무조건 1씩 증가하는
번호가 아니며, 삭제 후 재등록한 데이터를 예전 버전과 구분하도록 새 값을 부여합니다.
여러 컬렉션을 수정하는 모든 작업이 하나의 트랜잭션이라고 설명하지 않습니다.

## 7. 인덱스는 어디에 걸었나요

**중복 방지와 사용자별 최근 기록 조회에 맞춰 인덱스를 정의했습니다.**

| 키 | 목적 |
|---|---|
| `users.username` 고유 | 같은 사용자 이름 중복 방지 |
| `rfid_bindings(user_id, uid)` 고유 | 같은 사용자 안에서 UID 중복 방지 |
| `communication_sessions(user_id, created_at 내림차순)` | 사용자별 최근 기록 조회 |
| `auth_sessions.expires_at` TTL | 만료 세션 정리 |

시작 시 인덱스를 생성하는 코드가 있습니다. 실제 DB에 모두 생성됐는지는 별도 확인이
필요하며, 대규모 성능 개선 효과를 측정했다고 주장하지 않습니다.

## 8. 같은 버튼을 두 번 눌러도 기록이 두 개 생기나요

**같은 요청 ID와 같은 내용의 재요청은 기존 기록을 돌려주도록 처리합니다.**
같은 ID로 다른 사용자나 다른 카드 내용의 요청을 보내면 충돌로 처리합니다.
서로 다른 요청 ID로 같은 카드를 보내는 경우까지 모두 중복으로 간주하는 것은 아닙니다.
문장 재사용 캐시와 요청의 중복 저장 방지는 별도 기능입니다.

## 9. 다른 사용자의 데이터를 볼 수 없게 어떻게 하나요

**로그인한 사용자와 지원 관계·관리 권한을 서버에서 확인한 뒤 데이터를 조회합니다.**
기능별로 사용자 조건과 권한 검사를 적용합니다. 사용자마다 별도 DB를 만드는 구조나
DB 자체의 행 단위 보안을 구현했다고 설명하지 않습니다.
권한 검사가 모든 경로에서 안전한지는 계속 검증해야 합니다.

## 10. 비밀번호와 로그인 토큰을 그대로 저장하나요

**비밀번호는 솔트를 적용한 PBKDF2 해시로, 세션 토큰은 SHA-256 해시로 저장합니다.**
현재 비밀번호 해시는 PBKDF2-HMAC-SHA256을 31만 회 적용합니다.
세션은 불투명 토큰 방식이며 JWT 방식이 아닙니다.
세션 만료 시각을 요청마다 검사하고, TTL 인덱스는 만료 데이터 정리에 사용합니다.
TTL 삭제가 즉시 실행된다는 가정으로 인증을 처리하지 않습니다.

## 11. 스키마가 없으면 데이터 형식이 제각각 되지 않나요

**API 입력 검증과 저장 규칙을 두고, 문서에는 schema_version을 기록합니다.**
`schema_version`은 데이터 형식을 구분하고 `revision`은 동시 수정을 구분합니다.
버전 필드가 있다고 이전 데이터가 자동 변환되거나 DB 수준의 모든 형식 검증이
보장되는 것은 아닙니다. 형식 변경 시 백업과 마이그레이션 검증이 필요합니다.

## 12. 카드 이미지는 어디에 저장하나요

**현재 등록 카드의 이미지와 썸네일 데이터는 카드 문서에서 관리합니다.**
목록 조회에서는 큰 이미지 필드를 제외하고 필요한 이미지는 별도 경로로 제공합니다.
현재 구현을 S3나 GridFS 기반이라고 설명하지 않습니다.
이미지 규모가 커지면 외부 파일 저장소 분리와 용량·응답 시간 검토가 필요합니다.

## 13. DB가 꺼져도 AI의 규칙 기반 대체 처리가 되나요

**외부 AI 장애에 대한 대체 처리와 DB 장애는 다릅니다. DB 장애 시 정상 사용을 보장하지 않습니다.**
규칙 기반 문장 대체는 외부 모델 실패를 위한 경로입니다.
계정·매핑·기록 저장이 필요한 DB 장애까지 해결하지 않으며,
현재 서버 상태 확인에서도 MongoDB 연결을 확인합니다.

## 14. 백업과 복구는 어떻게 하나요

**로컬 Compose MongoDB용 백업 도구가 있으며, 별도 DB에 복원해 확인하는 절차를 안내합니다.**
실제 마이그레이션 전에는 쓰기 작업을 멈추고 복원 결과를 검증해야 합니다.
DB 백업에는 `.env`, 브라우저 저장소, 외부 모델 파일까지 포함되지 않습니다.
압축 파일이라고 암호화된 것은 아니므로 개인정보가 포함된 백업의 접근 관리가 필요합니다.
자동 재해 복구나 정기 복원 훈련까지 완료했다고 답하지 않습니다.

## 15. 개인정보 삭제와 로그 보관은 어떻게 하나요

**삭제 중에는 관련 기록 쓰기를 제한하고, 감사 로그 보관 정리는 별도 절차로 처리합니다.**
기록 쓰기 전에 동의 상태와 삭제 상태·버전을 재확인하는 경로가 있습니다.
감사 로그는 세션처럼 자동 TTL로 삭제하는 정책이 아니라 명시적 보관 정리 도구를 사용합니다.
서비스에서 삭제해도 과거 백업이나 다른 브라우저의 데이터까지 자동 삭제되지는 않습니다.

## 16. DB 성능과 안정성은 얼마나 검증했나요

**기능 테스트와 동시 수정 방어를 구현했지만 대규모 운영 성능을 입증한 단계는 아닙니다.**
일반 백엔드 테스트는 mongomock 기반 검증을 포함합니다.
실제 MongoDB 부하·장애·복구 검증과 동일하지 않습니다.
동시 사용자 수나 초당 처리량은 별도 부하 측정 없이 숫자를 제시하지 않습니다.

## 가장 먼저 연습할 답변

“MongoDB에는 계정, 등록 카드, 칩 매핑과 문장 생성 기록을 저장합니다.
중복은 고유 인덱스와 요청 ID로 처리하고, 동시 수정은 revision을 비교해 충돌을 확인합니다.
비밀번호와 세션 토큰은 해시로 저장하며, 백업·복구와 대규모 부하 검증은
기능 테스트와 구분해 관리해야 합니다.”

## 확인 근거

- DB 연결: `backend/app/services/database.py`
- 인덱스 정의: `backend/app/services/indexes.py`
- 데이터 형식 버전: `backend/app/services/schema_versions.py`
- 칩 매핑과 동시 수정: `backend/app/services/rfid.py`
- 문장 기록과 재요청 처리: `backend/app/services/communication.py`
- 인증: `backend/app/services/authentication.py`
- 이미지: `backend/app/services/card_submissions.py`
- 기록 쓰기 보호: `backend/app/services/recording_guard.py`
