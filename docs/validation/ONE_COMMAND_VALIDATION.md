# 한 명령으로 로컬 검증

개발 서버와 별개의 Docker 환경에서 기존 테스트를 묶어 실행한다. 매번 명령을 조합하거나
호스트 Python 가상환경·Chrome 설치를 준비할 필요가 없다. 최초 빌드는 다운로드가 필요하며,
이후 의존성·브라우저 설치 레이어를 Docker 빌드 캐시로 재사용한다.

## 준비와 실행

- Node.js: 프런트엔드와 같은 지원 범위인 22.13 이상 22.x, 24.x 또는 26 이상
- Docker Desktop의 Linux 컨테이너와 Docker Compose v2를 실행한 상태
- 최초 이미지 빌드를 위한 인터넷 연결과 Docker 이미지·빌드 캐시 공간

프로젝트 루트에서 실행한다. 루트 패키지는 외부 의존성이 없으므로 별도 `npm install`은 필요 없다.

```powershell
npm run verify
```

| 명령 | 실행 범위 |
|---|---|
| `npm run verify` | 실행기·MongoDB 초기화 정책 검사, 백엔드 단위, 프런트엔드 단위·React·빌드 |
| `npm run verify:frontend` | 실행기·초기화 정책 검사와 프런트엔드 단위·React·빌드 |
| `npm run verify:backend` | 실행기·초기화 정책 검사와 백엔드 단위 |
| `npm run verify:full` | 기본 검증 + 격리 MongoDB 통합 + 서버 준비 상태 확인 + Chromium E2E |
| `npm run verify:security` | 기존 독립 인증 MongoDB 검증 스크립트; PowerShell 7 추가 필요 |

기본 검증에서 백엔드 단위와 프런트엔드 검사는 병렬 실행한다. DB 통합·브라우저는 그 뒤
순서대로 실행하고 브라우저 worker는 1개로 유지한다. 테스트 수·기대값·재시도 정책을
줄여 속도를 얻는 방식이 아니다. 프런트엔드만 수정했다면 해당 범위 명령으로 먼저 확인하고,
영향 범위가 큰 변경이나 커밋 전에는 필요한 전체·보안 검사를 추가한다.

셸 진입점도 같은 실행기를 사용한다.

```powershell
.\scripts\verify.ps1 full
.\scripts\verify.ps1 full -DryRun
```

```sh
sh scripts/verify.sh full
sh scripts/verify.sh frontend
```

실행 계획만 확인하려면 `node scripts/verify.mjs full --dry-run`, 사용법은
`node scripts/verify.mjs --help`다. 두 명령은 Docker·검증 환경·결과 폴더를 만들지 않는다.
실행기 자체 회귀 검사는 Docker 없이 `npm run test:verify`로 실행한다.

## 개발 환경 보호

- 실행마다 `pesc-verify-<UUID>` 프로젝트를 새로 만든다. 개발·인증 DB Compose 파일과
  병합하지 않고 `compose.verify.yaml` 하나와 비어 있는 `scripts/verify.env`만 지정한다.
- 개발 DB의 주소·볼륨, 저장소 `.env`, 운영 자격 증명을 사용하지 않는다. 컨테이너에
  Docker 소켓도 마운트하지 않는다. 검증용 데모 자격 증명은 외부 포트 없이 임시 환경에서만 사용한다.
- 검증 MongoDB는 tmpfs에만 저장하고 호스트 포트를 열지 않는다. API·웹 서버도 외부에
  공개하지 않는다. 런타임 네트워크는 내부 전용이며 Ollama·외부 이미지 심사는 비활성이다.
- 브라우저는 검증 웹 서버의 네트워크 공간을 공유해 내부 `127.0.0.1:5173`으로 접속한다.
  Vite의 호스트 검사나 서비스 워커의 secure-context 조건을 느슨하게 만들지 않는다.
  전체 E2E 전에 브라우저 컨테이너의 동일 주소로 API 상태를 확인해 연결 오류를 먼저 차단한다.
- 소스는 이미지에 복사한다. 개발 소스·`node_modules`·이미지 자산을 쓰기 가능한 상태로
  마운트하지 않는다. 브라우저 결과 폴더만 호스트에 기록한다.
- 빌드가 시작된 뒤 성공·실패·처리 가능한 취소 모두 해당 UUID 프로젝트의 `down`을
  시도한다. 개발 프로젝트를 내리거나 Docker 전체 `prune`을 실행하지 않는다.
- 로그·리포트·테스트 이미지는 남기고 임시 컨테이너·네트워크·검증 DB만 정리한다.
  Docker 캐시와 이미지가 쌓일 수 있으며 이 도구가 공유 캐시를 자동 삭제하지는 않는다.

검증 결과는 이미지 빌드 때 복사된 소스에 대한 결과다. 빌드 후 소스를 수정했다면
새 변경은 다시 검증해야 한다. 컨테이너 복사본으로 실행하므로 개발 서버 자동 재시작은
이 검증의 화면이나 API를 바꾸지 않는다.

## 결과와 오류

단계별 `RUN`·`PASS`·`FAIL`, 소요 시간과 장시간 실행 알림을 출력한다. 상세 로그는
`.local-validation/<시각-UUID>/`에 저장하며 Git에서 제외한다.

- `summary.json`: 전체 상태, 단계별 종료 코드·소요 시간·로그 파일
- `build.log`, `backend-unit.log`, `frontend-tests-build.log`: 설치·단위·빌드 출력
- `mongodb-integration.log`, `browser-e2e.log`: 전체 모드의 DB·브라우저 출력
- `browser/report/index.html`, `browser/artifacts/`: Playwright 리포트와 실패 추적 자료
- 실패 시 `service-logs.log`: 해당 임시 서버의 진단 로그

준비·검사·정리 중 하나라도 실패하면 명령은 0이 아닌 종료 코드를 반환한다. 독립된 두
기본 검사는 모두 끝까지 확인하되, 선행 검사 실패 시 DB·브라우저 단계로 넘어가지 않는다.
오류를 조회 0건으로 간주하거나 캐시된 이전 성공 리포트를 사용하지 않는다.

Ctrl+C를 처리할 수 있는 경우 진행 중 CLI를 중지하고 정리를 시도한다. 프로세스 강제 종료,
전원 차단이나 Docker 중단은 정리를 보장하지 않는다. 재시작 후 필요하면 출력·요약에 적힌
정확한 UUID 프로젝트만 같은 Compose 파일로 내린다. 정리 실패 시 실행기가 재시도 명령을
출력한다. 기존 `pesc-mate` 프로젝트나 이름을 확인하지 않은 볼륨은 삭제하지 않는다.

## 포함하지 않는 완료 조건

`full`은 위 표의 자동 회귀 검증 범위이며 인증 DB 검증·백업/복구 모의훈련·실제 태블릿과
AAC 사용자 검수·개인정보/라이선스 검토·운영 배포 승인을 대신하지 않는다. 인증 DB 변경은
`verify:security`도 실행한다. 기존 GitHub Actions 검증을 생략하거나 자동 push하지 않는다.

## 실행 검증 — 2026-10-20

Windows의 Docker Desktop Linux 컨테이너에서 최종 실행을 확인했다.

| 측정 | 결과 |
|---|---|
| 최초 의존성·브라우저 이미지 빌드 | 159.3초 |
| 캐시 재사용 전체 실행의 이미지 빌드 | 7.7초 |
| `npm run verify` | 45.0초, 정책/실행기 28개 + 백엔드 318개 + 프런트엔드 168개와 빌드 통과 |
| `npm run verify:full` | 331.8초, 위 기본 범위 + MongoDB 통합 53개 + Chromium 33개 통과; 총 600개와 빌드 |

수치는 이 PC의 실제 측정이며 다른 PC의 성능 보장이 아니다. 전체 검사 자체가 사라지지는
않으며, 준비 작업을 캐시하고 평소 변경 범위를 좁혀 선택하는 것이 주된 시간 절감 방법이다.

최초 시도에서는 `http://frontend:5173` 주소를 Vite의 호스트 검사가 403으로 차단했다.
직접 응답 본문으로 원인을 확인하고 해당 실행의 브라우저 컨테이너만 중단했다. 실패 상태·
진단 로그 보존과 UUID 프로젝트 정리 성공을 확인했다. 웹 서버 네트워크를 공유한 내부
localhost 방식으로 바꾼 뒤 최종 전체 33개가 통과했다. Vite의 허용 호스트를 확대하거나
브라우저 보안 플래그·기존 테스트 기대값·재시도 정책·제한 시간을 완화하지 않았다.

PowerShell과 Git Bash의 셸 진입점은 `full --dry-run`에 해당하는 실행 계획을 출력하는지
확인했다. 성공한 전체·기본 실행과 실패한 최초 실행 모두 검증 컨테이너가 남지 않았고,
기존 개발 스택의 backend/frontend/MongoDB는 계속 구동 중임을 확인했다. 테스트 이미지와
로그·리포트는 의도적으로 남겼으며 기존 개발 DB·사용자 이미지 자산을 변경하지 않았다.

CI에는 실행기 정책 회귀 검사를 추가했으나 원격 실행은 push/PR 이후 별도로 확인한다.
인증 DB 스크립트는 기존 구현을 호출하는 별도 명령이며 이번 도구 검증에서는 재실행하지 않았다.
