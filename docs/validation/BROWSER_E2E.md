# 역할별 브라우저 E2E

Playwright가 실제 브라우저에서 AAC 사용자, 보호자, 일반 담당자, 운영 권한 담당자의 로그인과 메뉴 접근 경계를 확인한다.

## 실행

애플리케이션 전체를 먼저 실행한다.

```powershell
docker compose up -d
cd frontend
npm run test:e2e
```

Windows에서는 설치된 Chrome을 자동으로 사용한다. 다른 브라우저 실행 파일을 사용하려면 `PLAYWRIGHT_BROWSER_PATH`에 절대 경로를 지정한다. Windows 이외의 환경이나 CI에서는 `npx playwright install --with-deps chromium`으로 Playwright 브라우저를 준비한다.

기본 프런트엔드 주소는 `http://127.0.0.1:5173`이며 API는 같은 출처의 `/api`를 사용한다. 다른 서버를 검증하려면 `E2E_BASE_URL`을 지정하고, API를 별도 출처로 직접 검증할 때만 `E2E_API_BASE_URL`을 지정한다.

## 검증 범위

- AAC 사용자에게 의사소통·학습 메뉴만 표시되는지 확인
- AAC 사용자의 다른 아동 대시보드 직접 API 요청이 403인지 확인
- 보호자와 일반 담당자에게 공용 콘텐츠 운영 메뉴가 숨겨지는지 확인
- 콘텐츠 운영 권한을 가진 담당자에게만 운영 메뉴가 표시되는지 확인
- 잘못 누른 표현을 취소하고 수정한 카드 조합으로 다시 말하는지 확인
- 기본 긴급·복구 음성 13개를 자동 재생 없이 저장하고 새 페이지에서 음성·API 요청 차단 상태로 실제 재생하는지 확인
- 기기 TTS 실패 시 저장된 WAV로 대체하고 하나의 요청 ID에 시작·성공 이력을 한 번씩 저장하는지 확인

2026-10-16 로컬 개발 스택과 Windows Chrome에서 위 7개 시나리오를 통과했다.
음성 재생 시험은 네이티브 Audio의 `playing`·`ended`, 디코딩된 길이와 저장 파일 바이트를 확인한다.
새 페이지 시험은 개발 앱 셸을 온라인으로 제공하므로 앱 완전 종료·오프라인 콜드 스타트 실기 검수를 대신하지 않는다.

## 사용자 흐름 회귀 검증

`frontend/e2e/workflows.spec.js`는 테스트마다 별도 AAC 계정을 만들고 다음을 확인한다.
종료 시 해당 계정의 카드·학습·발화·연결 데이터만 개인정보 삭제 API로 정리한다.
로그인 계정과 삭제 영수증은 서버 정책에 따라 남는다.

- 첫 문제를 푼 뒤 말하기 화면으로 이동하고 새로고침해도 같은 문제와 요청 ID로 재개하며 학습 결과를 한 번 저장한다.
- 오프라인 완료 결과를 IndexedDB에 넣고 재연결 후 같은 요청 ID로 전송한다. 다시 전송해도 참여 횟수는 한 번이다.
- 발화 원문 없이 카드 ID만 대기열에 넣고 동기화 503 뒤 같은 이벤트를 재시도한다. 서버에서도 한 건만 유지한다.
- 발화 이력 205건이 API 한도에 맞춰 100·100·5건으로 전송되며 동시 재연결에도 서버에 205건만 남는다.
- 보호자가 개인 PNG를 등록하면 WebP로 정규화되고, 고정 카드판에 추가한 카드가 아동 계정에서 선택된다.

기기 TTS는 흐름 검증용으로 대체하며, 실제 WAV 재생 검증은 `core-speech.spec.js`에서 별도로 수행한다.

`frontend/e2e/board-conflicts.spec.js`는 독립된 두 브라우저 컨텍스트에서 같은 아동의
빠른 표현을 편집한다. 먼저 저장한 구성만 반영되고, 두 번째 저장은 409로 거절되며
초안이 화면에 남는지 확인한다. 최신 구성 불러오기 후 재저장하면 버전이 증가하고
성공 감사 기록만 두 건 남아야 한다.

2026-10-16 최종 통합 실행에서 Windows Chrome·로컬 개발 스택의 브라우저 시나리오
13개가 모두 통과했다. 같은 코드의 백엔드 단위 테스트 162개, 프런트엔드 테스트
87개와 프로덕션 빌드도 통과했다. 백엔드 테스트는 테스트 의존성을 설치한 일회용
컨테이너에서 외부 모델 호출을 끄고 실행했다. 실제 태블릿 검수와 원격 CI 실행은 별도 확인이 필요하다.

## API 지표 연동 검증

`frontend/e2e/api-metrics.spec.js`는 실제 로컬 API에 요청해 비로그인 401,
AAC 사용자·보호자·일반 담당자 403, 운영 권한 담당자 200과 캐시 금지를 확인한다.
임의 경로의 404를 집계해도 경로 원문·검색어가 응답에 포함되지 않고 누적 분포 개수가
요청 수와 일치하는지 확인한다. 화면 조작 대신 Playwright의 API 클라이언트를 사용하는
검증이며 2026-10-17 두 테스트를 통과했다.

## TTS 지표와 중복 보고 검증

`frontend/e2e/tts-metrics.spec.js`는 테스트 전용 AAC 계정의 성공·실패·취소·결과 미수신
이력을 실제 MongoDB에 저장하고 운영 전용 집계를 확인한다. 0ms와 누락 지연을 구분하고,
동일 ID 시작·완료 재전송과 동시 완료가 건수·최초 결과를 바꾸지 않는지 검증한다.
오류 코드의 임의 텍스트와 사용자·요청 ID는 집계 응답에 포함되지 않아야 하며,
다른 계정의 요청 ID 시작은 409, 완료는 404여야 한다. 검증 계정의 콘텐츠만 종료 시 정리한다.
이 시험은 클라이언트 보고 집계를 확인하며 기기에서 실제로 들린 소리의 성공률을 뜻하지 않는다.

2026-10-17 Windows Chrome·로컬 개발 스택에서 `tts-metrics.spec.js` 3개,
`core-speech.spec.js` 2개, `api-metrics.spec.js` 2개를 함께 실행해 7개 모두 통과했다.
기본 음성 준비와 비동기 이력 응답은 다운로드·API 요청 제한을 고려해 최대 20초까지
확인한다. 이는 재생 시작 지연의 허용 기준이 아니며, 네이티브 오디오 재생·종료와
동일 요청 ID의 성공 보고를 별도로 검사한다. 실제 태블릿 검수는 여전히 별도다.

## 오프라인 동기화 지표 검증

`frontend/e2e/offline-sync-metrics.spec.js`는 운영자 조회 권한을 검사하고, 실제 API에
발화·학습을 저장한 뒤 브라우저 응답만 끊어 기기 대기열이 유지되는지 확인한다.
새로고침 뒤 같은 UUID로 재전송하면 재시도 헤더가 0에서 1로 바뀌고, DB에는 각각
한 건만 남으며 신규 2·중복 2·재시도 2가 집계돼야 한다. 로컬 표시·사용자 ID는 본문에
전송하지 않고, 지표에 사용자·요청 ID를 노출하지 않는다.

부분 저장 후 다른 계정의 UUID와 충돌하면 신규·실패·미처리를 각각 구분하고,
정상 항목 재전송은 중복을 제거해야 한다. 같은 발화·학습 UUID로 동시에 10번씩
요청해도 각각 한 건만 저장되고 신규 2·중복 18로 집계되는지 추가로 확인한다.
테스트 전용 계정의 콘텐츠만 정리하며 기기의 실제 오프라인 지원 판정과는 구분한다.

2026-10-17 Windows Chrome·로컬 개발 스택에서 동기화 지표 4개와
`workflows.spec.js` 5개를 함께 실행해 9개 모두 통과했다. 백엔드 단위 테스트 203개,
프런트엔드 단위·컴포넌트 테스트 107개와 프로덕션 빌드도 통과했다. 초기 연결 실패는
중지된 로컬 개발 스택을 다시 실행한 뒤 해소됐으며, 데이터 볼륨은 삭제하지 않았다.

## 운영 알림 검증

`frontend/e2e/operational-alerts.spec.js`는 운영 권한 조회 경계를 검사하고, 테스트
전용 계정의 공용 카드를 실제 제출해 대기 알림이 증가하는지 확인한다. 390px 화면에서
알림 제목과 숫자가 겹치지 않아야 하며, 알림에서 검수 목록으로 이동해 승인하면
다음 조회에서 대기 수가 감소해야 한다. 로그아웃하면 알림 패널도 제거한다.
음성 최종 실패 보고와 동기화 서비스 실패가 3회 이상이면 각각 고정 알림 하나를
표시하며, 임의 오류 코드·사용자·요청 ID를 알림 응답에 포함하지 않아야 한다.

2026-10-17 Windows Chrome·로컬 스택에서 운영 알림 3개와 API·TTS·동기화 지표
9개를 함께 실행해 12개 모두 통과했다. 백엔드 단위 테스트 216개,
프런트엔드 단위·컴포넌트 테스트 115개와 프로덕션 빌드도 통과했다.
이는 화면 내 알림 검증이며 외부 푸시·이메일·실제 태블릿 검수는 포함하지 않는다.

## 데이터 버전 기준선 회귀 검증

2026-10-17 신규 MongoDB 문서에 `schema_version=1`을 추가한 뒤 로컬 개발 스택과
Windows Chrome에서 브라우저 전체 25개가 통과했다. 기존 버전 누락 문서와 신규
문서가 공존하는 상태에서 로그인·역할 경계·카드·기기 음성·학습·재시도·보드 충돌
흐름을 검증했다. 별도 백엔드 단위 테스트 235개와 실제 임시 DB 마이그레이션 시험
5개도 통과했다. 기존 로컬 DB의 일괄 적용과 운영 백업·복원 리허설은 실행하지 않았다.
자세한 범위는 [데이터 버전·마이그레이션](../development/DATA_SCHEMA_MIGRATIONS.md)을 따른다.

## PR 자동 검사

`.github/workflows/ci.yml`은 백엔드 단위 테스트, 프런트엔드 테스트·빌드와 브라우저 E2E를 실행한다.
E2E는 임시 MongoDB의 `pesc_mate_e2e` 데이터베이스를 쓰며 외부 모델 호출을 끈다.
`E2E_START_SERVERS=true`일 때 Playwright가 API·프런트엔드 서버를 시작하고 종료한다.
실패 시 `browser-test-results` 아티팩트에 보고서·화면·trace를 7일 보관한다.
워크플로우 설정의 원격 성공 여부는 push/PR 후 GitHub Actions에서 확인한다.

실패하면 `frontend/test-results`에 HTML 보고서, 화면, 브라우저 콘솔, 네트워크 요청이 포함된 trace를 남긴다. 이 디렉터리는 테스트 산출물이므로 Git에는 포함하지 않는다.
