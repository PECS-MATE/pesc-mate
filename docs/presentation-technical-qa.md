# PECS MATE 기술 질문 대비

답변은 현재 구현 기준입니다. 먼저 굵은 한 문장으로 답하고, 꼬리질문이 있을 때
세부 설명을 붙입니다. 사용하지 않은 기술을 썼다고 답하지 않습니다.

DB 선택 이유·구조·인덱스·동시 수정·백업 질문은
[DB 질문 대비](presentation-db-qa.md)에서 별도로 연습합니다.

## 1. 전체 시스템은 어떻게 구성했나요

**React 화면, FastAPI 서버, MongoDB, Arduino RFID 장치로 구성했습니다.**
브라우저가 USB로 칩 UID를 읽고 서버에서 연결된 카드를 조회합니다.
문장 생성은 서버가 OpenRouter의 Qwen 모델에 요청하고, 음성은 별도 합성 경로로 처리합니다.
서버·DB·음성 워커는 Docker Compose로 실행합니다.

```text
RC522 → SPI → UNO R4 → USB 시리얼 → React → FastAPI → MongoDB
                                               ├→ OpenRouter Qwen 문장 생성
                                               └→ 음성 합성 워커 → WAV 재생
```

## 2. 왜 FastAPI와 MongoDB를 사용했나요

**API 입력 검증과 기능 분리를 구현하고, 카드·매핑·사용 기록을 저장하기 위해 사용했습니다.**
FastAPI에서 요청 형식을 검증하고 서비스 계층에서 권한과 실제 처리를 수행합니다.
MongoDB에는 카드 의미 정보와 생성·검증 기록을 문서로 보관합니다.
다른 프레임워크나 관계형 DB보다 항상 빠르다는 비교 실험을 한 것은 아닙니다.

## 3. Arduino에서 웹으로 데이터를 어떻게 보내나요

**USB 시리얼로 한 줄씩 JSON을 보내고, 브라우저에서 파싱합니다.**
현재 프로토콜은 `snapshot`에 `protocol_version`, `boot_id`, `event_id`,
리더별 `status`와 `uid`를 담습니다. 웹은 형식과 상태 값을 검사하고 UID를 정규화합니다.
현재 시연은 USB 포트 접근을 지원하는 PC 브라우저에서 연결합니다.

## 4. 왜 boot_id와 event_id가 필요한가요

**보드 재시작과 같은 부팅 안에서의 이벤트 순서를 구분하기 위해서입니다.**
`boot_id`는 재시작 구분에, `event_id`는 프레임 순서 확인에 사용합니다.
이 번호를 인증 비밀키로 사용하는 것은 아닙니다.

## 5. 카드 없음과 리더 고장을 어떻게 구분하나요

**펌웨어가 PRESENT·EMPTY·ERROR를 구분하고, 별도 진단 명령도 제공합니다.**
단순히 UID가 없다는 이유만으로 카드 없음으로 처리하지 않습니다.
`STATUS test1` 진단에서는 리더 버전 레지스터가 0이나 255이면 오류로 표시합니다.
통신 오류의 원인이 전원인지 배선인지까지 JSON만으로 확정할 수는 없습니다.

## 6. 한 카드를 계속 대고 있으면 중복 입력되지 않나요

**펌웨어의 연속 확인과 웹의 표시·입력 추적으로 반복 읽기를 처리합니다.**
펌웨어는 같은 UID를 두 번 확인한 뒤 감지 상태로 바꾸고, 제거도 연속 미감지와
경과 시간을 보고 판단합니다. 웹의 큐 모드는 같은 칩을 한 번만 담습니다.
현재 USB 펌웨어와 진단용 구형 출력은 상태 판별 능력이 다르므로 구분합니다.

## 7. 리더 세 개는 어떻게 연결했나요

**SPI의 SCK·MOSI·MISO는 공유하고, 리더별 SS와 RST를 분리했습니다.**
SS는 D10·D8·D7, RST는 D9·D6·D5입니다. UNO와 RC522 사이에는
전압 레벨 변환을 구성했습니다. 전원과 공통 GND가 빠지면 통신이 안 됩니다.
특정 컨버터가 모든 SPI 속도와 배선 길이에서 안정적이라고 보장하는 것은 아닙니다.

## 8. 칩과 카드의 매핑은 어디에 저장하나요

**칩에 그림을 넣는 대신, 서버에 UID와 카드 ID의 연결을 저장합니다.**
공용 매핑과 사용자별 연결을 구분합니다. 운영 담당자의 공용 검색에서는 이미 연결된
카드를 제외하고, 별도 확인 화면에서 칩을 스캔하면 연결된 카드를 표시합니다.

## 9. 연속 스캔할 때 이전 응답이 나중에 도착하면 어떻게 하나요

**확인 화면은 조회 순번을 비교해 가장 최근 스캔의 결과만 반영합니다.**
다음 칩을 읽으면 이전 카드 표시를 지우고 조회 상태로 바꿉니다.
이전 요청이 늦게 끝나도 최신 화면을 덮지 않으며, 화면 종료나 로그인 변경도 확인합니다.

## 10. AI에는 무엇을 보내고 무엇을 받나요

**선택한 카드 이름, 규칙 문장, 출력 지침을 보내고 짧은 한국어 한 문장을 받습니다.**
현재 모델은 `qwen/qwen3-30b-a3b-instruct-2507`이며, 서버에서만 API 키를 사용합니다.
학습이나 파인튜닝을 한 것이 아니라 기존 모델을 API로 호출한 것입니다.

## 11. AI가 카드와 다른 문장을 만들면 어떻게 하나요

**응답 형식과 카드 의미 및 안전 항목을 검사하고, 실패하면 규칙 문장으로 바꿉니다.**
선택하지 않은 주어를 임의로 넣는지, 문장이 너무 길거나 여러 줄인지 등을 확인합니다.
이후 카드 의미와 안전 규칙도 확인합니다. 규칙 기반 검증이므로 모든 의미 오류를
완벽히 판별한다고 주장하지 않습니다.

## 12. 속도 개선은 어떻게 했나요

**문장 생성을 클라우드로 옮기고, 짧은 출력과 검증된 결과 재사용으로 지연을 줄였습니다.**
현재 출력 상한은 기본 96토큰, API 제한 시간은 기본 8초이며 긴 추론 출력을 요청하지 않습니다.
예제에서 약 0.86~1.34초를 확인했지만 실제 네트워크에서 달라질 수 있습니다.
API 요청 실패 시 느린 로컬 모델을 다시 호출하지 않고 규칙 문장으로 대체합니다.
8초는 HTTP 요청 제한 설정이지 모든 단계의 완료 시간을 보장하는 수치는 아닙니다.

## 13. 캐시 때문에 다른 아동의 문장이 섞이지 않나요

**문장 재사용은 같은 계정의 최근 기록만 대상으로 합니다.**
카드 순서·맞춤 카드 의미·모델·제공자·정책 버전이 맞고 검증도 통과해야 재사용합니다.
현재 재사용 기간은 5분이며, 명시적 재생성은 API를 다시 호출합니다.
음성은 별도 캐시를 사용하므로 문장 캐시와 구분해서 설명합니다.

## 14. 문장 생성과 음성 출력은 같은 모델인가요

**별도입니다. OpenRouter Qwen은 문장 생성이고, 현재 음성 실행 구성은 MeloTTS입니다.**
음성 서버가 반환한 WAV를 브라우저에서 재생합니다.
요청 성공과 실제 소리 재생 완료를 구분해 처리하며, 음성 요청은 큐와 캐시로 관리합니다.
Qwen 음성 API 코드는 준비했지만 실제 연결 검증이 끝난 것처럼 소개하지 않습니다.

## 15. 인터넷 연결 여부는 어떻게 판단하나요

**인터넷 상태 신호만 믿지 않고 로컬 API 서버의 응답을 확인합니다.**
PC 핫스팟은 인터넷이 없어도 로컬 웹에 접근할 수 있기 때문입니다.
다만 로컬 웹 접속 가능과 서버의 외부 문장 생성 API 접속 가능은 별개입니다.
서버가 살아 있다는 상태 검사만으로 외부 API 키와 잔액까지 검증되지는 않습니다.

## 16. 중복 요청으로 기록이 두 번 저장되지 않나요

**요청 ID를 사용해 동일 요청의 재전송과 새로운 요청을 구분합니다.**
이미 저장한 요청 ID로 같은 카드를 다시 보내면 기존 결과를 반환합니다.
같은 요청 ID에 다른 카드가 들어오면 충돌로 거절합니다.

## 17. 로그인은 JWT인가요

**현재는 JWT가 아니라 서버에서 조회하는 불투명 세션 토큰 방식입니다.**
비밀번호는 개별 salt와 PBKDF2-HMAC-SHA256으로 해시하고,
API에서 로그인과 기능별 권한 및 연결 사용자 범위를 확인합니다.
클라이언트에서 메뉴를 숨기는 것만으로 권한을 통제하지 않습니다.

## 18. 무엇을 테스트했나요

**API 요청·검증·대체·캐시와 RFID 화면 동작을 자동 테스트하고, 일부 실제 호출도 확인했습니다.**
OpenRouter 변경의 관련 테스트 28개가 통과했고 예제 API 호출도 성공했습니다.
당시 전체 백엔드 검사에는 API 계약 기준 관련 실패 2개가 남았습니다.
테스트 통과가 실제 아동 사용성이나 모든 기기에서의 안정성 입증을 뜻하지는 않습니다.

## 답변에서 피할 표현

| 질문 | 피할 답변 | 현재 구현에 맞는 답변 |
|---|---|---|
| 모델을 직접 만들었나요 | 큐웬을 직접 학습했다 | 기존 모델 API를 서비스 흐름에 연결했다 |
| 보안은 완벽한가요 | UID나 토큰이 있어 절대 안전하다 | 권한 검사를 하며 추가 보안 검증은 필요하다 |
| 어디서나 USB가 되나요 | 모든 폰과 태블릿에서 된다 | 현재 시연은 지원 PC 브라우저에서 확인한다 |
| 비용이 3만 원을 넘지 않나요 | 코드가 무조건 3만 원에서 멈춘다 | 현재 총액 강제 차단은 없고 계정 한도로 관리한다 |
| 성능은 항상 1초인가요 | 모든 요청이 1초 안에 끝난다 | 예제 측정값이며 전체 음성 지연과는 별개다 |

## 코드 확인 위치

- 문장 생성·설정: `backend/app/services/model.py`
- 의미 검증·재사용·기록: `backend/app/services/communication.py`
- 음성 합성 경로: `backend/app/services/server_speech.py`
- 세션 인증: `backend/app/services/authentication.py`
- USB 파싱·연결: `frontend/src/services/usbRfid.js`
- 연속 칩 확인: `frontend/src/rfid-chip-check-page.jsx`
- 리더 펌웨어: `hardware/arduino/rfid-usb-board/rfid-usb-board.ino`
